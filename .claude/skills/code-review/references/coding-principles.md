# AI開発用 コーディング原則（AI常時参照版）

コードを**書く・直す・レビューする**ときの判断語彙。`ai-security-guardrails.md`（P0=絶対遵守）と違い、これは**機械的チェックリストではなく判断基準の語彙集**である。各技法に ID（A-1 等）と確立した名前を付す——指摘・記録では **ID か技法名で引用**すること。

## 0. 使い方（最優先）

- **生成・リファクタ時**（tdd-implement の Refactor 等）: 改善の「手」を選ぶチェックリストとして使う。
- **レビュー時**（code-review の H/I レンズ等）: 指摘の語彙・根拠として使う。ただし**主観の押し付けにしない**——明確な違反・実害があるもの以外は LOW〜MEDIUM・信頼性 🟡/🔴 に留める。
- **ただし E-1〜E-4（機能バグの反復パターン）は例外**: これらは好みの問題ではなく**実害のある機能バグ**なので、上の「LOW〜MEDIUM に留める」は適用しない。該当すれば実害に応じた重大度を付け、**修正＋リグレッションテスト**まで求める。レビュー観点としては H/I ではなく B（ロジック）・D（エラー処理）・E（既存整合）・F（実データ整合）側で効く。
- **プロジェクト固有規約（CLAUDE.md・note.md・既存コードのパターン）が常に優先**する。適用しない判断も正当（理由を一言）。
- **最優先の一原則**: 迷ったら **C-1 高凝集×疎結合**。これが満たされれば他の多くは自然に満たされる。

## A. 読みやすさ（Readability）

- **A-1 背景コメント（Why コメント）** — コメントは「何をするか」の直訳ではなく「**なぜこのコードが在るか**」（背景・制約・落とし穴）だけを書く。実装の言い換え・進捗ログ的コメントは書かない。コードで表せることは命名・構造で表す。
- **A-2 要約変数（Summary Variable）** — 複雑な式・条件に意味のある名前を与えて1変数に束ねる（例: `const isEligible = age >= 18 && hasConsent`）。コメントの代わりに変数名で語る。
- **A-3 説明変数とデメテルの法則（Explaining Variable / Law of Demeter）** — 深いチェーン参照（`a.b.c[0].d`）は中間変数で段階化する。「直接の友達とだけ話す」。
- **A-4 意図の関数化（Extract Function）** — 同じ関心事のかたまりは、意図を表す名前の関数に切り出す（例: `isUserIdValid()`）。関数名が仕様の文になる。
- **A-5 ガード節（Guard Clause／早期リターン）** — 前提チェック・バリデーションは冒頭で return し、本処理のネストを浅く保つ。
- **A-6 驚き最小の原則（Principle of Least Astonishment）** — 名前・シグネチャから予想されるとおりに振る舞う。隠れた副作用を持たない。

## B. 変更に強い構造（Changeability）

- **B-1 不変優先（Immutability First）** — 状態は原則 `readonly`/`const`。生成時（コンストラクタ）に検証し、**不正な状態のオブジェクトを作らせない**。可変は必要な箇所だけ。
- **B-2 実装を見ずに使える公開面（Self-Explanatory Interface／カプセル化）** — 公開面（コンストラクタ・型・シグネチャ）だけで正しく使えるよう設計する。必須値はコンストラクタで強制する。※code-map の「公開シンボルで再利用」の前提となる原則。
- **B-3 境界での隠蔽（Facade / Factory／腐敗防止層）** — レガシー・複雑な外部 API は境界の1箇所（Factory・アダプタ）に閉じ込め、正しい使い方だけを提供する。
- **B-4 コンポジション優先（Composition over Inheritance）** — 実装共有のための継承は使わない。部品を持たせて委譲する。
- **B-5 依存性注入（DI: Dependency Injection）** — 外部依存（HTTP クライアント・時計・乱数・プロセス起動等）はコンストラクタ/引数で注入する。テストでの差し替え・環境切替を可能にする。
- **B-6 依存性逆転（DIP: Dependency Inversion Principle）** — 上位（ビジネスロジック）は下位（DB・外部 API）の具体実装ではなくインターフェースに依存する。
- **B-7 型で守る（Generics）** — `any`／キャストではなく型パラメータで安全に汎用化する。

## C. 凝集・結合と抽象化の張力（Tension）

- **C-1 高凝集×疎結合（High Cohesion, Loose Coupling）** — 関連するデータと処理は近くに置き、モジュール間は契約（インターフェース）越しに繋ぐ。**最優先原則**。
- **C-2 DRY（本質の重複排除）** — 同じ「知識・仕様」が2箇所にあるなら1箇所へ。既存の公開シンボル（code-map）を再利用する。
- **C-3 AHA／偶然の一致を共通化しない（Avoid Hasty Abstractions）** — **C-2 の対**。「たまたま今は同じ」コードでも、**変更理由（本質）が違うなら共通化しない**。誤った抽象より重複の方が安い。
- **C-4 三度目の法則（Rule of Three）** — 抽象化は3回目の出現まで待ってよい。2回目までは重複を許容し、パターンが確定してから括る。
- **C-5 YAGNI（You Aren't Gonna Need It）** — 今の要件に無い拡張ポイント・設定・汎用化を先回りで作らない。

> C-2 と C-3/C-4 は**張力**であり、常に両方を天秤にかける。「重複を見つけたら即共通化」も「共通化を一切しない」もどちらも誤り。

## D. アーキテクチャ指針（サービス/モジュール境界レベルは service-boundary スキルが担当）

- **D-1 依存は中心へ（Clean / Onion Architecture）** — ドメイン（ビジネスロジック）を中心に置き、DB・UI・外部サービスは外側の交換可能な詳細として、依存を内向きにする。
- **D-2 読み書き分離（CQS: Command-Query Separation）** — 問い合わせ（副作用なし）と命令（状態変更）を1つの関数に混ぜない。
- **D-3 契約から生成（Contract-First）** — API・スキーマは契約（OpenAPI・interfaces・schema）を正とし、可能なら型/SDK を機械生成する（beam3 の設計契約と同じ思想）。

## E. LLM が特にやりがちな逸脱（自己点検リスト）

### E-a. 書き方の逸脱（ID なし。指摘は該当する A〜D の ID で引用する）

- **過剰コメント**: 実装の直訳・作業ログ的コメントの量産 → **A-1 違反**。「なぜ」以外は書かない。
- **早すぎる共通化**: 2箇所の類似を見て即ヘルパー化 → **C-3/C-4 違反**。「変更理由は同じか？」を自問する。
- **浅いラッパーの乱造**: 1行だけの意味のない委譲関数・クラス → 凝集を下げるだけ（**C-1 違反**）。
- **巨大関数・巨大差分**: 関心事が混在 → **A-4（切り出し）・A-5（ガード節）**で構造化する。
- **不要な防御的コード**: 到達不能な null チェック・エラーを握り潰す try/catch → **A-6 違反**。エラーは適切に伝播させる。
- **既存パターンの無視**: プロジェクトの流儀と違う独自流の持ち込み → 固有規約・code-map の既存規約が**常に優先**。

### E-b. 機能バグの反復パターン（E-1〜E-4。ID で引用する）

> **なぜ別枠か**: E-a はレビューで見つけやすい「書き方」の問題だが、以下は**一見動くコードに見える機能バグ**である。しかも AI は同じものを繰り返し作り込む。**AI が書いたコードを同じ AI がレビューすると、両方に同じ前提（盲点）が入る**ため、これらは**レビューでは安定して捕まらない**——機械的なテストで固定するしかない。
>
> したがって **E-1〜E-4 を発見したら、修正と同時に ID を名前に含めたリグレッションテストを書く**（例: `E-1 リグレッション: キャッシュ命中時も同じ形状を返す`）。テスト名にバグ ID を入れておくと、次に同じ盲点が再発したとき即座に落ちる。

- **E-1 多重コードパスの不整合（Multi-Path Divergence）** ★最頻出 — 同じ契約（レスポンス形状・戻り値・状態）を返す**経路が2つ以上**あるとき（本番/モック・feature flag の on/off・キャッシュ命中/ミス・環境分岐など）、**片方だけ直してもう片方を忘れる**。型は通り、片方の経路でしか再現しないため発覚が遅れる。
  - 対策: 契約を**1箇所に定義**して全経路から参照する。分岐が残るなら「**全経路が同じ形状を返す**」ことをテストで固定する。
  - レビュー時: 差分が分岐の**片側しか触っていない**箇所を必ず疑う。
- **E-2 契約フィールドの取得漏れ（Contract Field Omission）** — 戻り値・レスポンスに新しいフィールドを足したが、**その値を取得する側**（DB の射影・SELECT 句・DTO 変換・マッピング）に足し忘れる。型チェックは通るのに実行時は常に `undefined` になる。
  - 対策: 必須フィールドの一覧を1箇所に持ち、**全フィールドが存在すること**をテストでアサートする。
- **E-3 失敗時に古い状態が残る（Stale State on Error）** — エラーハンドリングを足したが、**エラー表示だけして古いデータを消さない**。前回の結果が表示され続け、利用者には成功しているように見える。
  - 対策: エラー経路で関連する状態を**明示的にリセット**する。「失敗したとき何を消すか」を必ずセットで設計する。
- **E-4 楽観的更新のロールバック欠如（Missing Rollback）** — UI や状態を先に更新してから非同期処理を投げるが、**失敗時に元へ戻さない**。画面と実データが乖離する。
  - 対策: 変更前の状態を保持し、失敗時に必ず復元する。
