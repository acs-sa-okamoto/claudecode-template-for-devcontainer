# レビューレポート出力テンプレート

このファイルは `code-review` スキルがレビューレポートを生成する際に参照する書式・記法・見本の定義です。書式を勝手に変えてはいけません。

---

## 1. 記法ルール（必須）

### 1.1 重大度（Severity）

各指摘には必ず重大度を付ける。**「直さないと何が起きるか」**で決める。

| 重大度 | 意味 | 対応 |
|---|---|---|
| 🔴 CRITICAL | セキュリティ P0 違反 / データ損失・破壊 / 本番障害に直結 | **マージ前に必須修正** |
| 🟠 HIGH | 明確なバグ / 重大なロジック誤り / 重要な要件未達 | 修正を強く推奨 |
| 🟡 MEDIUM | 限定条件で問題化 / 保守性・堅牢性の懸念 | 修正推奨 |
| 🔵 LOW | 軽微・スタイル・改善提案 | 任意 |

### 1.2 信頼性レベル（Confidence）— 重大度とは別軸

各指摘には必ず信頼性レベルを付ける。**断定と仮説を区別する**ためのもので、誤検知ノイズを抑える肝。

- 🔵 **確実**: 差分内で根拠が完結する明確な問題。
- 🟡 **妥当な推測**: 文脈次第で問題になる。確認が必要。
- 🔴 **推測**: 仮説。別の意図・見落としの可能性が残る。

> 重大度（影響の大きさ）と信頼性（確からしさ）は独立。例: 「🔴 CRITICAL／🟡 妥当な推測」＝もし本当ならクリティカルだが要確認、という指摘もありうる。

### 1.3 カテゴリ

指摘は以下のいずれかに分類する：
`セキュリティ` / `ロジック` / `非同期・並行` / `エラー処理・リソース` / `整合性・規約` / `実データ整合` / `要件適合` / `可読性・保守性` / `設計` / `パフォーマンス` / `テスト・CI` / `その他`

### 1.4 指摘の書式

各指摘は ID（`FINDING-NN`、ゼロパディング2桁）を持ち、以下の形式で書く：

```
#### [FINDING-NN] {重大度絵文字} {重大度} ｜ {カテゴリ} ｜ 信頼性: {信頼性絵文字} {信頼性}
- **場所**: `相対パス:行番号`
- **根拠**: なぜ問題か（何がどう壊れるか）を具体的に
- **修正提案**: 具体的な修正方針。可能ならコード断片や diff で示す
```

- 場所は**プロジェクトルートからの相対パス**＋行番号。
- 根拠を示せない指摘は出さない。

### 1.5 数値・事実で書く

「危険」「良くない」といった曖昧表現は禁止。「N 件目で配列外参照」「認証チェックが無い」など、検証可能な事実で書く。

## 2. 出力テンプレート

以下のテンプレートに従ってレポートを生成する。`[...]` は実際の内容で置き換える。

**プロジェクト種別:** [beam / 一般]
**CIステータス:** [gh pr checks の結果（成功/失敗の件数） / 取得不可]
**レビュー日:** [YYYY-MM-DD]

---

## サマリー

| 重大度 | 件数 |

| 🔴 CRITICAL | [n] |

**カテゴリ別:** セキュリティ [n] / ロジック [n] / 非同期・並行 [n] / エラー処理・リソース [n] / 整合性・規約 [n] / 実データ整合 [n] / 要件適合 [n] / 可読性・保守性 [n] / 設計 [n] / パフォーマンス [n] / テスト・CI [n]

## 3. 見本（指摘1件）

````markdown
#### [FINDING-03] 🟠 HIGH ｜ 整合性・規約 ｜ 信頼性: 🔵 確実
- **場所**: `src/repositories/userRepo.ts:31`
- **根拠**: DB トランザクション `tx` の内側で外部決済 API `stripe.charge()` を呼んでいる。外部 API は数秒かかりうるため、その間 DB の行ロックが保持され、同時実行時にロック枯渇・タイムアウトを招く。既存の `orderRepo.ts:50` ではトランザクション外で外部呼び出しを行っており、規約とも不整合。
- **修正提案**: 外部 API 呼び出しをトランザクションの外へ出す。「①ローカル整合性チェック（tx内）→ ②commit → ③外部API → ④結果を別txで反映」の順に分割し、`orderRepo.ts` のパターンに合わせる。
````
