# AI開発用 ビルド・デプロイ ハイジーン（AI常時参照版）

ソフトウェアを**設定する・ビルドする・デプロイする**ときの判断語彙。`coding-principles.md`（コード設計の語彙）と `ai-security-guardrails.md`（P0=絶対遵守のセキュリティ）を補完する第3のレンズで、**「コードは正しいのに、ランタイム・依存・ツール設定・デプロイ手順のせいで品質が静かに落ちる／本番で壊れる」層**を扱う。各項目に ID（R-1 等）を振る——指摘・記録では **ID か技法名で引用**すること。ID は coding-principles（A〜E）や code-review の観点レター（A〜K）と衝突しない **R / P / T / V** を用いる。

## 0. 使い方（最優先）

- **設定・変更時**（direct-implement の setup、依存追加、ツール設定変更）: 「落とし穴を踏んでいないか」の判断語彙として使う。
- **レビュー時**（code-review で差分が `package.json`・lint/tsconfig・CI・フレームワーク設定を触ったとき）: 指摘の語彙・根拠として使う。
- **デプロイ前検証時**（power6-verify 等）: V 群を検証手順の観点として使う。
- **プロジェクト固有規約（CLAUDE.md・note.md・既存の設定パターン）が常に優先**する。適用しない判断も正当——黙って飛ばさず「なぜ不要か」を一言述べる。
- **プロジェクト種別で適用範囲が変わる**: 本レンズは**デプロイ型の Web/アプリ**を主対象とする。非デプロイ型（CLI・ライブラリ・データパイプライン等）では *prod* を前提とする項目が非該当になる（**R-2 dev/prod パリティ／R-3 コンテナ固定〔非コンテナ時〕／V-1 の「デプロイと同じビルド」の部分**）。一方 **V-1 の「クリーン環境でビルド」・P-2 lockfile・T 群 は非デプロイ型でも同様に効く**（ライブラリなら「publish 前にクリーンビルド」と読み替える）。該当しないものは理由一言でスキップ。
- **アプリ vs ライブラリの区別**: 「実行するもの（アプリ）」は版・入力を固定して**再現**を狙い、「配布するもの（ライブラリ）」は**互換範囲**を広く宣言する。両者で正解が逆になる項目がある（R-1 のランタイム版、R-3 のベースイメージ＝アプリは固定／ライブラリは CI マトリクスで複数版を試す）。
- **最優先の一原則**: 迷ったら **V-1（クリーン環境でビルド）＋ V-2（警告を信号として拾う）**。この2つが回っていれば、以下の多くは事前に露見する。

## R. ランタイム再現性（Runtime Reproducibility）

- **R-1 ランタイム版のピン留め（Version Pinning）** ★★★ — デプロイするアプリは実行ランタイムをメジャー固定する（例: Node は `engines: {"node": "22.x"}`、または `.nvmrc` / `.node-version` / Volta）。**開いた範囲（`>=22`）はプラットフォーム任せの自動アップグレードを招く**。
  - ⚖️ **アプリとライブラリで逆**: ライブラリの `engines` は「最小サポート版の宣言」なので `>=` が正しい。アプリの `engines` は「実際に動かす版」なので固定が正しい。
  - 🔶 トレードオフ: 固定するとメジャー更新が手動になる（放置で EOL リスク）。→ **メジャー固定（`22.x`）に留め、exact 固定（`22.22.3`）はしない**。更新は意図的に、dev / CI と同時に上げる。
- **R-2 dev / CI / prod パリティ（Dev/Prod Parity）** ★★ — 開発（devcontainer）・CI・デプロイ先のランタイム版を、R-1 で固定した版に揃える。ズレると「ローカルで動くが本番で違う」やエンジン不一致警告が出る。
  - 🔶 トレードオフ: 版を同期し続ける保守コスト。→ 固定の出典を1つ（`engines` か `.nvmrc`）に決め、他はそれを参照する運用にして二重管理を避ける。
- **R-3 コンテナ／ベースイメージのピン留め（Base Image Pinning）** ★★ — コンテナで動かす場合、DevContainer / Dockerfile のベースイメージを浮動タグ（`:latest` や `node:22`）でなく意図した版に固定する。R-1 が Node 実行版を固定しても、ベースイメージが浮動だと OS ライブラリ・システム依存・同梱ツールがビルドのたびに静かにドリフトする。**特にこのプロジェクト群のように DevContainer で dev/CI/prod を揃える構成では要**（power0 が生成する DevContainer も対象）。
  - ⚖️ **アプリとライブラリで逆**（R-1 と同型）: アプリは動かす版を固定。ライブラリは固定より CI マトリクスで複数ベースを試す方が価値が高い。
  - 🔶 トレードオフ: 固定すると CVE パッチが自動で乗らない／digest 固定（`@sha256:…`）は再現性最大だが保守が重い。→ **メジャー・ディストロ固定（例: `node:22-bookworm`）を既定とし、digest 固定は重要イメージだけ**。更新は R-1・R-2 と同時に意図的に上げる。

## P. 依存・パッケージマネージャ（Dependencies & Package Manager）

- **P-1 ビルドスクリプト承認の明示管理（Explicit Build-Script Allowlist）** ★★★ — 依存の install スクリプト（postinstall 等）の扱いを明示する。pnpm 10 は**既定でブロック**し許可制（`onlyBuiltDependencies` / `approve-builds`）、npm / yarn は既定で実行するが `ignore-scripts` 等で制御できる。ビルドが必要なネイティブ依存は、**承認対象を設定ファイルに明記**して CI でも再現させる。
  - 🔶 **両刃（要ニュアンス）**: これは**サプライチェーン・セキュリティとの綱引き**。PM が閉じた「任意コード実行の面」を、承認によって再び開く行為である。したがって——
    - **無条件承認（対話で全部 yes、一括許可）は禁止**。
    - **素性が分かり、実際にビルドが要るパッケージだけ**を個別に列挙する。
    - 「承認リストに入れた ＝ 安全」ではない。**何を通したかがレビュー対象**である旨を残す。
  - この判断は `ai-security-guardrails.md`（依存の最小化・信頼できるものに限る）と地続き。迷ったら人間に確認する。
- **P-2 lockfile 固定と決定的インストール（Lockfile + Frozen Install）** ★★★ — lockfile をコミットし、CI / デプロイは**厳密モード**で入れる（`pnpm install --frozen-lockfile` / `npm ci`）。lockfile と `package.json` の乖離を早期に検出する。
  - 📎 重複回避: 「依存を lockfile で固定」の原則自体は `ai-security-guardrails.md` P1 が出典。本項は**二重管理せず**、「install / CI では frozen で入れる」という**運用面**だけを足す位置づけ。
  - 🔶 トレードオフ: lockfile が古いと build が落ちる（それが目的だが、更新忘れで詰まる）。→ 依存更新時は lockfile 更新を同一 PR に含める。
- **P-3 単一パッケージマネージャ（Single Package Manager）** ★★ — 1リポジトリ1 PM。lockfile の混在（`package-lock.json` と `pnpm-lock.yaml` が両方ある等）を禁止し、`packageManager` フィールド + corepack で版を固定する。トレードオフはほぼ無し（corepack 初回 DL 待ち程度）。

## T. フレームワーク・ツール設定の健全性（Tooling Config Health）

- **T-1 統合が"実効"であることの確認（Effective Tooling Integration）** ★★★ — Lint・型チェック・フォーマッタ等が、**設定されているだけでなく実際に効いている**ことを確認する。特に:
  - フレームワークのプラグインが検出・ロードされているか（例: Next.js の ESLint プラグイン検出）。
  - flat config 等で、**対象ファイルが実際にルール適用範囲に入っているか**（`files` / `ignores` の取りこぼし）。
  - **ツールが探索・参照する設定ファイル自体を、誤って `ignores` に入れて無効化していないか**。
  - 🔶 トレードオフ: ほぼ無し（純粋に upside）。副作用として設定ファイルも lint 対象になりうるが、scoping で解決できる。
- **T-2 サイレントな無効化の明示化（No Silent Suppression）** ★★★ — 安全網を静かに切る設定に注意する: `eslint.ignoreDuringBuilds`、`typescript.ignoreBuildErrors`、広すぎる `ignores`、乱発された `// eslint-disable` / `@ts-ignore`、CI の `continue-on-error` 等。
  - 🔶 **両刃（要ニュアンス）**: 「無効化を一切禁止」は現実に破綻する（急ぎのデプロイで一時的に型エラーを ignore する等は正当な判断）。→ ルールは**ゼロトレランスではなく**、**「無効化するなら "明示 ＋ 理由 ＋（可能なら）解除期限 / 追跡"」**。判断不能・恒久的に握り潰す形を避ける。
- **T-3 設定を現行サポート形式・メジャー整合に保つ（Keep Config Current）** ★★ — ツールのメジャー版と設定形式を一致させる（例: ESLint 9 なら flat config）。放置すると deprecation 警告 → ある日ビルドが動かなくなる。
  - 🔶 トレードオフ: 移行コスト。→ ツールのメジャー更新時にセットで設定移行する。

## V. ビルド・デプロイ検証の規律（Build/Deploy Verification Discipline）

- **V-1 クリーン環境でのビルド（Clean-Environment Build）** ★★★ — デプロイ前に、**まっさらな状態**でデプロイと同じビルドを通す（fresh clone 相当 / clean install / 本番と同じ `build` コマンド）。**開発サーバ（`dev`）はビルド時チェック（lint・型・プラグイン検出・静的解析）を走らせない**ため、`dev` だけでは見えない問題が多い。
  - 🔶 トレードオフ: 時間 / CI 分を消費。→ だが「本番で初めて分かる」を潰す費用対効果は最大。CI に1本用意すれば人手はかからない。
- **V-2 警告を"信号"として扱う（Warnings as Signal）** ★★★ — build / install / lint の**非致命の警告（exit 0 でも出るもの）を放置しない**。「落ちないこと（green）」だけを合格条件にすると、警告は永遠にすり抜ける。検出した警告は**対処するか、既知・許容として明示的に記録**する。
  - 🔶 **両刃（要ニュアンス）**: `--max-warnings 0` 的なゼロトレランスは、**自分では修正できない第三者ライブラリの警告**まで拾って CI を赤にし、ノイズで麻痺させる。→ 正しくは**「新規の警告を検知して triage する／既知の許容は明示リスト化する」**。一律ゼロ必須にはしない。
  - 📎 このプロジェクト群での位置づけ: 既存の検証ゲート（power6-verify・direct-implement・DoD）は「全 green」を条件にしており、**warning を信号として拾う段が無い**。本項はその穴を埋めるための語彙。
- **V-3 ビルド入力の再現性（Reproducible Build Inputs）** ★★ — ビルド時に必要な環境変数・設定を**宣言**し（`.env.example` / beam の `prep.md`）、マシン固有の状態に暗黙依存しない。
  - 📎 重複回避: シークレットの**値**の扱い（直書き禁止・Secret Manager 等）は `ai-security-guardrails.md` P0 の管轄。本項は**値を扱わず「何が必要かの宣言の所在」だけ**を対象にする。
- **V-4 生成物を版管理に入れない（No Committed Build Artifacts）** ★★ — ビルド生成物・キャッシュ・依存ディレクトリ（`dist/`・`.next/`・`build/`・`node_modules/`・カバレッジ出力等）は `.gitignore` に入れ、コミットしない。版管理に載せるとソースと生成物が乖離し、古い成果物の混入・無用な差分・コンフリクト・リポジトリ肥大を招く。差分に生成物が現れたら疑う。
  - 🔶 例外: 生成物を直接配信する構成や、生成が高コストで意図的にキャッシュする場合は例外。その場合も**「なぜコミットするか」を明示**し、生成コマンドから再生成できる状態を保つ。
  - 📎 重複回避: 秘匿すべき生成物（`.env` 等）の非コミットは `ai-security-guardrails.md` P0 の管轄。本項は**機密でない生成物のノイズ**だけを対象にする。

## 収録しない／参照に留めるもの（基準ドリフト防止）

二重管理は基準がずれる元。以下は**出典を1つに保ち、本ファイルからは参照だけ**する（`code-review` SKILL.md の「チェックリストを二重管理しない」運用に倣う）:

- **シークレット管理・ログの秘匿・インジェクション対策** → `ai-security-guardrails.md`（P0 / P1）。
- **依存脆弱性スキャン・自動アップデートの人間承認** → `ai-security-guardrails.md`「参考」節。
- **コード設計（凝集・結合・命名・抽象化）** → `coding-principles.md`（A〜E）。

（P-2 の lockfile 固定・V-3 のシークレットは、原則の出典を上記に置き、本ファイルは "運用・宣言面" だけを足すことで重複を最小化している。）

| R-3 | コンテナ／ベースイメージのピン留め | ★★ | 🔶 |
| P-1 | ビルドスクリプト承認の明示管理 | ★★★ | 🔶 |
| P-2 | lockfile 固定と決定的インストール | ★★★ | – |
| P-3 | 単一パッケージマネージャ | ★★ | – |

| T-2 | サイレント無効化の明示化 | ★★★ | 🔶 |
| T-3 | 設定を現行形式に保つ | ★★ | – |

★★★=再発しやすく実害大（優先）／★★=状況依存だが効く。🔶=「やり過ぎると逆効果」型。絶対規則ではなく、文脈で重み付けする判断語彙として使う。
