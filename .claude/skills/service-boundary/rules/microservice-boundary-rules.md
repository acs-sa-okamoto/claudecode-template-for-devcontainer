# マイクロサービス境界判定ルール

要件・設計段階で、機能をどのサービス境界（Bounded Context）に属させ、どこを分割すべきかを
判断するためのルール。**目的は「正しく分けること」ではなく「分けすぎないこと」**にある。

---

## 大原則（最初に読む）

### 1. 既定は「1つにまとめる」＝モジュラモノリス
- **迷ったら分割しない。** まず 1 つの境界（1 デプロイ）に置き、内部を**論理的なモジュール／コンテキスト**として分ける。
- 「分割*できる*とき」ではなく「**分割しないと無理が出る**とき」に分ける。後述ルールの証拠が**複数**揃って初めて分割を検討する。

### 2. 論理境界と物理境界を分ける（最重要の区別）
- **論理境界**：1 リポジトリ／1 デプロイの中の module・package・Bounded Context。**まずこれを引く。**
- **物理境界**：別リポジトリ・別デプロイ・別データストアの独立サービス。**後述「物理分離のバー」を越えたときだけ。**
- 物理分離して初めて「マイクロサービス」。引いた論理境界のうち将来バーを越えそうなものは
  **「将来の独立サービス候補」**として記録するに留める（＝今は切らない）。

### 3. 物理分離の対価（割るほど増える）
- ネットワーク往復・レイテンシ、部分障害、結果整合性、分散トランザクションの困難、デプロイ／監視／運用の多重化。
- **個人・小規模開発では「運用負荷の多重化」が分割可否の主軸。** チーム分割（Conway）の論理は弱いので、運用コストで代替して判断する。

---

## Rule 1: 同じ業務成果を生み出す機能群は同じ境界候補

利用者から見て同じ成果・目的を達成する機能は、原則として同じ境界にまとめる。

良い例（注文管理）：注文作成／変更／キャンセル／状態確認 → すべて「注文を管理する」業務成果 → `Order Context`。

悪い例：`CreateOrderService` / `CancelOrderService` / `UpdateOrderService` のように**機能単位で細切れ**にする。
サービス間通信が増え、責務も不明瞭になる。

---

## Rule 2: 異なるアクターが主に利用する機能群は分離候補

アクター（利用者）が異なる機能群は、異なる業務関心を持つ可能性が高い。

良い例（EC）：顧客向け（商品検索／カート／注文）＝ `Customer Context` ／ 店舗運営者向け（商品登録／在庫／売上分析）＝ `Merchant Context`。

**注意：アクターが違うだけでは割らない。** 同じ業務責務なら同一境界でよい
（顧客向け注文確認・管理者向け注文管理 → どちらも `Order Context`）。

---

## Rule 3: 独立して価値提供できる業務能力はサービス候補

その機能群だけで独立した業務価値を提供できるなら、（将来）独立できる可能性が高い。

良い例：決済（支払い／返金／決済履歴）＝ `Payment Context`、通知（Email／SMS／Push）＝ `Notification Context`。
通知のように**他から利用される共通基盤**になりやすいものは特に境界として明確。

悪い例：`Coupon Validation Service`（クーポン判定のみ）。単独価値が弱く、注文側に含めた方が自然。

---

## Rule 4: 常に同時変更が必要な機能群は同一境界を優先

仕様変更時に**必ず一緒に修正される**機能は、同じ境界に属する可能性が高い（変更理由の共有）。

良い例：「法人注文は承認フローを追加」という変更が、注文作成／状態管理／履歴を同時に触る → 同一 `Order Context`。

分離が妥当な例：注文の変更があっても決済は変更不要なことが多い → 変更理由が独立 → 別境界候補。

悪い例：`Order` / `Payment` / `Shipping` が**すべての仕様変更で 3 つ同時修正**になる構成。
実質的に強結合であり、マイクロサービスのメリットを失う。

---

## Rule 5: データ所有権・整合性境界を割らない（最重要）

- **1 境界 = 自分のデータを所有**。他境界のテーブルを直接読み書きしない（API／イベント経由にする）。
- **強整合トランザクション**（同一トランザクションでのコミットが業務上必須な範囲）は**同一境界に置く**。
  跨ぐと分散トランザクションになり、ほぼ常に過剰。
- 例：「注文確定」と「在庫引当」が必ず同時に整合すべきなら同一境界。事後の**結果整合**で足りるなら分離可。

> 「割れそう」に見えても、強整合の越境が 1 つでもあれば分割の費用対効果は急落する。Rule 5 は分割への最大のブレーキ。

---

## Rule 6: BFF（プレゼンテーション集約）はドメイン境界とは別レイヤー

BFF は Rule 1〜5 の**ドメイン境界とは層が違う**。クライアント向けの**集約・整形**であり、業務ロジックの所有者ではない。

設置を検討する条件（複数該当で検討）：
- 3 つ以上のサービス／コンテキストを集約する
- アプリ側で複数 API を叩いて初めて 1 画面が成り立つ
- フロント用にデータの整形が必要
- クライアント（Web／モバイル等）により同一データの出し分けが必要

> 注意：BFF にドメインロジックを溜めない（肥大化アンチパターン）。BFF は薄く保つ。

---

## 物理分離のバー（別デプロイ／別リポにするか）

論理境界のうち、**次が複数同時に成り立つ**ものだけ物理分離を検討する：

1. 独立した業務価値がある（Rule 3）
2. 変更理由が独立している（Rule 4）— 他境界と同時変更されない
3. データを独立所有でき、**強整合の越境がない**（Rule 5）
4. スケール特性・可用性要件・技術スタックが大きく異なる、または運用上どうしても分けたい明確な理由がある

→ 上記が **1〜2 個なら論理境界どまり**（モジュール分割に留める）。**将来の独立サービス候補**として記録する。

---

## 判断優先順位

1. 業務成果は何か（Rule 1）
2. 誰が使うか（Rule 2）
3. 独立した価値があるか（Rule 3）
4. 変更理由は独立しているか（Rule 4）
5. データ所有・整合性境界はどこか（Rule 5）
6. BFF は必要か（Rule 6）
7. **物理分離のバーを越えるか**（越えなければ論理境界どまり）

---

## 出力フォーマット（この順で）

1. **機能棚卸し**：`機能 / 主アクター / 変更理由 / 扱うデータ` の表
2. **推奨構成**：境界候補（Bounded Context）ごとに `責務 / 所有データ / 主アクター / 結合度（同一・疎結合・別製品級）`
3. **境界間の連携**：呼び出し方向、整合方式（同期呼び出し／イベント・結果整合）
4. **BFF の要否**と理由
5. **物理 or 論理**：各境界が「物理分離候補」か「論理境界どまり」か（既定は論理）
6. **将来の独立サービス候補**：今は切らないが、いずれ抽出しうる境界と、その引き金（バーを越える条件）
7. **却下した分割候補と理由**：過分割を避けた判断の記録

> 個人・小規模なら、最終推奨は多くの場合「**1 デプロイ＋内部モジュール境界＋将来候補リスト**」になる。
> それが**正常**であり、いきなり複数サービスに割るのは過剰のサイン。
