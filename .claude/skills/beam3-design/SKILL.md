PRD・タスクノート・要件定義書を参照しながら技術設計を実施し、技術仕様を明確化します。各項目に信頼性レベル（🔵🟡🔴）を付与して設計文書を作成します。

# context

- 出力ディレクトリ: `docs/spec/{要件名}/design`
- 要件名: `{要件名}` （step1 で確定）
- PRDファイル: `docs/spec/{要件名}/product-requirements.md`
- タスクノート: `docs/spec/{要件名}/note.md`
- 要件定義書: `docs/spec/{要件名}/requirements.md`
- 作業規模: `{work_scope}` （引数。未指定の場合は `"フル機能開発"` をデフォルトとする）
- 信頼性評価: `[]`

# 変数表記の凡例

- `{要件名}` は step1 で確定する変数。実際のファイルパス生成時には具体値に置換する。
- `{work_scope}` は引数（"フル機能開発" / "軽量開発" / "カスタム" のいずれか）。

## step1: 開発コンテキストの準備

- **要件名の確定**
  - Bash で `pwd` を実行し、basename をプロジェクトルートディレクトリ名として取得する
  - 取得したディレクトリ名を `{要件名}` として確定する

- **専用ルールの読み込み**
  - スキルディレクトリ内の `rules/rules.md` を読み込む

- **タスクノートの読み込み**
  - `docs/spec/{要件名}/note.md` を読み込む
  - ノートには技術スタック、開発ルール、関連実装、設計文書、注意事項が含まれる
  - **存在しない場合**: beam1-tasknote を先に実行する必要がある旨を警告し、AskUserQuestion で継続するか確認する

- **PRDファイルの読み込み**
  - `docs/spec/{要件名}/product-requirements.md` を読み込む
  - PRDには以下が含まれることを期待：
    - プロダクトビジョン
    - ターゲットユーザー
    - 主要機能
    - ビジネス要件
    - 成功指標

- **要件定義書の読み込み**
  - `docs/spec/{要件名}/requirements.md` を読み込む
  - 要件定義書には以下が含まれることを期待：
    - 機能要件（EARS記法）
    - 非機能要件
    - エッジケース
    - **「未解決事項（beam3-designで決定）」表**（区分 / 項目 / 信頼性 / 次フェーズでの取扱い）— beam2 が信頼性 🔴/🟡 で残した技術選定・アーキ・データ・設定等の決め事
  - **重要**: 「未解決事項（beam3-designで決定）」表が存在する場合は、その**全項目を抽出**して保持する。これらは本フェーズで確定すべき宿題であり、step3 のヒアリング・step4 の設計で1件ずつ決着させる（後述「未解決事項の確定」）。

- **関連文書の読み込み（存在する場合のみ）**
  - `docs/spec/{要件名}/user-stories.md`
  - `docs/spec/{要件名}/acceptance-criteria.md`
  - `docs/spec/{要件名}/interview-record.md`
  - `docs/spec/{要件名}/prep.md`

- **追加ルールの読み込み（存在する場合のみ）**
  - `docs/rule/` ディレクトリ
  - `docs/rule/beam/` ディレクトリ
  - `docs/rule/beam/design/` ディレクトリ

- **プロジェクト基本情報の収集**
  - `CLAUDE.md` の内容を読み込む（プロジェクト概要・技術スタック・制約）
  - プロジェクト構造（ディレクトリ構成）を把握

- **既存設計文書・実装の調査**
  - `docs/spec/{要件名}/design/` 配下に既存ファイルがある場合は一覧確認
  - **安全装置**: 該当ファイルが20件を超えた場合はファイル名一覧を表示し、AskUserQuestion で読み込み対象を絞る

- **スコープ選定の確認（scope-options.md）**: `docs/spec/{要件名}/scope-options.md` の**選定記録が要望案以外**で、再整列チェックに design が未完了で残っている場合は**選択案モード**で動作する:
  - 既存 `design/` は**旧案（要望案）の産物**として扱い、流用前提にしない
  - `design-interview.md` の確定判断のうち**スコープ非依存のもの**（フレームワーク・言語選定等）だけをシードとして引き継ぐ（**再質問しない**）
  - 文書は選択案スコープ（再生成済みの requirements.md）を正として再生成する
  - 完了後、scope-options.md の再整列チェックの design を ✅ に更新する

- **外部データソースの実スキーマ確認（読む対象がある場合は必須）**

  > **原則**: アプリが**既存DB・外部API・既存ファイル等の外部データソースを読む**設計をする場合、
  > 理想化・推測したスキーマではなく、**実物の本当の形**（テーブル名の命名規則・列の型・ID の表現）を
  > 確認して設計契約（interfaces.ts / database-schema 等）に固定する。乖離は実装の致命的バグになる。

  - 実ソースが入手可能なら、実際にその中身（テーブル一覧・列・サンプル行）を確認して契約に反映する
  - 特に注意する点: 識別子の文字種（ハイフン等を含むか）、ID が数値か文字列か、列の有無・命名
  - **beam の task DB（`data/tasks.db`）を読むアプリの場合**は、beam4 の実スキーマを前提とする:
    - テーブル名 = **要件名（ケバブケース＝ハイフン入り。例 `task-bridge`）**。識別子はクォートして扱い、ハイフンを除外しない
    - `task_id` は **TEXT（例 `"TASK-0001"`）**。数値ではなく文字列として設計する
    - 主な列: `task_id, title, content, status, notion_sync_status, is_deleted, update_badge, created_at, updated_at`（ほか phase / story_point 等）

- **収集情報のサマリー作成**
  - 定義済み要件・未定義部分の特定
  - 技術制約・非機能要件の整理
  - ギャップ分析（要件 vs 既存実装 vs ユーザー期待）

- 読み込み完了後、context の内容（要件名、作業規模、PRDサマリー、ノートサマリー、要件定義書サマリー）をまとめてユーザに宣言する
- step2 を実行する

## step2: 作業規模の確認

- `{work_scope}` の値に応じて分岐：
  - `"フル機能開発"`: そのまま step3 に進む
  - `"軽量開発"`: そのまま step3 に進む
  - `"カスタム"`: 以下の AskUserQuestion を実施してから step3 に進む

- カスタム時の質問:
  ```
  AskUserQuestion({
    questions: [{
      question: "設計文書に含める項目を選択してください（複数選択可）",
      header: "含める項目",
      multiSelect: true,
      options: [
        { label: "型定義（interfaces.ts等）", description: "エンティティ・APIリクエスト/レスポンスの型定義を作成" },
        { label: "DBスキーマ", description: "テーブル定義・インデックス・リレーションシップを作成" },
        { label: "API仕様", description: "エンドポイント詳細・リクエスト/レスポンス例を作成" },
        { label: "詳細なシーケンス図", description: "主要機能ごとに詳細なシーケンス図を作成" }
      ]
    }]
  })
  ```
- 選択結果を `custom_items` として保持し、step3, step4 で参照する

## step3: 既存情報ベースの差分ヒアリング

作業規模に応じてヒアリング項目を調整。

**重要**: 以下の質問は例示。実際のプロジェクト状況に応じて AskUserQuestion ツールを使用して適切な質問を作成すること。

### 共通ルール

- すべての質問は AskUserQuestion ツールで実施する
- すべての質問を一度に投げず、文脈に応じて段階的に質問する
- ユーザーの回答を受けて、必要に応じて追加質問を行う
- 質問は具体的で、選択肢から選べる形式にする（自由記述は「その他」オプションで対応 — 自動付与される）

### フル機能開発の場合

**最優先: 未解決事項の確定**
step1 で抽出した requirements.md の「未解決事項（beam3-designで決定）」表の各項目を、**ヒアリングの最優先トピック**として扱う。各項目について、設計判断に必要な情報をユーザーに確認するか、設計者として妥当な選択肢を提示して合意を得る。

- 表の項目を1件ずつ取り上げ、選択肢を提示して AskUserQuestion で確認する（技術選定はメリット/デメリットを添える）
- ユーザーがこだわらない項目は「設計者の推奨で確定してよいか」を確認し、合意が取れたものは🔵に格上げする
- ここで確定した内容は step4 で各設計文書に反映し、design-interview.md に「未解決事項 → 確定結果」として記録する

例（技術選定の確認）:
```
AskUserQuestion({
  questions: [{
    question: "Webフレームワークの選定について。要件（軽量・localhost・個人利用）からは {推奨案} を推奨します。どうしますか？",
    header: "技術選定",
    multiSelect: false,
    options: [
      { label: "{推奨案}（推奨）", description: "{推奨理由}" },
      { label: "{代替案}", description: "{代替案の特徴}" },
      { label: "おまかせ", description: "設計者の推奨で確定してよい" }
    ]
  }]
})
```

その後、以下のカテゴリごとに、既存情報（要件定義、既存設計文書、実装）から特定した具体的な課題・不明点について質問する：

**既存アーキテクチャの妥当性確認**
- 既存のアーキテクチャパターンが要件に適合するか
- 技術スタック選択の妥当性
- 既存設計で実現困難・非効率な部分の代替案
- **サービス境界 / モジュール構成**: 機能群が複数の Bounded Context に分かれるかを確認する（step4 で `service-boundary` スキルが分析する。**既定はモジュラモノリス**＝1 デプロイ内のモジュール境界。物理的なサービス分割は「物理分離のバー」を越える明確な正当化があるときのみ）。利用者には「1 つにまとめる／内部モジュール分割／（例外的に）サービス分割」のどれを目指すか方針を確認する

例:
```
AskUserQuestion({
  questions: [{
    question: "現在のアーキテクチャは{具体的なパターン}ですが、{新要件}には{別のパターン}の方が適している可能性があります。変更を検討しますか？",
    header: "アーキテクチャ",
    multiSelect: false,
    options: [
      { label: "現行維持", description: "現在のアーキテクチャを維持" },
      { label: "変更検討", description: "新しいアーキテクチャパターンを検討" }
    ]
  }]
})
```

**未定義設計の詳細化**
- データモデルの詳細
- 状態管理方法
- 認証・認可方式
- エラーハンドリング戦略

**技術選択の確認**
- 使用するライブラリ・フレームワークの選択
- データベース種別・ORMの選択
- キャッシュ戦略
- 外部サービス連携方法

**パフォーマンス・スケーラビリティ要件**
- パフォーマンス要件の具体的な数値
- スケーラビリティの要件
- データ量・トラフィック予測

**セキュリティ・コンプライアンス要件**
- セキュリティ要件の詳細
- データ保護要件
- コンプライアンス要件

**優先順位・フェーズ分け**
複数の設計要素がある場合、優先順位を質問:
```
AskUserQuestion({
  questions: [{
    question: "以下の設計要素の優先順位を教えてください（複数選択可）",
    header: "優先順位",
    multiSelect: true,
    options: [ /* 実際の設計要素リストから動的に生成 */ ]
  }]
})
```

### 軽量開発の場合

**必須項目のみ確認** — 簡潔に質問する:
- **requirements.md の「未解決事項」表の項目（あれば最優先で確定）**
- 基本的なアーキテクチャ方針の確認
- 主要な技術選択の確認（3-5項目程度）
- 最低限のデータモデル確認
- 優先順位（Phase 1 のみ）

### カスタム開発の場合

step2 で選択された項目（`custom_items`）に関連するヒアリングのみ実施する。

### ヒアリング記録の作成

すべての質問と回答を記録する。各質問について以下を記録：
- 質問内容
- 質問日時
- カテゴリ（アーキテクチャ/データモデル/技術選択/パフォーマンス/セキュリティ）
- 質問の背景（なぜこの質問が必要だったか）
- ユーザーからの回答
- 信頼性への影響（この回答により信頼性レベルがどう変化したか）

ヒアリング結果のサマリー：
- 確認できた事項
- 設計方針の決定事項
- **未解決事項の確定結果**（requirements.md の「未解決事項」表の各項目について、何にどう決まったか。信頼性 🔴/🟡 → 🔵 への変化を記録）
- 残課題（このフェーズでも確定できなかった項目があれば明記）
- 信頼性レベル分布（ヒアリング前後の比較）

この記録は step4 で `design-interview.md` として出力する。

- step4 を実行する

## step4: 統合設計文書の作成

- 作業規模に応じた出力ファイルを選択：
  - `"フル機能開発"`: 全ファイルを作成（architecture, dataflow, design-interview, interfaces, database-schema, api-endpoints）
  - `"軽量開発"`: architecture.md と dataflow.md と design-interview.md のみ作成
  - `"カスタム"`: architecture.md と dataflow.md と design-interview.md は必ず作成し、`custom_items` で選択された項目を追加

- context の情報でテンプレートを埋めて、以下のファイルを Write ツールで保存する
  - 出力ディレクトリが存在しない場合は Bash の `mkdir -p docs/spec/{要件名}/design` で作成
- **重要**: すべてのファイルのすべての項目に信頼性レベル（🔵🟡🔴）を記載

### 出力ファイル

すべて `docs/spec/{要件名}/design/` 配下に出力する。

1. `docs/spec/{要件名}/design/architecture.md`: アーキテクチャ概要（**常時生成**）
   - `<architecture_template>` を使用
   - **サービス境界 / モジュール構成の決定**: `Skill(skill="service-boundary", args="{要件名}")` を実行し、その境界マップを「サービス境界 / モジュール構成」節に反映する。**既定はモジュラモノリス**（1 デプロイ内のモジュール境界）。物理分離は「物理分離のバー」を越えた境界のみ。論理境界は「ディレクトリ構造」節のモジュール構成として実体化する
   - `service-boundary` が **`別製品級`** と判定した境界があれば、それは 1 製品の内部分割ではなく**別 PRD／別リポジトリ（to-prd の製品分解）にすべきシグナル**。design-interview.md にその旨を記録し、ユーザーに伝える（本リポジトリのスコープから外すか確認）
   - 各設計決定に信頼性レベルと出典を記載

2. `docs/spec/{要件名}/design/dataflow.md`: データフロー図（**常時生成**）
   - `<dataflow_template>` を使用
   - 各フローに信頼性レベルと出典を記載

3. `docs/spec/{要件名}/design/design-interview.md`: ヒアリング記録（**常時生成**）
   - `<design_interview_template>` を使用
   - step3 の質問と回答を記録
   - 信頼性レベルの変化を記録

4. **フル機能開発の場合、またはカスタムで「型定義」が選択された場合**:
   - `docs/spec/{要件名}/design/interfaces.ts` （対象言語が TypeScript でない場合は適切な拡張子に変更。例: Python の場合は `interfaces.py`）
     - `<interfaces_template>` を使用
     - **インターフェース定義が不要なプロジェクトの場合は生成しない**
     - 既存の note.md や tech-stack.md の型定義パターンに合わせる
     - 各型定義に信頼性レベルと出典をコメントで記載

5. **フル機能開発の場合、またはカスタムで「DBスキーマ」が選択された場合**:
   - `docs/spec/{要件名}/design/database-schema.sql` （対応する DBMS の構文に合わせる。NoSQL の場合は `database-schema.md` でスキーマ定義）
     - `<database_schema_template>` を使用
     - **データベースが不要なプロジェクトの場合は生成しない**
     - 各テーブル定義に信頼性レベルと出典をコメントで記載

6. **フル機能開発の場合、またはカスタムで「API仕様」が選択された場合**:
   - `docs/spec/{要件名}/design/api-endpoints.md`: API仕様
     - **`<api_design_ref>`（`references/api-design.md`）を先に読む**——URL 命名（API-1〜3）・メソッドとステータスコード（API-4〜6）・レスポンス形式（API-7〜9）・ページネーション（API-10〜11）・バージョニング（API-12〜14）の判断基準。設計文書には**採った判断の ID を併記**する（例: 一覧はカーソル方式（API-10: 無限スクロールのため））
     - `<api_endpoints_template>` を使用
     - **API を持たないプロジェクト、または既存 API のみ利用する場合は生成しない**（その旨を一言述べる）
     - **既存 API がある場合はその流儀を優先**する（リファレンスより一貫性が上位。API-0 の原則）
     - 最後に `<api_design_ref>` の「リリース前チェックリスト」で自己点検する
     - 各エンドポイントに信頼性レベルと出典を記載

### 未解決事項の反映（必須）

step1 で抽出した requirements.md の「未解決事項」表の**各項目について、確定した設計判断を該当する設計文書に反映**する（例: Webフレームワーク選定 → architecture.md、テーブル分割方針 → database-schema.md/interfaces.ts、ポート/パス → architecture.md）。

- 確定内容と根拠は `design-interview.md` に「未解決事項 → 確定結果」として記録する
- このフェーズでも確定できなかった項目が残った場合は、その旨と理由を design-interview.md の「残課題」に明記する

### 品質判定

作成した設計文書について以下を評価する:
- 設計の完全性
- **未解決事項の解消率**（requirements.md の「未解決事項」表のうち、何件を確定できたか。未確定が残ればその件数と理由）
- 技術的実現可能性
- パフォーマンス・スケーラビリティ
- セキュリティ考慮
- 信頼性レベル（🔵🟡🔴の分布） — すべてのファイルを通じて集計

品質判定結果をユーザーに表示する（全ファイル統合の信頼性レベル分布を含む）。

- step5 を実行する

## step5: prep.md の更新（ユーザー準備タスクの同期）

beam2 が生成した `docs/spec/{要件名}/prep.md`（ユーザー準備タスク）を、**本フェーズで確定した設計に同期**させる。
準備タスク（API キー・アカウント・環境変数など）は技術選定の結果で変わるため、設計確定後のここで必ず見直す。
（セキュリティ・ガードレール P0「取得・設定が必要な API キー・トークン・環境変数は prep.md に列挙する。実装側で勝手にダミー値を埋めない」を成立させ続けるための同期点でもある）

### 5.1 設計から「人間の準備タスク」を抽出する

確定した設計文書（architecture / interfaces / database-schema / api-endpoints / design-interview）から、以下の観点で**人間が事前に行うべきタスク**を洗い出す：

- **外部サービス・API（選定結果）**: アカウント作成、API キー／トークンの取得、プラン・課金・権限の確認
- **環境変数**: interfaces.ts（EnvConfig 等）や architecture.md で定義した環境変数の取得・設定（`.env` への記入）
- **ローカル環境**: DB・ランタイム・CLI 等のインストールや初期化のうち、自動化（DIRECT タスク）にできず人間の操作が必要なもの

### 5.2 既存 prep.md と突合して更新する

- **prep.md が存在しない場合**: 5.1 の抽出結果が 1 件以上あるときのみ、beam2 の prep テンプレートと同じ構造（必須／推奨／確認事項＋サマリー）で新規作成する。0 件なら本ステップをスキップし、その旨を報告する。

既存項目との突合は **3 操作**で行う：

| 操作 | 条件 | 書き方 |
|---|---|---|
| **追加** | 設計で新たに必要になったタスク | 該当セクション（必須／推奨／確認事項）に追加し、タスク名の後ろに `🆕(beam3)` ＋ 信頼性レベル ＋ *出典（設計文書名）* を付す |
| **変更** | 内容（環境変数名・取得先・手順等）が設計で変わったタスク | 本文を更新し `✏️(beam3)` ＋ *出典* を付す。**チェック状態 `- [x]` は保持**する。ただし実質的にやり直しが必要な変更なら `- [ ]` に戻し、理由を 1 行注記する |
| **不要化** | 設計の結果、不要になったタスク | **削除しない**。`~~タスク名~~ ❌(beam3 で不要化: {理由})` の形で取り消し線を付けて残す（実施済みの作業履歴を消さないため） |

- beam2 の「確認事項」セクションのうち **beam3 で決着した項目**は、決定結果を 1 行で記入し、不要化（❌）扱いにする。
- **冪等性**: 再実行時、同名タスクを二重追加しない。既に `🆕(beam3)` 等のマークが付いた項目へ重ねてマークを付けない。

### 5.3 サマリーと変更履歴を更新する

- サマリー表（優先度×信頼性の件数）を再集計する（不要化 ❌ の項目は件数から除外する）。
- ファイル末尾の「変更履歴」セクションに 1 行追記する（セクションが無ければ作る）：
  `- {YYYY-MM-DD} beam3: 追加 {N} 件 / 変更 {M} 件 / 不要化 {K} 件`
- 変更が 1 件も無かった場合は prep.md を書き換えず、「prep.md: 変更なし（設計と整合済み）」として step6 で報告する。

- step6 を実行する

## step6: 完了報告とTODO更新

- TodoWrite ツールで TODO ステータスを更新する
  - 設計フェーズを「completed」にマーク
  - 次のフェーズ「タスク分割（beam4-tasks）」をTODOに追加
  - 品質判定結果をTODO内容に記録
  - TODO が存在しない場合は新規作成する

- 完了報告を表示：
  - 収集した既存設計情報のサマリー
  - step3 でのヒアリング結果と既存情報との差分
  - **未解決事項の確定結果**（requirements.md の「未解決事項」表 N 件のうち、確定 M 件／未確定 (N-M) 件。未確定が残ればその一覧）
  - **prep.md の更新サマリー**（step5 の結果: 追加／変更／不要化の件数。**新規の「必須」タスクがある場合は一覧で強調**し、実装フェーズ（beam4〜5）開始前に完了が必要な旨を伝える。変更なしなら「変更なし（設計と整合済み）」と報告）
  - 作成したファイルのパス一覧（実際に生成されたファイルのみ）
  - 各ファイルの信頼性レベル分布
  - 全体の信頼性レベル分布（すべてのファイルを通じた集計）
  - 既存設計からの変更点・追加点の件数
  - 各ファイル内のリンクが正しく設定されていることを確認
  - 既存実装との整合性確認を促すメッセージ

- 次のステップ表示: 「次の推奨ステップ: `beam4-tasks` でタスク分割を実施します。」

## step7: Git 連携（フェーズブランチへコミット＋スタックド PR）

beam3 が生成した設計文書一式（`design/*`）と、step5 で更新した `prep.md` を**フェーズブランチ `beam3-{要件名}`**（前フェーズ `beam2-{要件名}` の上に分岐）へコミットし、**スタックド PR を作成**する（PR にはこのフェーズの生成物のみが入る）。Git 処理は `beam-sync` スキルに委譲する（冪等・秘密情報はコミットしない）。

- `Skill(skill="beam-sync", args="{要件名} beam3")` を実行する
- `beam-sync` が前提未達（`gh` 未認証・git identity 未設定・非 git リポジトリ）を報告した場合は、その案内をユーザーに伝えて**フェーズ自体は完了とする**（Git 連携のみスキップ）
- 結果（ブランチ／コミット／**PR の URL**）の要約をユーザーに伝える
