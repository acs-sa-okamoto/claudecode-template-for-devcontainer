# API 設計リファレンス（設計時の判断語彙）

`api-endpoints.md`（設計契約）を書くときの判断基準。各項目に ID（API-1 等）を振る——設計文書・レビュー指摘では **ID か項目名で引用**すること。

## 0. 使い方（最優先）

- **beam3-design**: `api-endpoints.md` を生成するときの規約。**HTTP API を作らない設計（CLI・ライブラリ・バッチのみ）では不要**——その旨を一言述べてスキップする。
- **power3-design**: 既存 API に**エンドポイントを足す／契約を変える**ときに読む。ただし**既存システムの流儀が常に優先**する。既存が本書と違う書き方（例: 単数形リソース・独自エラー形式）で統一されているなら、**本書に合わせるのではなく既存に合わせる**（一貫性 > 教科書的正しさ）。逸脱の理由を change-plan に一言残す。
- **プロジェクト固有規約（CLAUDE.md・note.md・既存 API）が常に本書より優先**。適用しない判断も正当——黙って飛ばさず「なぜ不要か」を一言述べる。
- **API-0 一貫性が最優先（最重要）** — 本書のどの選択肢を採るかより、**プロジェクト内で1つに決めて揃っていること**の方が重要。既存 API があるなら**本書より既存の流儀に合わせる**。本書は「まだ決まっていないことを決める」ためにある。

## 1. リソースと URL

- **API-1 リソースは名詞・複数形・ケバブケース。URL に動詞を入れない** — 操作は HTTP メソッドが表す。
  - ⭕ `GET /api/v1/team-members` / `POST /api/v1/users`
  - ❌ `/api/v1/getUsers`（動詞）・`/api/v1/user`（単数形）・`/api/v1/team_members`（スネークケース）
- **API-2 CRUD に乗らない操作だけ、サブリソースとして動詞を許す** — 濫用しない。
  - `POST /api/v1/orders/:id/cancel` / `POST /api/v1/auth/login`
- **API-3 所有関係はネスト、絞り込みはクエリパラメータ** — 「その親に属するものだけ」ならネスト、「条件で絞る」ならクエリ。
  - ネスト: `GET /api/v1/users/:id/orders` ／ クエリ: `GET /api/v1/orders?status=active`
  - ネストは**1段まで**。2段以上（`/users/:id/orders/:oid/items`）は最下位リソースを独立させる。

## 2. メソッドとステータスコード

- **API-4 メソッドの意味論（安全性・冪等性）を守る** — GET で状態を変えない。リトライされうる操作は冪等に。

  | メソッド | 冪等 | 安全 | 用途 |
  |---|:--:|:--:|---|
  | GET | ○ | ○ | 取得 |
  | POST | × | × | 作成・アクション |
  | PUT | ○ | × | 完全置換 |
  | PATCH | △ | × | 部分更新（実装次第で冪等にできる） |
  | DELETE | ○ | × | 削除 |

- **API-5 意味はステータスコードで表す。200 に `success: false` を詰めない** — HTTP のセマンティクスを潰すと、クライアント・プロキシ・監視のすべてが誤動作する。

  | コード | 用途 |
  |---|---|
  | 200 / 201 / 204 | 取得・更新 ／ 作成（+ `Location`）／ 本文なし（DELETE 等） |
  | 400 / 401 / 403 / 404 | 不正な形式 ／ 未認証 ／ 認証済みだが権限なし ／ 存在しない |
  | 409 / 422 / 429 | 競合・重複 ／ 形式は正しいが意味的に不正 ／ レート制限超過 |
  | 500 / 502 / 503 | 予期しない障害 ／ 上流障害 ／ 一時的過負荷（+ `Retry-After`） |

  - **401 と 403 を混同しない**（誰か分からない vs 誰か分かるが許可がない）。
  - バリデーション失敗に 500 を返さない（400/422）。
- **API-6 作成は 201 ＋ `Location` ヘッダー** — 生成されたリソースの場所を返す。

## 3. レスポンス形式

- **API-7 成功・エラーの形を1つに固定し、混在させない** — エンベロープ（`{ "data": ... }`）を使うか、リソースを直接返すかは**どちらでもよい**。ただし**プロジェクト内で統一**する。エンドポイントごとに違うのが最悪。
- **API-8 エラーは機械可読なコード＋人間向けメッセージ＋フィールド単位の詳細** — クライアントが分岐できるよう、メッセージ文字列で判定させない。

  ```json
  {
    "error": {
      "code": "validation_error",
      "message": "Request validation failed",
      "details": [
        { "field": "email", "code": "invalid_format", "message": "Must be a valid email address" }
      ]
    }
  }
  ```

- **API-9 日時は ISO 8601（UTC）、ID は文字列として扱う** — 数値 ID でも JSON では文字列にしておくと桁あふれ・型揺れを避けられる。フィールドの命名規則（`snake_case` / `camelCase`）も**プロジェクトで1つに統一**する。

## 4. 一覧の扱い（ページネーション・フィルタ・ソート）

- **API-10 一覧を返すエンドポイントには必ずページネーションを入れる** — 「今は件数が少ないから」で無制限に返さない（後から破壊的変更になる）。

  | ユースケース | 方式 | 理由 |
  |---|---|---|
  | 管理画面・小規模（〜1万件） | **オフセット**（`?page=2&per_page=20`） | 実装が単純、ページ番号ジャンプ可 |
  | 無限スクロール・フィード・大規模 | **カーソル**（`?cursor=...&limit=20`） | 件数に依らず高速、同時挿入でもズレない |
  | 検索結果 | オフセット | 利用者がページ番号を期待する |

  - オフセットの弱点は**大きな OFFSET が遅い**ことと、**取得中の挿入で重複・欠落が起きる**こと。どちらかが問題になるならカーソルへ。
- **API-11 フィルタ・ソート・検索の記法を統一する** — 等値は `?status=active`、範囲は `?price[gte]=10`、ソートは `?sort=-created_at`（`-` で降順）、全文検索は `?q=...`。**どれを採るかより、全エンドポイントで同じ記法**であることが重要。

## 5. バージョニングと変更管理

- **API-12 `/v1` から始め、必要になるまで版を増やさない** — URL パス方式を既定とする（明示的・テストしやすい）。同時に活かす版は**現行＋1つ前まで**。
- **API-13 「破壊的変更」の定義を決めておく** — これを曖昧にすると版が無闇に増える。
  - **非破壊（版を上げない）**: レスポンスへの**フィールド追加**、**任意**クエリパラメータの追加、新エンドポイントの追加。
  - **破壊的（版を上げる）**: フィールドの削除・改名・型変更、URL 構造の変更、認証方式の変更、**必須**パラメータの追加。
  - ⚠️ クライアントが「知らないフィールドを無視する」実装でない場合、追加も破壊的になりうる。前提を契約に明記する。
- **API-14 廃止は予告 → `Sunset` ヘッダー → `410 Gone`** — 外部公開 API では十分な予告期間を置く。

## 収録しない／参照に留めるもの（基準ドリフト防止）

二重管理は基準がずれる元。以下は**出典を1つに保ち、本ファイルからは参照だけ**する:

- **認証・認可（IDOR/BOLA を含む）・入力検証・レートリミット・CORS・エラーからの内部情報漏洩** → `ai-security-guardrails.md`（P0 / P1）。API 設計時も**そちらが基準**。
- **そのエンドポイントがどのサービス/モジュールに属するか（境界の切り方・BFF の要否）** → `service-boundary` スキル（`rules/microservice-boundary-rules.md`）。
- **命名・可読性・責務分割などコードレベルの判断** → `coding-principles.md`（A〜E）。
- **契約を正として型/SDK を生成する思想** → `coding-principles.md` の **D-3（Contract-First）**。本書はその「契約の中身をどう決めるか」を担う。

## beam / power での位置づけ

- 生成物は `docs/spec/{要件名}/design/api-endpoints.md`（beam3）または既存契約の**拡張差分**（power3）。**この契約が実装の正**であり、実装が逸脱する場合は**契約側を更新して理由を記録**する（beam3/beam5・power3/power5 の既存ルール）。
- 外部データソース（既存 DB・他システム）に触れる API は、**推測でなく実物のスキーマを確認**して契約に固定する（「テスト全通過 ≠ 動く」の予防。beam3 の既存方針）。

## リリース前チェックリスト

新しいエンドポイントを設計文書に確定する前に:

- [ ] URL が命名規約に従う（名詞・複数形・ケバブケース・動詞なし）— API-1
- [ ] HTTP メソッドの意味論が正しい（GET が状態を変えない等）— API-4
- [ ] ステータスコードが意味を表す（200 に `success:false` を詰めていない）— API-5
- [ ] 作成が 201 ＋ `Location` — API-6
- [ ] 成功・エラーの形が**プロジェクト内で統一**されている — API-7
- [ ] エラーに機械可読な `code` とフィールド単位の `details` がある — API-8
- [ ] 命名規則・日時形式が既存エンドポイントと揃っている — API-9
- [ ] 一覧にページネーションがあり、方式の選択理由が言える — API-10
- [ ] フィルタ・ソートの記法が他と揃っている — API-11
- [ ] バージョニング方針と「破壊的変更」の定義が決まっている — API-12/13
- [ ] 認証・認可・レートリミットが定義されている（基準は `ai-security-guardrails.md`）
- [ ] 既存 API がある場合、**本書より既存の流儀を優先**した（逸脱があれば理由を記録）
