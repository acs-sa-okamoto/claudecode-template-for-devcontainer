あなたは、既存システムの仕様の文書を整理する担当です。完了した機能の文書を片付け、**「いまのシステムが何をするか・何をしないか」を 1 か所（現役の仕様）で読める状態**にします。

# 何のためにあるか

power は機能ごとに差分の文書を書き足すので、改修のたびに 1 機能あたり数十〜百本ほど文書が増える（試行したリポジトリでは 13 機能で約 1,040 本・12 万行）。しかも「今の仕様の全体」がどこにも無く、今の仕様を知るには最初の要件と全機能の差分と改定記録を重ねて読むしかない。power2 の矛盾チェックが重く、古い記述が混ざる原因になる。

完了した機能の文書は役割で分けられる:

| 区分 | 例 | 完了後 |
|---|---|---|
| **まとめる元** | `requirements.md`・`acceptance-criteria.md`・`product-requirements.md`（beam）、`feature-requirements.md`（power） | 現役の仕様（`docs/spec/current/`）へまとめてから片付ける |
| **運用を移す** | `prep.md` | まだ有効な運用の知識を `docs/operations.md` へ移してから片付ける |
| **作業用** | note・理解ブリーフ・変更計画・設計・TASK-*.md・overview・開発ごとの code-map・`docs/implements/` の全部 | 片付ける（工程間の受け渡しのための文書。中身は現役の仕様・地図帳・コードに反映済み） |
| **記録** | レビューの結果・conformance-report・回帰レポート | 片付ける（Git の履歴と PR に残る） |

**片付けても消えない。** Git の履歴に残り、`docs/spec/ARCHIVE.md` に書いた「取り出すコミット」から `git show` で取り出せる。

# 原則（最優先）

- **作業中の機能には触らない。** 片付けるのは、スクリプトが「完了」と判定し、ユーザーが選んだものだけ。
- **参照されているものは、そのままでは片付けない。** コード・テスト・現役の文書が参照しているファイルは、参照を直すか、残すかを決めてから片付ける（片付けた後にテストが落ちたり、案内が切れたりするため）。
- **要件の ID は変えない。** コードとテストのコメントが元の ID を参照している（試行したリポジトリでは約 3,100 か所）。現役の仕様では `FR-11（app-guide-onboarding）` のように出典の名前を添えて書く。
- **要件を黙って落とさない。** まとめる元で定義された ID は、現役の仕様に書くか、ARCHIVE.md の「まとめなかった ID」に理由を添えて書く。`check-current-spec.sh` が抜けを 0 にするまで先へ進まない。
- **推測で要件を足さない・変えない。** 判断できないものは 🔴 にして、ユーザーに確かめる。
- **AI は最終承認者ではない。** 現役の仕様は人がレビューしてから、片付けとコミットに進む。push と PR は確認してから行う。
- **シークレットの値を書かない・読まない。** `docs/operations.md` には環境変数の名前と置き場所だけを書く。`.env*` の値は読まない。

# 入出力

- 入力: 引数の名前（空なら完了した機能をすべて）、`docs/spec/*/`・`docs/tasks/*/`・`docs/implements/*/`・`docs/reviews/`、改定記録 `docs/revisions/`、地図帳 `docs/code-atlas/`（あれば）
- 出力:
  - `docs/spec/current/README.md`（入口）と `docs/spec/current/{領域}.md`（領域ごとの現役の仕様）、`docs/spec/current/texts/`（文面の正本。あれば）
  - `docs/spec/ARCHIVE.md`（片付けの記録）、`docs/operations.md`（運用の知識。移すものがあれば）
  - 片付け用のブランチ `chore/spec-archive-{YYYYMMDD}` のコミット（push と PR は確認してから）

## step0: 準備

### スクリプトの呼び出し方（以降すべての step で同じ）

スクリプトは**このスキルの置き場所から辿る**（作業ディレクトリや `$HOME` を基準にしない）。

```bash
B='<このスキルのベースディレクトリ>'   # Claude Code が「Base directory for this skill」で示す値をそのまま入れる
B="$(printf '%s' "$B" | tr '\134' '/')"                    # \ を / に揃える（\134 はバックスラッシュ）
if command -v wslpath >/dev/null 2>&1; then                # WSL の bash のときだけ変換する
  case "$B" in
    //wsl.localhost/*/*|//wsl[$]/*/*) B="/${B#//*/*/}" ;;   # \\wsl.localhost\<distro>\x → /x
    [A-Za-z]:/*) B="$(wslpath -u "$B")" ;;                  # C:\x → /mnt/c/x
  esac
fi
```

### ブランチ

- トランクを最新にする（`git fetch`。失敗しても手元のトランクで続け、その旨を伝える）。トランクは `origin/HEAD` → `origin/main` → `main` の順で決める。
- 未コミットの変更（`git status --porcelain`）を確かめる:
  - **無い** → トランクから `chore/spec-archive-{YYYYMMDD}` を切って移る（日付は `date +%Y%m%d`）。
  - **スキル更新の変更だけ**（変更がすべて `.claude/skills/`・`.claude/skills-catalog/`・`docs/rule/ai-security-guardrails.md` の下。直前に `/skills-update` をした場合）→ HEAD がトランクの先端と同じなら、そのまま `chore/spec-archive-{YYYYMMDD}` を切り、最初のコミットとして `chore: sync skills from template` でコミットしてから進む（片付けのコミットとは分ける）。HEAD がトランクの先端と違えば止まって尋ねる。
  - **それ以外の変更がある** → 止まり、未コミットの変更をどうするかを尋ねる（片付けのコミットに混ぜない）。
- すでに `chore/spec-archive-*` のブランチにいて、トランクとの差がスキル更新のコミットだけなら、そのブランチで続ける。
- 以降の作業はすべてこのブランチで行う。

## step1: 目録と、片付ける機能の決定

```bash
bash "$B/scripts/spec-inventory.sh" --all --list /tmp/spec-archive-list.tsv          # 引数の名前があれば --target 名前 を並べる
```

- 出力の 1（完了の判定）・2（区分ごとの本数）を要約して示す。判定の根拠は 3 通りで見ている: トランクに入っている／マージしていないブランチが無い（スタックド PR の積み直しで先端がずれていても、マージコミットとパッチの照合で判定する）／tasks.db に done でないタスクが無い（tasks.db があるときだけ）。
- **AskUserQuestion で片付ける機能を選んでもらう**（multiSelect。既定は「完了」のすべて。「作業中」は選択肢に出さない）。
- 「持ち主不明」のレビュー（名前から機能が分からないもの。beam の初期のレビューに多い）があれば、片付けに含めるかも尋ねる。
- 初めて片付けるリポジトリで機能が多いとき（目安: 5 機能以上）は、step4 のまとめ込みが重くなる（領域ごとにサブエージェント 1 本、1 本あたり 15〜30 万トークンの見込み 🟡）ことを添える。

## step2: 参照の確認と、対処の決定

目録の 3（参照されている候補）を、参照元の種類ごとに対処を決める。

| 参照元の種類 | 典型 | 対処 |
|---|---|---|
| コード・テスト・設定 | コードのコメントが文面の正本として参照（`文面の正本は docs/spec/…/public-pages-text.md`）／テストがファイルを読む | **文面の正本**: `docs/spec/current/texts/` へ `git mv` し、参照を書き換える。**テストが読む作業用のファイル**（開発ごとの code-map・回帰レポートなど）: テストの目的を読み、AskUserQuestion で「テストを直す / ファイルを残す」を選んでもらう。**経緯を指すコメント**（「設計契約: docs/spec/…/interfaces.ts」など）: 現役の仕様の該当 ID か、ARCHIVE.md の該当の行を指すように書き換える |
| 現役の文書 | README・CLAUDE.md・`docs/ui/`・`docs/rule/` | 現役の仕様（`docs/spec/current/`）か ARCHIVE.md を指すように書き換える |
| 地図帳 | 区画のページ（とくに文書の区画）が根拠として指している | 片付けと同じコミットで、該当の行を直す（文書の一覧なら現役の仕様と ARCHIVE.md に置き換える） |
| 片付けない機能の文書 | 作業中の機能が、完了した機能の文書を参照 | 直さない（その機能の作業で直す）。報告に挙げる |
| 改定記録・マイグレーション | 当時の記録・適用済みのマイグレーションのコメント | **直さない**（ARCHIVE.md から辿れる） |

- 対処の一覧を表で示し、**AskUserQuestion で「この方針で進める / 調整する / 中止」**を確認する。中止なら何も変えずに終わる。
- 旧版の全体の地図 `docs/code-map.md` からの参照は、そのファイル自体が片付けの対象（code-atlas への移行で消す）なら数えない。

## step3: 領域を決める

- **`docs/spec/current/README.md` が既にあるとき**: その「領域」の表を使い、今回まとめる ID を既存の領域へ振り分ける。どこにも当てはまらない要件がまとまってあるときだけ、新しい領域を提案する。
- **初めてのとき**: 領域（利用者から見た機能のまとまり）を 3〜10 個提案する。材料は、まとめる元の見出し・地図帳の `index.md`（区画と用語）・最初の PRD。各領域に「英名・扱うこと・入る ID の範囲（元の文書ごと）」を付ける。
- **AskUserQuestion で領域の案を承認してもらう。**

## step4: 現役の仕様へまとめる（B）

### 4-1. 領域のファイルを書く

- まとめる ID が少ないとき（目安: 合わせて 80 以下）は、メインが書く。多いときは、領域ごとに general-purpose のサブエージェントへ `references/consolidate-brief.md` の依頼文で任せる（並行は 4 本まで。サブエージェントは領域のファイルを直接書き、網羅チェックまで済ませて要約だけを返す）。
- 書式は `templates/current-domain-template.md`。決まり（依頼文と同じ）: ID は変えずに出典を添える／新しいものが勝つ（後の機能・改定記録の内容で書き、出典に上書きした機能を足す）／INT・REG・US・TC と作業のための制約は入れない／しないことを落とさない（理由と前提を添える）／出典はパスではなく名前／信頼性レベルを引き継ぐ。

### 4-2. メインが書くもの

- `docs/spec/current/README.md`（`templates/current-readme-template.md`）: このシステムについて（最初の PRD・要件から）・領域の表・ID の書き方・作業中の機能の一覧・確かめること（🔴 の項目）。
- `docs/spec/ARCHIVE.md`（`templates/archive-template.md`。無ければ作る）の「まとめなかった ID」: サブエージェントの報告と、メインの判断を `- ID（名前）: 理由` の形で書く（行の追加は step5）。
- `docs/operations.md`（`templates/operations-template.md`）: 各 `prep.md` のうち、**まだ有効な運用の知識**（環境変数の名前・外部サービスの設定・定期的な作業）だけを移す。一度だけの作業手順は移さない。シークレットの値は書かない。移すものが無ければ作らない。
- 文面の正本の移動（step2 で決めたもの）: `git mv` と参照の書き換え。

### 4-3. 機械の確認（両方とも、通るまで先へ進まない）

```bash
bash "$B/scripts/check-current-spec.sh" --target 名前1 --target 名前2 …     # 片付ける機能をすべて
bash "$B/scripts/find-stale-spec.sh" docs/spec/current                      # 今は無いコードを書いている節
```

- 網羅チェック: **抜け 0・重複 0** にする。抜けは、現役の仕様に書くか、ARCHIVE.md の「まとめなかった ID」に理由を添えて書く。
- 古い記述: 出てきた節は今の動きに合わせて直す（名前が変わっただけなら新しいパスに）。要件そのものが変わっているなら、ここでは直さず 🔴 にして README の「確かめること」に載せ、報告で `/revise` を案内する。

### 4-4. 人のレビュー（承認ゲート）

- 領域ごとの要件の数・新しいものが勝った箇所の主なもの・まとめなかった ID・古い記述を直した箇所・確かめること（🔴）を要約して示す。
- **AskUserQuestion で「片付けに進む / 現役の仕様を直す / 中止」**を確認する。直すなら、指摘を受けて直し、4-3 からやり直す。中止なら変更を捨てる（`git switch -` でトランクに戻り、ブランチを消すかを尋ねる）。

## step5: 片付ける（A）

1. **取り出すコミットを記録する**: `BASE="$(git rev-parse HEAD)"`（まだコミットしていないので、トランクの先端。ここに元の文書が全部ある）。
2. `docs/spec/ARCHIVE.md` の「片付けた機能」に、機能ごとに 1 行足す（片付けた日・名前・種類・`BASE`・本数・まとめた先・PR は後で埋める）。持ち主不明のレビューを片付けたら、その節にも書く。
3. 片付けの一覧（`/tmp/spec-archive-list.tsv`）から、選んだ機能の行のパスを取り出し、step2 で「残す」にしたものと、`git mv` で移したものを除いて `git rm` する:
   ```bash
   awk -F'\t' -v keep="名前1 名前2 …" 'BEGIN{n=split(keep,a," "); for(i=1;i<=n;i++) k[a[i]]=1} ($1 in k){print $4}' /tmp/spec-archive-list.tsv \
     | while IFS= read -r p; do [ -e "$p" ] && printf '%s\n' "$p"; done > /tmp/spec-archive-rm.txt
   # 残すと決めたパスを /tmp/spec-archive-rm.txt から除いてから:
   xargs -d '\n' git rm -q -- < /tmp/spec-archive-rm.txt
   ```
4. step2 で決めた参照の書き換え（コード・テストのコメント、現役の文書、地図帳）を行う。
5. 残りが無いことを確かめる: 片付けた機能を `spec-inventory.sh --target` で見て、ファイルが 0 本であること。参照の確認で「直す」種類の参照が残っていないこと。

## step6: 確認とコミット

- **コードかテストを変えたとき**（コメントの参照の書き換え・テストが読むパスの変更）: プロジェクトの `CLAUDE.md` のコマンドで、テスト・型チェック・Lint を通す。落ちたら直す。
- **地図帳を直したとき**: code-atlas の `verify-atlas-evidence.sh` で、直したページの根拠を検証する（code-atlas のスキルの置き場所から辿る）。
- コミットする（`.env*` と `data/tasks.db` は含めない）:
  ```
  chore(spec): 完了した機能の仕様を現役の仕様にまとめ、作業用の文書を片付ける

  - まとめた機能: {名前の一覧}
  - 現役の仕様: docs/spec/current/（{領域数} 領域・要件 {件数}）
  - 片付けたファイル: {本数}（取り出し方は docs/spec/ARCHIVE.md）
  ```
- **push と PR は AskUserQuestion で確認してから**行う。PR の説明には、まとめた機能・領域ごとの要件の数・片付けた本数・確かめること・取り出し方（ARCHIVE.md）・レビューしてほしい点（現役の仕様の各領域）を書く。PR を作ったら、ARCHIVE.md の PR の列を埋めて追加のコミットを push する。
- マージは人が行う。

## step7: 完了報告

- まとめた機能と、片付けた本数（区分ごと）・残した本数とその理由
- 現役の仕様: 領域の一覧と要件の数、まとめなかった ID の数
- 確かめること（🔴）と、`/revise` が要りそうな箇所
- 参照の書き換えをした場所（コード・テスト・現役の文書・地図帳）と、テストの結果
- ブランチ名・コミット・PR（作ったなら）
- **次から**: 新しい機能が完了してマージされたら、次の power1 が片付けを提案する（単独で `/spec-archive` を呼んでもよい）

## ほかのスキルとの関係

- **power1-scope**: 最初に `spec-inventory.sh --brief` を実行し、「完了して、まだ片付けていない機能」があれば `/spec-archive` を案内する。
- **power2-understand**: 既存要件との矛盾チェックで、現役の仕様（`docs/spec/current/`。とくに「しないこと」）と、作業中の機能の `feature-requirements.md` を読む。片付けた機能の文書は読まない。
- **revise**: 完了済みの要件（現役の仕様）の変更は、現役の仕様を直し、影響はコード・テスト・地図帳から洗い出して、担い手（実装する機能）を決める。片付けた TASK や記録は読まない。
- **code-atlas**: 今の構造（どこに何のコードがあるか）は地図帳が持つ。現役の仕様は「何をするか・しないか」だけを持つ（役割を分ける）。
- **tasks.db** には触らない（Git で管理していない手元のデータベース。ダッシュボードには完了した機能の行が残る）。

## スクリプト

| スクリプト | 内容 |
|---|---|
| `scripts/spec-inventory.sh` | 機能ごとの完了の判定・文書の区分・参照の確認。`--list` で片付けの一覧、`--brief` で「完了して片付けていない名前」だけを出す。読み取りだけ。bash・git（sqlite3 があれば tasks.db も見る） |
| `scripts/check-current-spec.sh` | まとめる元で定義された ID が、現役の仕様か ARCHIVE.md の「まとめなかった ID」にあるかを調べる（抜け・重複・両方にあるもの）。`--rev` で片付けた後に履歴の元と照らせる |
| `scripts/find-stale-spec.sh` | 見出しの節ごとに、今の HEAD に無いコードのパスを書いているところを出す（古くなった記述の手がかり）。revise と power2 からも使う |
