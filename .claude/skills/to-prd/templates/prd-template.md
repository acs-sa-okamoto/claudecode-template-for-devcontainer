# PRD 出力テンプレート

このファイルは `to-prd` スキルがPRDファイルを生成する際に参照する書式・記法・見本の定義です。
後続の Claude Code が機械的に読み取れる構造化PRDを作るため、以下のルールを厳密に守ってください。

---

## 1. 記法ルール（必須）

### 1.1 ID付与ルール

各要件には以下の規則でIDを付ける。連番（ゼロパディング2桁）で一意に振る。

| 種類 | プレフィックス | 例 |
|------|--------------|-----|
| 機能要件（Functional Requirement） | FR- | FR-01, FR-02 |
| 非機能要件（Non-Functional Requirement） | NFR- | NFR-01, NFR-02 |
| ユーザーストーリー（User Story） | US- | US-01, US-02 |
| 受け入れ条件（Acceptance Criteria） | AC- | AC-01, AC-02 |

### 1.2 優先度ラベル（MoSCoW）

機能要件・ユーザーストーリー・非機能要件には必ず優先度ラベルを付ける:

- `[Must]` 必須。これがないとプロダクトとして成立しない
- `[Should]` 重要。あった方がよいが、なくても初期リリースは可能
- `[Could]` できれば。時間があれば
- `[Won't]` 今回はやらない（スコープ外と同義）

### 1.3 ユーザーストーリーの書式

```
**US-NN** [優先度] As a <誰が>, I want <何をしたい>, so that <なぜ／どんな価値>
  - 受け入れ条件: AC-XX, AC-YY
```

ユーザーストーリーには必ず関連する受け入れ条件のIDを紐付ける。

### 1.4 受け入れ条件は Given-When-Then 形式（必須）

散文で書かず、必ず以下の形式で書く:

```
**AC-NN**: <条件のタイトル>
- **Given** <前提条件>
- **When** <ユーザーの操作・イベント>
- **Then** <期待される結果>
```

### 1.5 機能要件の書式

```
**FR-NN** [優先度] <一文でできることを記述>
```

### 1.6 非機能要件は計測可能な数値で

「速い」「安全」「使いやすい」などの曖昧な表現は禁止。必ず計測可能な数値・基準を含める。数値が不明な場合はユーザーに聞き直す。

```
**NFR-NN** [優先度] <測定可能な定量条件>
```

## 2. 出力テンプレート

以下のテンプレートに従って `docs/spec/{要件名}/product-requirements.md` を生成してください。`[...]` の部分は実際の内容で置き換え、見本の書式・記法をそのまま踏襲してください。

````markdown
# プロダクト要求定義書

**要件名（Requirement Name）:** [kebab-case-name]
**作成日:** YYYY-MM-DD
**バージョン:** 1.0

---

## 1. プロダクトビジョンと目的

[なぜ作るのか、どんな未来を実現したいのかを2〜3文で簡潔に記述]

**見本:**
> 共働き夫婦が家計を共同で管理できるモバイルアプリ。月のカテゴリ別予算に対する超過をリアルタイム通知することで、月末に「使いすぎた」と気づく状況をなくす。二人で家計を見える化することを目的とする。

---

## 2. ターゲットユーザーと課題・ニーズ

### 主なユーザー
- **[ペルソナ名]**: [年代・属性・状況]
  - 抱えている課題: [...]
  - ニーズ: [...]

**見本:**
- **30代共働き夫婦**: 二人ともフルタイム勤務、スマホ操作は問題なし
  - 抱えている課題: 月末に予算超過に気づくが時すでに遅し
  - ニーズ: リアルタイムで二人とも家計を把握したい

---

## 3. 主要な機能一覧

|------|------|--------|

**見本:**

|------|------|--------|
| 支出記録 | 金額・カテゴリ・日付を手動入力 | Must |

| 月次グラフ | カテゴリ別の支出をグラフ表示 | Must |
| レシートOCR | カメラで撮影して金額を自動入力 | Should |
| 銀行口座連携 | API経由で取引を自動取得 | Could |

|------|--------|---------|

**見本:**
- **リリース期限:** 2026-11-30
- **予算:** 規定なし（副業開発のため工数優先）
- **法的・規制要件:** 個人情報保護法準拠、財務データの国内保存
- **その他制約:** エンジニア2名＋デザイナー1名の副業チーム

## 6. ユーザーストーリー

書式: `**US-NN** [優先度] As a <誰>, I want <何>, so that <価値> ／ 受け入れ条件: AC-XX`

**見本:**

- **US-01** [Must] As a 共働き夫婦の妻, I want 買い物のその場で支出を入力したい, so that 帰宅後に思い出す手間が省ける
  - 受け入れ条件: AC-01, AC-02
- **US-02** [Must] As a 共働き夫婦の夫, I want パートナーが入力した支出をリアルタイムに見たい, so that 家計の状況を共有できる
  - 受け入れ条件: AC-01
- **US-03** [Must] As a 家計担当者, I want 予算超過の前に警告を受けたい, so that 使いすぎを未然に防げる
  - 受け入れ条件: AC-03

---

## 7. 受け入れ条件

書式: Given-When-Then 形式（必須）

**見本:**

**AC-01**: 支出のリアルタイム共有
- **Given** 夫婦がペアリング済みでアプリにログインしている
- **When** 一方が「支出を記録」ボタンから金額・カテゴリを入力して保存する
- **Then** もう一方の画面に3秒以内に反映される

**AC-02**: 支出入力の所要操作数
- **Given** ホーム画面が表示されている
- **When** 「支出を記録」ボタンをタップする
- **Then** 2タップ以内で入力画面に遷移する

**AC-03**: 予算80%超過の通知
- **Given** カテゴリの月予算が10,000円に設定されている
- **When** 月内の支出合計が8,000円（予算の80%）に達する
- **Then** 夫婦両方のスマホにプッシュ通知が届く

---

## 8. 機能要件

書式: `**FR-NN** [優先度] <一文でできることを記述>`

**見本:**

- **FR-01** [Must] ユーザーはメールアドレスとパスワードでアカウント登録できる
- **FR-02** [Must] ユーザーは支出を金額・カテゴリ・日付・メモ付きで記録できる
- **FR-03** [Must] ユーザーは招待コードを生成しパートナーと共有できる
- **FR-04** [Must] ユーザーは招待コードを入力してパートナーアカウントと連携できる
- **FR-05** [Must] ユーザーは月単位でカテゴリごとの予算を設定できる
- **FR-06** [Must] システムは予算の80%・100%超過時に夫婦両方へプッシュ通知を送信する
- **FR-07** [Must] ユーザーは月次のカテゴリ別支出をグラフで確認できる
- **FR-08** [Should] ユーザーはレシート画像から金額を自動入力できる
- **FR-09** [Could] ユーザーは銀行口座と連携して取引を自動取り込みできる

---

## 9. 非機能要件

書式: `**NFR-NN** [優先度] <測定可能な定量条件>`

すべて数値で記述する。

**見本:**

- **NFR-01** [Must] 支出入力後、パートナーの画面に3秒以内で反映される
- **NFR-02** [Must] 月次稼働率99.5%以上を維持する
- **NFR-03** [Must] HTTPS（TLS 1.2以上）で通信する
- **NFR-04** [Must] パスワードはbcrypt（コスト10以上）でハッシュ化して保存する
- **NFR-05** [Must] アプリ起動時間は3秒以内
- **NFR-06** [Should] iOS 16以上、Android 12以上で動作する
- **NFR-07** [Should] オフライン時も入力可能、復帰後30秒以内に自動同期する

---

## 10. スコープ外

このPRDで明示的に「やらない」と決定した項目を列挙する。後続の開発タスクで実装してはいけないもの。

**見本:**

- 銀行口座・クレジットカードの自動連携（Phase 2 以降で検討）
- Webブラウザ版（モバイルアプリのみ対応）
- 収入管理機能（支出のみ対象）
- 多通貨対応（円のみ）
- 家族3人以上のグループ機能（夫婦2人のみ）
- 確定申告連携・税務機能

````
