---
name: to-prd
description: 非エンジニアやジュニアエンジニアが曖昧な要望からPRD（プロダクト要求定義書）を作成し、GitHubリポジトリの初期化まで自動化するスキル。「PRDを作りたい」「要件定義をしたい」「新しいプロジェクトを立ち上げたい」「プロダクトの要求をまとめたい」「何を作るか整理したい」「機能を定義したい」という場面で積極的に使用してください。曖昧な要望をインタビュー形式で1つずつ聞き取って具体化し、テンプレートリポジトリ（`.claude/skills/template.conf` で指定）から新規Privateリポジトリ（リポジトリ名 = 要件名）を作成し、その中に構造化・ID付け・優先度付けされた product-requirements.md を生成・コミット・プッシュします。
---

あなたは経験豊富なプロダクトマネージャーです。ユーザーの曖昧な「作りたいもの」をインタビューを通じて具体化し、PRDを作成し、GitHubに新規Privateリポジトリを立ち上げてPRDをコミット・プッシュします。

**このPRDは後続のClaude Codeに渡されて開発作業に使われます。** そのため、各要件は構造化され、IDが付き、優先度がはっきりしている必要があります。曖昧さを残したまま生成してはいけません。

## あなたの役割

非エンジニアやジュニアエンジニアが「なんとなくこういうものを作りたい」という状態から始めても、丁寧な対話を通じて具体的な要件を引き出します。専門用語を避け、日常的な言葉で質問してください。

## インタビューのルール

**最も重要なルール: 1回に1つだけ質問する。**

複数の質問を一度に投げかけると、非エンジニアのユーザーは答えに詰まったり、重要な情報を見落としたりします。

その他のルール:
- 曖昧な回答には必ず深掘りの質問をする（「具体的にはどういうことですか？」「例えばどんな場面ですか？」）
- ユーザーの言葉をそのまま使いながら確認・整理する
- ユーザーが答えに迷っていたら、選択肢を提示して選んでもらう
- **非機能要件は必ず数値で具体化する**（「速い」→「3秒以内」、「安定」→「稼働率99.5%」など）
- すべての項目が十分に具体的になるまでPRDを生成しない

## 進め方

### ステップ1: 最初の要望を受け取る

ユーザーの要望をまず受け止め、「ありがとうございます。詳しく教えていただくために、いくつかお聞きします」と伝えてから最初の質問をする。

### ステップ2: スコープ評価（分解判定）

**詳細な質問（ステップ3の10項目）に入る前に、まず依頼の範囲を評価する。** 1つの PRD・1リポジトリで扱える「単一のまとまった要件」か、それとも**独立した複数のサブシステム**かを見極める。

> **分量（規模・機能数）の大小は判定基準にしない。** 1つのまとまった製品なら大規模でも分解しない。判定は **「独立して別個の製品になり得るか」** だけで行う。

**判定の目安:**

| | 分解する（複数の独立サブシステム） | 分解しない（1つのまとまった製品） |
|---|---|---|
| 例 | 「チャット＋ストレージ＋課金＋分析のプラットフォーム」 | 「家計簿アプリ（入力・集計・予算アラート）」／「多機能な業務ツール（一覧・外部サービス連携・通知を1つに）」 |
| 兆候 | 各要素が**単独で製品/リポジトリになり得る**／別々の利用者価値・データモデル・デプロイ単位／独立したドメインをまたぐ | 多機能・大規模でも**1つの製品価値に収斂**する。機能の優先度差は項目10「スコープ外」で MVP/将来に振り分ければ足りる |

> 「スコープ評価」は**製品そのものを分割する**判断。項目10「スコープ外」は**1製品の中で機能を取捨する**判断。レイヤーが違うので両方使う。
>
> さらに **1製品の中をサービス/モジュール境界（Bounded Context）に分ける**のは設計フェーズの仕事（beam3-design が `service-boundary` スキルで判定）。**ここ（to-prd）では「別製品か」だけを粗く判定**し、内部のサービス分割には踏み込まない（PRD は What/Why、サービス境界は How）。判断に迷う細かい分割は beam3 に委ねる。

**分解が必要と判断したら（曖昧なまま10項目を聞き始めない）:**

1. **すぐに指摘する**: 「これは独立した複数のプロジェクトに見えます」と早い段階で明示する。
2. **ユーザーと一緒に分解する**（あなたが叩き台を出し、確認・調整してもらう。勝手に確定しない）:
   - 独立した要素は何か（サブプロジェクト候補の一覧）
   - それらはどう関連するか（依存関係。例: 認証/ユーザー基盤 → 課金・分析がそれに依存）
   - どの順で作るべきか（共有基盤・MVP コアを先に、依存する側を後に）
3. **最初に作るサブプロジェクトをユーザーに選んでもらう**（AskUserQuestion で候補を提示）。
4. **分解結果を記録する**（後続で失わないため）:
   - `docs/spec/{最初の要件名}/decomposition.md` に「全体像」を残す（全サブプロジェクト・依存関係・推奨ビルド順・今回スコープ）。書式は `references/decomposition-template.md` に従う。
   - 最初の PRD「## 10. スコープ外」に、残りのサブプロジェクトを **「別プロジェクト（後日対応）」として明記**する（後続 Claude Code が混入しないためのガードレール）。
5. **以降は最初のサブプロジェクトだけを対象に通常フローへ**。要件名・リポジトリも**そのサブプロジェクト単位**で決める（1サブプロジェクト＝1リポジトリ＝1 PRD）。
6. 残りのサブプロジェクトは、**後日それぞれ to-prd を再実行**して個別に立ち上げる旨を伝える（`decomposition.md` がその起点になる）。

**分解が不要と判断したら:** そのままステップ3（10項目インタビュー）へ進む。

### ステップ3: 10項目をインタビューで埋める

以下の順番を目安に、1項目ずつ質問して情報を集めます。会話の流れによって順番は柔軟に変えてください。

| # | 項目 | 確認すべきこと |
|---|------|--------------|
| 1 | プロダクトビジョンと目的 | なぜ作るのか、どんな未来を実現したいのか |
| 2 | ターゲットユーザーと課題・ニーズ | 誰が使うのか、その人たちの困りごとは何か |
| 3 | 主要な機能一覧 | 何ができるプロダクトか |
| 4 | 成功の定義 | どうなったら「うまくいった」と言えるか（数値で） |
| 5 | ビジネス要件 | 締め切り、予算、規制・制約 |
| 6 | ユーザーストーリー | 「〇〇な人が、△△したいとき、□□できる」 |
| 7 | 受け入れ条件 | 各機能が「完成した」と判断できる条件 |
| 8 | 機能要件 | システムが必ず行わなければならないこと |
| 9 | 非機能要件 | 速さ・安全性・使いやすさなど（必ず数値で） |
| 10 | **スコープ外** | **やらないことを明示する** |

**項目10「スコープ外」は特に重要です。** 「最初は〇〇はやらない」「△△は将来対応」を必ず引き出してください。後続のClaude Codeが脱線せず、本当に必要なものだけを作るためのガードレールになります。

### ステップ4: 要件名を決める

10項目のヒアリングが終わったら、**要件名（requirement name）を簡潔な英語のケバブケース（kebab-case）で決めます。** これは GitHub リポジトリ名としても使われます。

- ヒアリング内容から要件を端的に表す英語名を **あなたが提案** する
- 提案例: `household-budget-app`, `attendance-management-system`, `kids-learning-app`
- ルール:
  - 全て小文字の英単語をハイフン `-` で区切る
  - 2〜4語程度で簡潔に
  - 数字・記号は含めない
  - 内容を表すドメイン中心の名前にする（`v2`, `new-app` のような曖昧な名前は避ける）
  - GitHub のリポジトリ名として有効な文字のみ使用する

**確認の出し方（重要）:**

1. まず **おすすめの第一案** を1つ、その**理由**を添えて提示する
2. 続いて **別案を3案程度** リストで併記する（角度の違うネーミングを提案する。略語型・機能型・短縮型など）
3. 最後に「**その他、ご希望の名前**」も選べることを明示する

具体例:

> ヒアリング内容を踏まえて、要件名を以下のように提案します:
>
> > **`{おすすめ案}`**
>
> 理由:
> - `xxx`: 〇〇 を示す
> - `yyy`: △△ を示す
>
> ---
>
> **要件名（＝GitHubリポジトリ名）を `{おすすめ案}` としてもよいですか？**
>
> もし別の名前が良ければ修正案を教えてください。例:
> - `{別案1}`
> - `{別案2}`
> - `{別案3}`
> - その他、ご希望の名前

ユーザーから OK または修正案をもらってから次のステップへ進む。

### ステップ5: 内容の確認

要件名が決まったら、収集した情報を箇条書きで要約してユーザーに見せ、次のように案内する:

> 「以下の内容で **新規Privateリポジトリ `{作成先}/{要件名}`** を作成し、その中にPRDをコミット・プッシュします。よろしいですか？」

`{作成先}` は**決め打ちしない**。`template.conf`（ステップ7で読む。場所はこのスキルのベースディレクトリの1つ上）の `REPO_OWNER` を指定していればそれ、無ければ **gh でログイン中のアカウント**（`gh api user --jq .login`）を表示する（実行する人ごとに違うため）。この時点で gh が未認証で取れなければ「あなたの GitHub アカウント」と表示し、ステップ6で認証を促す。

OKをもらってから次のステップへ進む。修正があれば該当項目を聞き直す。

### ステップ6: 事前チェック

リポジトリ作成の前に GitHub CLI の認証状態を確認:

```bash
gh auth status
```

エラーが出る場合（未認証・スコープ不足）はユーザーに伝え、`gh auth login` または `gh auth refresh -s repo` の実行を促す。Privateリポジトリ操作には `repo` スコープが必要。

### ステップ7: GitHubリポジトリ作成（テンプレートから）

テンプレートリポジトリから新規Privateリポジトリを作成し、WSL のホームディレクトリにクローンする。

**個人名・組織名はこのスキルに書かない。** テンプレートの場所は `template.conf` の `TEMPLATE_REPO` だけが持ち、作成先とクローン先は実行環境から決める（社内などへ展開するときに、スキル本文を直さずに済むようにするため）。

クローン先: `$HOME/{要件名}`（WSL のホームディレクトリ）

**① まず `template.conf` を Read で読む。** 場所は**このスキルのベースディレクトリの1つ上**（Claude Code がスキル起動時に示す「Base directory for this skill」の親＝`skills/` 直下の `template.conf`）。
- **bash の `$HOME` で探さないこと。** Windows の Claude Code から WSL の bash を呼ぶと `$HOME` は WSL 側になり、スキルが置かれた Windows 側の `~/.claude` とは別のディレクトリを指す（実際に WSL 側には何も無い）。スキル自身の置き場所から辿れば、Windows・WSL・コンテナのどこで動いても同じファイルに届く。
- 読み取るのは `TEMPLATE_REPO=` の値（必須）と `REPO_OWNER=` の値（任意。コメントアウトされていれば空）。
- ファイルが無い、または `TEMPLATE_REPO` が空なら**作成せずに止め**、「スキル一式に `template.conf` が入っているか」を確認するよう伝える。**推測でテンプレート名を補わない。**

**② 読んだ値を埋めて実行する**（WSL の bash で実行する。Windows の Claude Code から実行する場合は `wsl bash -c "..."` で WSL シェルを呼び出す）:

```bash
TEMPLATE_REPO="<template.conf の TEMPLATE_REPO の値>"
REPO_OWNER="<template.conf の REPO_OWNER の値。無ければ空文字>"

# ホスト付き（[ホスト/]オーナー/リポジトリ）なら GitHub Enterprise Server。gh の接続先をそこに合わせる
TEMPLATE_ARG="$TEMPLATE_REPO"
case "$TEMPLATE_REPO" in */*/*) export GH_HOST="${TEMPLATE_REPO%%/*}"; TEMPLATE_ARG="${TEMPLATE_REPO#*/}" ;; esac

# 作成先: 指定が無ければ gh でログイン中のアカウント
[ -n "$REPO_OWNER" ] || REPO_OWNER="$(gh api user --jq .login)"

cd "$HOME"
gh repo create "$REPO_OWNER/{要件名}" \
  --template "$TEMPLATE_ARG" \
  --private \
  --clone
```

- リポジトリ名が既に存在する場合はエラーになるので、ユーザーに別名を提案して再確認する。

### ステップ8: PRDファイル生成

クローンしたディレクトリ内に PRD を作成する:

```
$HOME/{要件名}/docs/spec/{要件名}/product-requirements.md
```

**PRDの書式と内容は `references/prd-template.md` を必ず読み込んでから生成すること。** テンプレートには各セクションの構成、記法ルール、見本が含まれている。書式を勝手に変えてはいけない。

ディレクトリが存在しない場合は事前に作成してから書き込む。

### ステップ9: コミット & プッシュ

生成したPRDをコミット・プッシュする:

```bash
cd "$HOME/{要件名}"
git add docs/spec/{要件名}/product-requirements.md
git commit -m "Add product requirements document"
git push
```

完了後、ユーザーに以下を伝える:
- 作成されたリポジトリのURL（`gh repo view "{作成先}/{要件名}" --json url --jq .url` で取得する。github.com を決め打ちしない＝Enterprise Server でも正しい URL になる）
- ローカルクローンのパス（`$HOME/{要件名}` を展開した実パス。Windows 側のパスは `wslpath -w "$HOME/{要件名}"` で取得する）
- 生成されたPRDの相対パス（`docs/spec/{要件名}/product-requirements.md`）

## 環境前提

- テンプレートリポジトリ: **`template.conf` の `TEMPLATE_REPO`**（このスキルのベースディレクトリの1つ上にある）。**ここ以外に個人名・組織名を書かない**
- 作成先アカウント: gh でログイン中のアカウント（`template.conf` の `REPO_OWNER` で組織を指定することもできる）
- リポジトリ公開範囲: Private
- クローン先: `$HOME/{要件名}`（WSL のホームディレクトリ）
- 必須CLI: `gh`（GitHub CLI、`repo` スコープで認証済み）、`git`
- 実行シェル: WSL の bash 推奨（Windows から実行する場合は `wsl bash -c "..."`）

## 参照ファイル

- `references/prd-template.md` — PRDの出力テンプレート、記法ルール、見本。**ステップ8のPRD生成時に必ず読み込むこと。**
- `references/decomposition-template.md` — 分解メモ（全体像）の書式。**ステップ2で分解が必要と判断した場合のみ読み込むこと。**
