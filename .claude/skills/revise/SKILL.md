あなたは仕様改定の司令塔です。**確定済みの仕様・設計への変更**を受け付け、①影響を既存成果物から導出 → ②承認 → ③上流を更新 → ④下流を部分再生成 → ⑤影響タスクを再キュー化、までを一貫して行います。

これは beam / power **共通の横断スキル**です。パイプラインの一工程ではなく、**変更が起きたときの「再入口」**（開発途中でも完了後でも使える）。

# 原則（最優先）

- **導出、宣言にあらず（Derive, Don't Configure）**: 影響グラフを新しいメタデータで管理しない。**既存成果物**（カバレッジ行列・conformance-report・TASK の要件リンク・change-plan・code-map・`docs/implements/` 記録）から**毎回導出**する。
- **色＝「影響あり」という判断の確からしさ**（導出元で機械的に決まる。恣意で塗らない）:
  - 🔵 **確実** … 直接の ID リンク（行列・conformance・要件リンク・文書中の明示的 ID 参照）
  - 🟡 **妥当な推測** … ファイル・モジュール経由の間接リンク
  - 🔴 **推測** … 語彙・領域の類似のみ（既定では対処しない）
- **HITL**: 影響リストは必ず承認を得てから実行する（step3 で中止すれば dry-run として機能する）。
- **ID 安定**: 既存 ID の番号は変えない。削除は物理削除でなく**廃止マーク**。追加は末尾連番。
- **段階認識**: 存在する成果物だけで波及を計算する（実装前なら仕様＋設計のみ、実装後なら conformance・src まで）。
- **再実装・最終検証はしない**: revise は「整合の回復と作業の再キュー化」まで。コードの再実装は beam5/power5、再検証はゲート（beam5 step4 / power6）に委譲する。

# context

- 対象: `{対象名}`（beam の要件名 or power の機能名。step1 で解決）
- 変更内容: 引数（**意図先行**）または git diff（**事後**）
- 出力: 更新された仕様・設計・TASK・tasks.db ＋ 改定記録 `docs/revisions/{YYYY-MM-DD}-{slug}.md`

# 成果物マップ（beam / power 両対応）

| 整合対象 | beam プロジェクト | power 機能 |
|---|---|---|
| 仕様 | `docs/spec/{要件名}/requirements.md`（＋user-stories / acceptance-criteria） | `docs/spec/{機能名}/feature-requirements.md` |
| 設計 | `design/*`（architecture / interfaces / schema / api / dataflow） | `design/change-plan.md`（＋差分契約） |
| タスク | `docs/tasks/{要件名}/` ＋ tasks.db（テーブル=要件名） | `docs/tasks/{機能名}/` ＋ tasks.db（テーブル=機能名） |
| 実装への鎖 | conformance-report・`docs/implements/*/`・code-map | 同左 ＋ understanding-brief（INT/REG/CON） |
| 付随整合 | prep.md（外部サービス・環境変数に影響時） | understanding-brief の INT/REG/CON |
| ブランチ | beam-sync が作る改定用ブランチ `revise-{slug}-{要件名}`（トランク基点） | `feature/{機能名}`（チェックアウトして作業） |

## ★交差ケース: 「引き金」と「対象」が別系統になることがある

上の表は**対象（target）**で引いた表である。だが**引き金（trigger）**は別系統でありうる:

| 引き金 | 対象 | 例 | 扱い |
|---|---|---|---|
| power 機能の設計 | **beam プロジェクトの仕様** | 機能の FR が既存 REQ と矛盾し、REQ を改定する必要が出た | **成果物は beam 列**（requirements / AC / US / PRD / conformance）を使う。ただし**ブランチは power の `feature/{機能名}`**（step7 参照） |
| power 機能の実装 | その power 機能自身の仕様 | FR の数値を変える | 素直に power 列 |
| beam の実装 | beam の仕様 | 要件の文言・数値を直す | 素直に beam 列（beam-sync 経由） |

この交差は珍しくない。**既存システムへ機能を足すと、既存要件の前提が変わることがある**からである（例: 「Xを実装してはならない」という制約の根拠が、新しいデータや新しい前提のもとで成立しなくなる）。

**step1 の対象解決では、引き金と対象を分けて把握すること。** 「power で作業中だから対象も power 機能だ」と決めつけない — 直すべきは beam の requirements.md であることが多い。

## step1: 準備（対象の解決と段階認識）

- **入口モードの判定**: 引数に変更内容があれば**意図先行**。空なら**事後**（`git status --porcelain` / `git diff` で `docs/spec/**` の変更を検出し、変更された ID・セクションを抽出）。
- **対象の解決**: 引数の ID・文言を `docs/spec/*/` 横断で検索する。beam（`requirements.md`）と power（`feature-requirements.md`）が**同一リポジトリに併存しうる**ため、複数候補・該当なしの場合は AskUserQuestion で確認する。
  - **「引き金」と「対象」を分けて把握する**（→ 上の「★交差ケース」）。power 機能の作業中に見つかった矛盾でも、**直すべきファイルが beam の `requirements.md`** であることは珍しくない。
- **進捗段階の認識**: 存在する成果物（design/ → tasks/ → implements/ → conformance-report）から「どこまで進んでいるか」を判定し、波及計算の範囲を決める。
- **関連成果物の読込**: 仕様・overview のカバレッジ行列・conformance-report・TASK-*.md・change-plan・code-map・understanding-brief（存在するもの）。
- **引き金が power 機能なら**（対象が beam の仕様であっても）`feature/{機能名}` ブランチにいることを確認する（違えばチェックアウト）。**判定軸は「対象」ではなく「引き金」**——交差ケースでは対象が beam でも、改定は当該機能の前提条件なので同じ feature ブランチに載せる（step7 参照）。

## step2: 変更内容の確定

- **意図先行**: 変更後の文言をインタビューで確定する（1問ずつ。EARS / Given-When-Then の書式・数値化ルール・信頼性レベルは既存規約を維持）。
- **事後**: git diff から抽出した変更点を「この変更で合っていますか？」と確認する。
- **設計レベルの変更**（例:「ライブラリXをYに変える」）の場合: 上流の要件と矛盾しないかを先に確認する。矛盾するなら「それは要件レベルの変更です」と指摘し、要件改定として扱い直す。

## step3: 影響導出 → 承認ゲート（★核）

変更対象から下流へ、**既存成果物の鎖**をたどって影響リストを作る:

| 導出元 | 得られるエッジ | 色 |
|---|---|---|
| 仕様内の相互参照（AC↔REQ、US→AC） | 仕様の兄弟項目 | 🔵 |
| overview のカバレッジ行列 | REQ/FR → TASK | 🔵 |
| conformance-report の行 | REQ → 実装 `file:line`・テスト名 | 🔵 |
| TASK-*.md の要件リンク | REQ → TASK | 🔵 |
| 設計文書中の明示的 ID 参照 | REQ → design セクション | 🔵 |
| `docs/implements/` の変更ファイル記録・change-plan のファイル一覧 | TASK/設計 → 同一ファイルを触る他の TASK | 🟡 |
| code-map のモジュール責務・（power 複数機能間）他機能の brief/plan のファイル参照 | 機能横断の波及 | 🟡 |
| キーワード grep 等の発見的手がかり | 弱い関連 | 🔴 |

- リポジトリが大きい場合、grep 網羅は **Explore サブエージェント（Task）に委譲**して結果だけ受け取る。
- 影響リストを表で提示する（**色・成果物・根拠（導出元）・提案アクション**）。冒頭に凡例を必ず添える:
  > 凡例: 色は「**影響あり」という判断の確からしさ**（🔵確実=直接IDリンク / 🟡妥当な推測=ファイル・モジュール経由 / 🔴推測=語彙のみ・既定では対処しない）
- AskUserQuestion で確認: **「実行 / 範囲を調整（🟡の取捨・🔴の昇格）/ 中止」**。中止なら何も変更せず終了（dry-run）。

## step4: 上流の更新

- 仕様ファイルを改定する。**ID 安定則**を厳守:
  - 既存 ID は番号維持で内容更新（REQ-05 は REQ-05 のまま）
  - 削除は `~~REQ-XX ...~~ ❌(廃止: {日付} {理由} → revisions/{ファイル名})` 形式で残す
  - 追加は末尾連番で新 ID
- 仕様ファイルの変更履歴セクションに**1行**追記（詳細は改定記録へのリンクのみ。二重管理しない）。

## step5: 下流の部分再生成と再キュー化

承認された 🔵 と、確認済みの 🟡 **についてのみ**実施する:

- **仕様の兄弟**: AC / US / EDGE を更新（beam は acceptance-criteria.md 等の別ファイル、power は同一ファイル内）。
- **設計**: 影響ファイル・影響セクション**だけ**を beam3 / power3 のテンプレート形式で再生成する。改定理由を design-interview.md（beam）/ change-plan.md（power）に記録する。
- **beam の prep.md**: 外部サービス・API キー・環境変数に影響する変更なら、beam3 step5 の3操作方式（追加🆕 / 変更✏️ / 不要化❌）で同期する。
- **power の understanding-brief**: INT / REG / CON に影響するなら該当項目を更新する。
- **TASK**: 影響 TASK-*.md を更新（要件リンク・実装詳細・テスト要件。列挙要件は項目単位で明記）。規模が変わったものは `Skill(skill="estimate-storypoint", ...)` で再見積もりする。
- **tasks.db**（beam4 スキーマ互換のまま）。**① 行を書き直す → ② 状態を遷移させる、の順で行う**:
  - **① 行を書き直す（TASK-*.md → tasks.db の同期）**: 上で **TASK-*.md を書き換えたタスク**と、**新しく足したタスク**の**両方**を、beam4 step4.7 の UPSERT で書き込む。UPSERT は既存の行とぶつかると `title` / `content` / `story_point` / `buffer_percent` / `complexity` / `blocked_by` / `task_file` を上書きして `update_badge = 1` を立て、**`status` は上書きしない**（既存の状態はここでは保たれる）。最後に `_projects` の UPSERT で合計 SP も更新する。
    - **なぜ**: TASK-*.md だけ書き換えて DB は状態の変更だけにすると、ダッシュボードに「更新あり」が出ているのに内容の列は古い要約のまま、という最も紛らわしい状態になる（Notion にも古い要約が同期される）。再見積もりした SP も DB に戻らず、合計 SP がずれる。実装エンジンは TASK-*.md を読むので実装そのものは正しいが、人が見る表示と集計が実態とずれる。
    - **`content` 列は 1〜3文・200字以内の要約**にし、TASK-*.md の全文を入れない／空にもしない（詳細は beam4 の 4.7.4。ダッシュボードと Notion 同期にそのまま出るため）。**新規も書き換えも同じ**。
    - 新規要件のタスクは、TASK 番号を末尾の連番で振ってから同じ UPSERT に通す。
    - **`in_progress`（実装中）のタスクは、UPSERT の前に警告して個別に確認する**。実装中の人が見ている内容が途中で変わるため。
  - **② 状態を遷移させる（① のあと）**:
    - `done` / `in_review` → **`ready` に戻す**（① で `update_badge = 1` が立っているので、ダッシュボードに「更新あり」で浮く）
    - `ready` → 状態は変えない（① の書き直しだけで終わり）
    - `in_progress` → ① で確認した結果に従う
  - 廃止タスク → `is_deleted = 1`（＋TASK ファイルに廃止マーク）
  - **実装済みコードの撤去が必要な廃止**（要件が消えたが done のコードが残る）→ is_deleted ではなく**新規の「削除タスク」を起票**する
  - **★例外: 再実装を担う下流タスクが別に存在する場合は再キューしない。** 典型は「power 機能が同じ変更を実装する予定で、beam 側の done タスクが同じ要件を指している」ケース。ここで beam タスクを `ready` に戻すと、**同じ作業が 2 つのテーブルに二重に積まれ、どちらが正なのか分からなくなる**。この場合は beam タスクを `done` のまま据え置き（② で `ready` に戻さない。TASK-*.md も書き換えないので ① の対象にもならない）、**改定記録の「再キューしたタスク」節に「どの機能のどの TASK が担うか」を明記する**（再実装が宙に浮かないよう、担い手を必ず名指しする）。判断に迷うなら AskUserQuestion で確認する
- **conformance-report**: 影響行の判定を **「⏳ 要再検証（→ revisions/{ファイル名}）」に書き換える**（⭕を残さない）。
- **code-map は更新しない**（as-built インデックスのため、再実装後に beam5/power5 が更新する）。

## step6: 改定記録と完了報告

- `templates/revision-record-template.md` に従い、`docs/revisions/{YYYY-MM-DD}-{slug}.md` を生成する（変更前後・影響リスト・実施アクション・再キュータスク・残作業）。日付は Bash `date +%Y-%m-%d`。ディレクトリが無ければ作成。
- 完了報告:
  - 変更した仕様（ID と要約）、再生成した成果物一覧
  - **書き直し L 件 / 再キュー N 件 / 廃止 M 件 / 新規 K 件**（tasks.db 反映済み。書き直し＝TASK-*.md の変更を DB の行へ同期した件数）
  - conformance の ⏳ 化行数
  - **次アクション**: 「`/beam5-implement`（または `/power5-implement {機能名}`）で再実装 → ゲート（beam5 step4 / power6）で再検証」

## step7: Git 反映（beam / power で方式が異なる）

- **power の機能**: `feature/{機能名}` ブランチ上で、変更一式（仕様・設計・TASK・改定記録。**tasks.db と `.env` は含めない**）を `git add` → `git commit -m "revise: {対象ID} {要約}"`。
- **beam プロジェクト（トランク上・通常）**: **自分では commit しない**。beam の Git 反映はスタックド PR（beam-sync）に一本化されており、revise が手元のブランチへ直接コミットすると**その差分はどのフェーズ PR にも載らずトランクに届かない**。代わりに `Skill(skill="beam-sync", args="{要件名} revise-{slug}")` を実行し、専用ブランチへのコミット＋トランクへの PR を beam-sync に作らせる（未知 phase は汎用処理されトランク基点の PR になる）。前提未達（`gh` 未認証等）の報告はユーザーに案内する。
- **★beam プロジェクトが対象だが、引き金が power 機能の場合**（＝交差ケース。power 機能の前提条件として既存要件を直している）: **beam-sync を呼ばず、いまの `feature/{機能名}` ブランチへ直接コミットする**（`git add` → `git commit -m "revise: {対象ID} {要約}"`）。
  - **理由**: beam-sync を呼ぶと要件改定がトランクへの別 PR になり、実装は power の feature PR に残る。**2 つの PR に分かれた時点で、マージ順によっては「要件だけ変わって実装が無い」「実装が入ったのに要件はまだ旧仕様」という状態がトランクを通過する**。power はトランクのリリース可能性を**マージ単位のアトミック性**で担保しており、それが崩れる。
  - **要件改定は当該機能の前提条件**であって独立した変更ではない。同じマージ単位に載せるのが正しい。
  - **判定**: 現在のブランチ `git rev-parse --abbrev-ref HEAD` が **power のスタックのいずれかの段**（`feature/{機能名}` / `power5-phase*-{機能名}` / `power6-{機能名}`）であり、かつ `docs/spec/{その機能名}/feature-requirements.md` が存在すること。**ブランチ名だけで判断しない**（beam プロジェクトで人が切った `feature/*` を誤判定しうる）。
  - **どの段に載せるか**: 原則は**いま居る段**にそのままコミットする。要件改定は「この機能を進めるための前提」なので、実装より前の段（`feature/{機能名}`）まで戻す必要はない。スタック全体が `gh stack merge` でアトミックに入るため、どの段に載っても**トランクには同時に届く**。
  - **スタック外の独立 PR にしない**。これが崩れると上記の「2つの PR に分かれる」問題がそのまま再発する。
- git 管理外ならスキップして一言述べる。

# やらないこと（スコープ外）

- **再実装・コード修正**（beam5 / power5 の仕事）と**最終検証**（ゲートの仕事）
- 変更の**自動実行トリガー**（hook は手編集を検知できず、意味変更の判定もできない。検知は beam5/power5/power6 の drift 警告が担い、本スキルは常に人間が起動する）
- フロントマター等の**メタデータ新設**（導出で足りる。足りなくなった時に再検討）
- code-map の更新（再実装後に実装フェーズが行う）

# 環境前提

- beam または power の成果物がある既存リポジトリ内で実行する。WSL の bash 推奨。
- tasks.db 更新には `sqlite3`（無ければ TASK ファイルのみ更新し、その旨を報告）。

# テンプレートファイル

- `templates/revision-record-template.md` — 改定記録の書式。**step6 で必ず読み込むこと。**
