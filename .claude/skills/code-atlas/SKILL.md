あなたは既存コードベースを読み解くシニアエンジニアです。対象リポジトリを解析し、**あとから AI と人が頼れる「コードの地図帳」**を `docs/code-atlas/` に作ります。

地図帳は「一度読んだら終わりの報告書」ではなく、**次の作業のたびに引かれる資料**です。だから、全部を 1 つのファイルに書かず、入口から必要なファイルだけを辿れる形にします。

# 原則（最優先）

- **コードが正しい**。文書は古い前提で扱い、書かれている決まりはコードで確かめる。
- **全部を読まない**。目録で全体をつかみ、区画に分け、深く読む場所を選ぶ。大きいリポジトリを一様に読むと、どこも浅くなる。
- **調べていないことを明記する**。地図に無いことが「存在しない」と読まれると、古い地図より害が大きい。区画ごとに深さと、深く読んだ範囲を記録する。
- **🔵 は自己申告で付けない**。`file:line` の根拠を添え、検証スクリプトを通ったものだけを 🔵 にする。AI が書いたものを同じ AI が確認しても、同じ思い込みが入るため。
- **目録は手がかりで、根拠ではない**。目録（機械的な集計）は「どこを見るか」を決めるのに使い、全体像や規約の根拠には使わない。
- **重い読み取りはサブエージェントに任せる**。区画のページは、読んだサブエージェントが自分で書いて検証する。メインは、区画をまたぐ集約（全体像・規約・用語・入口）とユーザーへの確認に徹する。
- **読み取り中心。コードは変更しない**。書き込むのは `docs/code-atlas/` の中だけ。

# context

- 引数: 深く読みたい区画やテーマ（例: `S03`、`認証まわり`、`チャットのタグ`）。空なら、新規のときは全体をつかみ、既にあるときは更新する。
- ほかのスキルから呼ばれるとき（下の「呼び出し元があるとき」）: `--from power2 {テーマ}` / `--from power6 {機能名}`
- 出力（すべて `docs/code-atlas/` の下）:

| ファイル | 中身 | 誰が書くか | AI がいつ読むか |
|---|---|---|---|
| `index.md` | **入口**。全体の要約、区画の一覧と深さ、「知りたいこと → 読むファイル」 | メイン | **毎回、最初に** |
| `inventory.md` | 目録（スクリプトの出力そのまま。🟡） | スクリプト | 配置や規模を知りたいとき |
| `architecture.md` | 全体像。層・図（構成／区画をまたぐ主要フロー 1〜2 本と、その選び方／データの流れ）・エントリポイント・コマンド | メイン | 全体の形や流れを知りたいとき |
| `conventions.md` | 規約。文書の決まり、横断の規約、禁止・制約 | メイン | コードを書く・直す前 |
| `glossary.md` | 用語の対応。業務や画面の言葉 ↔ コード上の名前 | メイン | 機能の場所を名前から探すとき |
| `sections/{ID}-{slug}.md` | 区画のページ（深く読んだ区画だけ）。入口・主要モジュール・データ・依存・注意 | **サブエージェント** | その区画を触るとき |

- 開発ごとの実装の索引（`docs/tasks/{名前}/code-map.md`。beam5・power5 が書く）とは別のものです。地図帳は「既存システムの地図」で、工程の最初（解析・深掘り）と最後（反映）にだけ書き換えます。

### 呼び出し元があるとき

| 引数 | 呼び出し元 | 動き |
|---|---|---|
| `--from power2 {テーマ}` | power2-understand | 地図帳が無ければ新規に作り、有れば鮮度を確かめてから、テーマに関わる区画を深掘りする。step3-3 の確認（深く読む範囲）は行う。**step7 のコミットと CLAUDE.md の確認は行わない**（コミットは power2 が行う）。結果の要約を呼び出し元に返して終わる |
| `--from power6 {機能名}` | power6-verify | **反映**。step1 の鮮度の確認で古くなったファイルを見つけ、`docs/tasks/{機能名}/code-map.md` と差分を材料に更新する（step1 の「更新」）。あわせて、**理解ブリーフ（`docs/spec/{機能名}/understanding-brief.md`）の流れの図を、主に通る区画のページの「主な流れ」へ持ち込む**（理解ブリーフは機能の完了後に spec-archive で片付けられ、地図帳に残らないため。`references/diagrams-and-evidence.md` の 2-3）。step7 の確認は行わない |

## step1: 状態の確認と進め方の決定

- `pwd` と `git rev-parse --show-toplevel` で対象リポジトリを確かめる。git 管理外なら、目録と検証のスクリプトが使えないので、その旨を伝えて止まる（`git init` するかはユーザーが決める）。
- `CLAUDE.md` と `docs/rule/ai-security-guardrails.md` があれば読む。
- `docs/code-atlas/index.md` の有無で、進め方を決める:

| 状態 | 進め方 |
|---|---|
| 無い | **新規**: step2 から順に全部 |
| 有る・区画やテーマの指定あり | **深掘り**: 鮮度を確かめ（下記）、step3 で対象の区画を決めて step5 へ。既存のページは残し、足す。終わったら step6 で入口・全体像・用語を直す |
| 有る・指定なし（または `--from power6`） | **更新**: 鮮度を確かめ、古くなったファイルと区画だけを直す（下記）。全部が最新なら、その旨を伝えて終わる（単独で呼ばれたときは「深掘りする区画があるか」を尋ねる） |

- **既存の資料は手がかりとして読む**（根拠にはしない）:
  - `docs/code-map.md`（旧版の power2 が作った全体の地図）: 新規のときに一度読み、区画の切り方と全体像の仮説に使う。地図帳ができたら役目を終えるので、**step7 で削除を提案する**（勝手には消さない。提案の前に、ほかのファイルからの参照を確かめる。step7 を参照）。
  - beam で作ったリポジトリの `docs/spec/*/design/`（設計書）と `docs/tasks/*/code-map.md`（実装の索引）: 区画の役割と主要モジュールの仮説に使う。こちらは消さない（完了した機能の文書は spec-archive が片付ける）。
  - 現役の仕様 `docs/spec/current/README.md`（spec-archive が作る。あれば）: 領域の表を、区画の切り方と用語の対応の手がかりに使う。

### 鮮度の確認と更新

```bash
bash "$B/scripts/check-atlas-freshness.sh"     # $B の決め方は下の「スクリプトの呼び出し方」
```

- 「要確認」と出たファイルを直す。古いまま深掘りを重ねない。
- 数えるのはコードと設定の変更だけ。地図帳自身と `docs/` の下（`docs/rule/` を除く）の変更は数えない（機能ごとに仕様書が増えるたびに全部が古く見えるのを防ぐ）。ただし、`docs/` を対象パスに持つ区画のページ（文書の区画）は、新しい仕様書でも「要確認」になる。そのときは一覧に足すだけで済むことが多い。
- **区画のページ**: 変更されたファイルを `git diff --name-only <そのページの検証リビジョン> HEAD -- <対象パス>` で出し、`references/subagent-briefs.md` の依頼文 4 で更新する。変更が少なければ（目安: 15 ファイル以下）、メインで直してよい。`--from power6` のときは、`docs/tasks/{機能名}/code-map.md` と、理解ブリーフの流れの図を材料として渡す。
- **流れ: 要確認**（スクリプトが、図B や区画の中の流れの根拠のファイルが変わったと報告したもの）: そのファイルを読み、**流れの順番・分岐・参加者が今も同じか**を確かめる。違えば描き直し、同じなら行番号だけ直す。根拠の検証は場所の実在しか見ないので、順番の古さはここでしか見つからない。
- **全体像・規約・用語・入口**: 区画どうしの関係、エントリポイント、規約、用語に関わる変更があったときだけ直す。無ければ、検証リビジョンだけを書き換える（根拠の行がずれていないかは step6-2 の検証が見る）。
- **目録**: 作り直す（step2）。
- 直したら step6-2 の検証を通し、index.md の「更新の履歴」に 1 行足す。

### スクリプトの呼び出し方（step2・step5・step6 でも同じ）

スクリプトは**このスキルの置き場所から辿る**（作業ディレクトリや `$HOME` を基準にしない。`cd` した後やコンテナの中で外れるため）。

```bash
B='<このスキルのベースディレクトリ>'   # Claude Code が「Base directory for this skill」で示す値をそのまま入れる
B="$(printf '%s' "$B" | tr '\134' '/')"                    # \ を / に揃える（\134 はバックスラッシュ）
if command -v wslpath >/dev/null 2>&1; then                # WSL の bash のときだけ変換する
  case "$B" in
    //wsl.localhost/*/*|//wsl[$]/*/*) B="/${B#//*/*/}" ;;   # \\wsl.localhost\<distro>\x → /x
    [A-Za-z]:/*) B="$(wslpath -u "$B")" ;;                  # C:\x → /mnt/c/x
  esac
fi
```

スクリプトは内部でリポジトリのルートへ移動するので、呼び出せさえすれば、どこから実行しても同じ結果になる。

## step2: 目録を作る

```bash
mkdir -p docs/code-atlas/sections
bash "$B/scripts/build-code-inventory.sh" > docs/code-atlas/inventory.md
```

- 1 秒程度で終わる。依存は bash・git・awk だけで、リポジトリには書き込まない。
- 出力を読み、次をつかむ: **規模の区分**（小・中・大。コード〔テストと文章を除く〕の行数で判定する）、**探索から外す候補**、**ディレクトリの俯瞰**、**大きいソースファイル**（テストと文章を除く）、**規約の文書**、**パッケージの境目**、**中身が同じファイル**（写し。読むのは片方だけでよい）。
- 文章（Markdown・`docs/` の下）が多いリポジトリ（beam・power で作ったものなど）では、行数の大半が文書になる。区分はコードで決まるので、文書の量に引きずられて深く読む範囲を広げすぎない。
- 「探索から外す候補」は名前と形だけで判定している。明らかに誤り（手書きのソースが外れている）なら、その場所は読む対象に戻し、index.md の「未探索・分かっていないこと」に一言残す。
- `inventory.md` は手で編集しない（作り直すと消えるため）。

## step3: 規約の文書を読み、区画に分け、深く読む範囲を決める

### step3-1: 規約の文書を読む

目録の 5 節に挙がった文書を読む（長いものは、構成・決まり・禁止に関わる節だけ）。**変更に関係する決まり**を、場所（`./AGENTS.md:74-82` の形）と一緒に抜き出して控えておく。文書の決まりは、この時点では 🟡（step4 でコードと突き合わせる）。

> リポジトリ直下の `AGENTS.md` のような文書には、「新しい上限は設定で変えられるようにする」「ブランチは dev から切る」といった、コードを読むだけでは分からない決まりが書かれていることがある。コードの探索に入る前に読む。

### step3-2: 区画に分ける（最大 12）

目録の「ディレクトリの俯瞰」と「パッケージの境目」から、リポジトリを**区画**に分ける。

- 区画は、**変更するときに一緒に読むまとまり**にする。パッケージ、上位のディレクトリ、層（ルート・ロジック・データ）が単位の候補。
- **最大 12**。超えるなら、小さいものを「周辺（運用・設定・スクリプト）」のようにまとめる。
- 1 つの区画が大きすぎる（テストを除いて全体の 3 割を超える）なら、下位のディレクトリで分ける。
- ID は `S01` から振る。**一度振った ID は変えない**（分けたら `S03a`・`S03b`、無くしたら「廃止」と書く）。ほかのファイルや会話から ID で参照されるため。
- テスト専用のディレクトリ（`e2e/` など）は 1 つの区画にまとめ、深く読む対象にはしない（場所と実行の仕方だけ記録する）。

### step3-3: 深く読む範囲を決める

規模の区分と引数から、深く読む区画と、その中で読む範囲を決める。

| 規模 | 既定の進め方 |
|---|---|
| **小**（5 万行未満） | すべての区画を深く読む。サブエージェントを使わず、メインで読んで書いてもよい |
| **中**（30 万行未満） | 全体を浅くつかみ、中心になる区画（3〜5 個）を深く読む |
| **大**（それ以上） | 全体を浅くつかみ、**指定された区画・テーマに関わる区画だけ**（まず 2〜4 個）を深く読む。残りは必要になったときに足す |

- **深さは 3 段階で、「深い」には読んだ範囲を添える**:
  - **深い（全体）** — 区画の主要モジュールまで読み、ページがある。
  - **深い（{範囲}）** — 区画のうち、テーマに関わる部分だけを深く読んだ（例: 「深い（会話とタグの部分）」）。大きい区画をテーマで読むときは、こちらになる。**範囲の外は未探索として扱う**。
  - **浅い** — 役割・入口・依存だけ確かめた。ページは無く、architecture.md の「区画の要約」が唯一の記載。
  - **未探索** — 目録の情報だけ。
- **テーマがあるとき**は、そのテーマに関わる区画を Grep で探す。**要件の言葉とコード上の名前は違うことがある**（「タグ」が `Bookmarks` という名前で実装されている、など）ので、同義語・英語・略語でも探し、見つけた対応を控えておく（step6 で glossary.md に書く）。
- **中・大のときは、区画の一覧と深く読む案（区画と範囲、サブエージェントの本数の見込み）を示し、AskUserQuestion で確認する**（「この案でよい／区画を足す・減らす／浅い把握だけにする」）。小のときは確認せずに進める。
  - 本数と消費の見込み: 浅い把握は 2〜4 区画で 1 本（約 10 万トークン）、規約の調査は 1〜2 本（1 本約 20 万）、精読は 1 区画で 1 本（15〜25 万）。**案には合計の目安も添える**（実測: 中規模で深い区画 7・浅い区画 3 のとき、9 本で約 165 万トークン）。

## step4: 全体を浅くつかみ、横断の規約を調べて、規約のページを書く

**`references/subagent-briefs.md` を読んでから依頼する。** 浅い把握（依頼文 1）と規約の調査（依頼文 2）は互いに独立なので、同時に起動してよい。**並行は 4 本まで**。

### step4-1: 全体を浅くつかむ（依頼文 1・Explore）

- **深く読まない区画**について、役割・入口・ほかの区画との関係だけを確かめる。1 本あたり 2〜4 区画をまとめて任せる。
- 深く読む予定の区画は、ここでは省く（step5 で同じことを確かめるため）。
- 小さいリポジトリなら、メインで読んでよい。
- **エントリポイント**（起動・ルートの登録・画面の起点）と**コマンド**（ビルド・起動・テスト）は、マニフェストと起動のファイルをメインで読んで確かめる。コマンドは、実行して確かめたものだけ 🔵。

### step4-2: 横断の規約を調べる（依頼文 2・Explore）

- サーバー側と、画面側＋テストの 2 本に分けてよい。step3-1 で控えた文書の決まりを、番号（D1・D2…）を振って渡し、コードで守られているかを確かめさせる。
- 深掘り・更新のとき（規約のページが既にある）は、行わない。新しく見つかった規約だけを step6 で足す。

### step4-3: 規約のページを書く（★区画の精読より先に）

`templates/conventions-template.md` に従って `docs/code-atlas/conventions.md` を書く。

- **規約に ID（CV-01…）、禁止・制約に ID（NG-01…）を振る**。区画のページは、この ID で規約を参照する（「CV-05 から外れている」）。だから、区画の精読より先に書いて ID を確定させる。
- 文書の決まりと、コードで確かめた規約を分ける。規約から外れている場所も書く（まねてはいけない既存の書き方として読まれる）。
- サブエージェントの報告は、そのまま貼らない。根拠が省略形で返ってきたら、完全なパスに直す。

## step5: 選んだ区画を深く読む（サブエージェントがページを書く）

`references/subagent-briefs.md` の依頼文 3 を使う。

- **1 区画につき 1 本**の `general-purpose` サブエージェント（書き込みができるもの）に、**区画のページを直接書かせ、検証スクリプトを通すところまで任せる**。メインが報告を写す形にしない（文脈を使い、根拠の写し間違いが起きるため）。
- 依頼文に必ず入れるもの: 書くファイルのパス、テンプレートと規約のページの場所、検証のコマンド（**メインの環境で動いた呼び出し方をそのまま**）、検証リビジョン（`git rev-parse HEAD` の 40 桁）、読む範囲、目録の該当部分（下位ディレクトリの行数、大きいファイル、外す候補）、区画の一覧。
- テストを除いて 5 万行を超える区画は、テーマに関わる範囲に絞るか、下位のディレクトリで分ける。
- **並行は 4 本まで**。step4 と合わせて 8 本を超えそうなら、step3-3 の確認で本数を伝えておく。
- サブエージェントが返すのは短い要約（役割、使う区画・使われる区画、用語、規約の候補、未探索、検証の結果）だけ。メインはこれを step6 の集約に使う。
- 書き込みのできるサブエージェントを使えない環境では、Explore に読ませて報告を受け取り、メインがページを書く（このとき、省略形の根拠は完全なパスに直す）。

## step6: 全体像・用語・入口を書き、全体を検証する

### step6-1: メインが書くファイル

**`references/diagrams-and-evidence.md` を読んでから書く。**

| 書くファイル | テンプレート | 要点 |
|---|---|---|
| `architecture.md` | `templates/architecture-template.md` | 図A は区画の単位。図B は区画をまたぐ主要フローを 1〜2 本。**候補を並べて 4 つの観点（壊れたときの影響・またぐ区画の数・変更の頻度・利用者にとっての中心）で比べて選び、「主要フローの選び方」の表に選んだ理由と選ばなかった候補を残す**（`references/diagrams-and-evidence.md` の 2-1。テーマがあるときは、そのテーマが乗る流れを 1 本目にする）。該当しない図・読んでいない流れは描かず、理由を残す。浅い区画は「区画の要約」の表が唯一の記載になる |
| `glossary.md` | `templates/glossary-template.md` | サブエージェントの要約と、step3-3 で控えた「言葉とコード上の名前の違い」を集める |
| `conventions.md` | （step4-3 で書いたもの） | サブエージェントの報告を 2 つの向きで反映する。① 「規約の候補」のうち、複数の区画に当てはまるものを足す（ID は末尾に追加。既存の ID は変えない）。② 「規約から外れていた場所」と「規約のページの記述がコードと違っていた点」（例外の漏れ・事実の誤り）を、該当の規約の行に直す。規約のページは、精読より先に Explore の抜き取りの調査で書いているので、精読で誤りが見つかるのが普通 |
| `index.md` | `templates/index-template.md` | **最後に書く**。150 行以内。ほかのファイルの要約と案内だけ。深さの欄には、読んだ範囲を添える |

- 各ファイルの冒頭に **検証リビジョン**（`git rev-parse HEAD` の 40 桁）を書く。
- 根拠は **リポジトリのルートからの完全なパス**で、**1 つのバッククォートに 1 つ**。`` `a/b.ts:10, 20` ``・`` `:12` ``・ファイル名だけ、は検証されないか、検証で落ちる。
- **根拠でない場所も、バッククォートで書くなら完全なパスにする**。「未探索」の欄に `types/agents.ts` のような途中からのパスを書くと、根拠とみなされて「ファイルが存在しない」で落ちる。
- 深掘り・更新のときは、既存の内容を捨てない。直した範囲だけを書き換え、そのファイルの検証リビジョンを更新する。index.md の「更新の履歴」に 1 行足す。

### step6-2: 根拠を検証する（全ファイル）

```bash
bash "$B/scripts/verify-atlas-evidence.sh"
```

- サブエージェントが書いたページも含めて、全体をもう一度検証する（報告の「失敗 0」をうのみにしない）。
- **失敗した根拠は必ず直す**（パスの誤り・行のずれ）。直せないものは根拠を外し、その項目を **🟡 に下げる**。
- **「検証されない書き方の疑い」が 0 になるまで直す**。疑いのある箇所は、書いたつもりで検証されていない。
- スクリプトが見つからない・実行できないときは「未検証」として扱い、🔵 を付けない。
- **検証が見ているのは「その場所が実在するか」まで**。サブエージェントの主張のうち、全体像や規約の柱になるものを 5〜10 か所、メインが自分で読んで確かめる。

## step7: 完了の報告

- 出力したファイルの一覧（パスと行数）を示す。
- まとめ: 規模の区分、区画の数と深さの内訳（深い・浅い・未探索。深い区画は読んだ範囲も）、**根拠の検証結果（検証した根拠 N 件／失敗 0 件／疑い 0 件）**、描いた図と描かなかった図（理由つき）、サブエージェントの本数。
- **未探索の区画と、分かっていないこと**を示す（何が見えていないかを、人が判断できるように）。
- コードと食い違っていた文書の決まり、規約から外れている場所があれば挙げる。
- **呼び出し元があるとき（`--from …`）は、ここまでを呼び出し元に返して終わる。** 下の確認は行わない。旧版の `docs/code-map.md` が残っているときは、削除の提案を、下の 3 の参照の確認の結果と一緒に呼び出し元に申し送る。
- **単独で呼ばれたときは、次を AskUserQuestion で確認してから行う**（勝手に行わない）:
  1. `docs/code-atlas/` をコミットするか（する場合は `git add docs/code-atlas && git commit -m "code-atlas: ..."`。ブランチは今いるものを使い、push はしない）。
  2. プロジェクトの `CLAUDE.md` に、地図帳への案内を 1 行足すか（例: 「コードの全体像は `docs/code-atlas/index.md` から読む」）。足しておくと、次のセッションの AI が最初から地図帳を使える。`CLAUDE.md` が無く `AGENTS.md` があるリポジトリでは、どちらに足すかも尋ねる。
  3. 旧版の `docs/code-map.md` が残っているとき: 削除するか（地図帳に置き換わったため）。**尋ねる前に、ほかのファイルからの参照を確かめる**:

     ```bash
     git grep -n -F 'docs/code-map.md' -- . ':(exclude)docs' ':(exclude).claude/skills' ':(exclude).claude/skills-catalog'
     git grep -n -F 'docs/code-map.md' -- docs/rule
     ```

     - `docs/` の下は `docs/rule/`（現役の規約）だけを見る。過去の機能の仕様書・実装の記録は書き換えないので数えない。同期されるスキルの写しも数えない（同期で直る）。開発ごとの `docs/tasks/{名前}/code-map.md` は別物なので、パスごと探す。
     - **参照が無ければ** `git rm docs/code-map.md` してよいかを尋ねる。
     - **テスト・コード・設定・現役の文書（指示書・README）が参照していれば、ここでは消さない**。消すとテストが落ちたり、案内が切れたりする。参照の一覧を示し、「参照を直す作業と一緒に消す」ことを提案する（power から呼ばれたときは、機能のタスクに回す）。
- 次にできることを案内する: 深掘り（`/code-atlas S05` や `/code-atlas 認証まわり`）、更新（`/code-atlas`）、機能追加（`/power`）。
