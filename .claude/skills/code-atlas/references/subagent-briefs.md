# サブエージェントへの依頼文

重い読み取りはサブエージェントに任せ、メインは集約と確認に徹する。ここには 4 種類の依頼文のひな形を置く。`{…}` を埋めて使う。

| 依頼文 | 使う場面 | サブエージェントの種類 | 結果の受け取り方 |
|---|---|---|---|
| 1. 区画を浅くつかむ | step4 | `Explore`（読み取り専用） | 報告を受け取り、メインが architecture.md に書く |
| 2. 横断の規約を調べる | step4 | `Explore`（読み取り専用） | 報告を受け取り、メインが conventions.md に書く |
| 3. 区画を深く読んで、ページを書く | step5 | `general-purpose`（書き込みができる） | **サブエージェントが区画のページを自分で書き、検証まで済ませる**。メインは短い要約だけを受け取る |
| 4. 区画のページを更新する | 更新・power6 からの反映 | `general-purpose` | 同上 |

サブエージェントは、この会話の経緯を知らない。**依頼文に書いたことだけが手がかり**なので、目録の該当部分・区画の場所・返す形を必ず入れる。

> **なぜ精読はページを直接書かせるのか**: 報告をメインが写す形だと、(1) メインの文脈を 1 区画あたり 1 万トークン前後使い、(2) サブエージェントが根拠を省略形（ファイル名だけ、`:12` だけ）で返したときに、メインが完全なパスに直す手間と写し間違いが生まれる。書いた本人が検証スクリプトを通すところまで行えば、どちらも無くなる。

## 共通の決まり（どの依頼文にも入れる）

```
# 共通の決まり
- コードは変更しない。{依頼文 1・2: 読み取りだけ行う。／依頼文 3・4: 書き込んでよいのは、指定された区画のページ 1 つだけ。}
- コードを正とする。文書やコメントより、実際のコード。
- 推測で埋めない。読んで確かめたものは 🔵、一部だけ確かめた妥当な推測は 🟡、推測は 🔴 を頭に付ける。
- 根拠は、**リポジトリのルートからの完全な相対パス**で `パス:行` または `パス:行-行` と書く。
  - 省略しない。ファイル名だけ（`tags.js:12`）、途中からのパス（`routes/tags.js:12`）、行だけ（`:12`）は使わない。同じファイルを続けて指すときも、毎回パスの全体を書く。
  - 1 つのバッククォートに 1 つだけ書く（`a/b.ts:1, 5` のように並べない。2 か所あるなら 2 つのバッククォートに分ける）。
  - ルート直下のファイルは `./package.json:10` のように ./ を付ける。
  - 行番号は、自分で読んだ場所だけを書く（Grep の結果だけで書かない）。
  - 根拠でない場所（未探索のディレクトリやファイル）をバッククォートで書くときも、完全なパスにする。
- 次の場所は読まない: {目録の「探索から外す候補」}
- 1,000 行を超えるファイルは全体を読まず、Grep で場所を絞ってから範囲を指定して読む: {目録の「大きいソースファイル」のうち該当するもの}
- テストは、仕様を知る手がかりとして読んでよいが、精読の中心にしない。
- 調べなかった場所・分からなかったことを、最後に必ず書く。
```

## 依頼文 1: 区画を浅くつかむ（Explore）

全体像（architecture.md）を作るための探索。複数の区画をまとめて 1 本に任せてよい（1 本あたり 2〜4 区画）。

```
既存リポジトリの全体像をつかむための調査です。次の区画について、それぞれ「役割・入口・ほかの区画との関係」だけを確かめてください。中身の精読は不要です。

# 対象
リポジトリ: {ルートのパス}
区画:
- {S02}: `{dir/}`（{行数} 行。目録からの推測: {役割の仮説}）
- {S03}: `{dir/}`（…）

# 手がかり（目録からの抜粋。根拠にはしない）
{ディレクトリの俯瞰の該当行、マニフェスト、規約の文書}

# 調べること（区画ごと）
1. 役割: 何を担う区画か（1〜2 文）。
2. 入口: 外から呼ばれる面（ルートの登録、公開している関数や型、イベント、ジョブ、CLI）。代表を 3 つまで。
3. 使う区画: この区画が import・呼び出している、ほかの区画や外部サービス。
4. エントリポイント: 起動・ルートの登録・画面の起点がこの区画にあれば、その場所。

{共通の決まり}

# 返す形（全体で {区画数 × 300} 語以内）
区画ごとに次の形で返してください。

## {S02} {名前}
- 役割: 🔵 …  `パス:行`
- 入口:
  - 🔵 {種類} {名前} `パス:行-行`
- 使う区画: 🔵 {S05}（何を使うか） `パス:行`
- エントリポイント: …（無ければ「なし」）
- 調べなかったこと: …
```

## 依頼文 2: 横断の規約を調べる（Explore）

規約のページ（conventions.md）を作るための探索。観点を 2 本に分けて並行させてよい（サーバー側／画面側とテスト）。**区画の精読より先に行う**（規約の ID を先に決め、区画のページから参照できるようにするため）。

```
既存リポジトリで、実際に守られている規約を調べる調査です。変更するときに「既存に合わせる」ための基準を作ります。

# 対象
リポジトリ: {ルートのパス}
調べる範囲: {深く読む区画の場所。全体が小さければ全体}
深追いしない場所: {特殊で大きい区画。代表例は、ふつうの一覧と編集の処理から選ぶ}

# 手がかり（根拠にはしない）
- 規約の文書に書かれている決まり: {メインが読んで抜き出した要点と場所。D1・D2… と番号を振る}
- 区画の一覧: {ID・場所・役割}

# 調べること（観点ごとに、守られている形と代表例）
{次から、この依頼で担当する観点を選んで入れる}
1. 認証・認可: どこで、どの単位で確かめているか。データの所有者の確かめ方。
2. 入力検証: どこで、何を使って確かめているか。検証の無い入口があれば、その場所。
3. エラー処理・ログ: 例外の扱い、応答の形、ログに出すもの。
4. データアクセス: データベースへの入り方（ORM・メソッドの層・トランザクション）。
5. 画面の状態管理とデータ取得: 使っている仕組み、更新後の反映の仕方。
6. テスト: 種類、置き場所、命名、モックの方針、実行のコマンド。
7. 設定・環境変数: 置き場所、既定値の決め方。
8. 命名・配置: ファイルやシンボルの付け方、新しいコードの置き場所（最近足されたと見える機能を 1 つ選び、ファイルの置き方を追う）。
9. 型チェックと静的チェック: 実行のしかた、コミット前に走るもの。

それぞれ、代表例を 2〜3 か所読んで確かめ、**規約から外れている場所**が見つかれば挙げてください。
文書に書かれている決まりは、コードで守られているかを確かめ、「守られている・一部だけ・確かめられなかった」を返してください。

禁止・制約: 「〜しない」「してはならない」という趣旨のコメントを Grep で探し（日本語と英語の両方。例: must not / never / do not / しない / してはならない / 禁止）、設計上の決まりを表すものだけを 8〜12 個選んで挙げてください（TODO や一時的な注意は除く）。

{共通の決まり}

# 返す形（全体で 1,500 語以内）
## {観点}
| 規約 | 代表例 | 例外・守られていない場所 | 信頼性 |
## 文書の決まりの確認
| 決まり（D1…） | コードで確かめた結果 | 根拠 |
## 禁止・制約
| 制約 | 場所 | 補足 |
## 未探索・分かっていないこと
```

## 依頼文 3: 区画を深く読んで、ページを書く（general-purpose）

**1 区画につき 1 本**。大きい区画（テストを除いて 5 万行超）は、テーマに関わる範囲に絞るか、下位のディレクトリで 2〜3 本に分ける（分けたときは `S03a`・`S03b` のように別のページにする）。

```
既存リポジトリの 1 つの区画を読み、ほかの人と AI がこの区画を変更するときに頼れる「区画のページ」を書く仕事です。ページを書き、根拠の検証を通すところまでがあなたの仕事です。

# 対象
リポジトリ: {ルートのパス}
区画: {S03} {名前}（`{dir/}`。テストを除いて {行数} 行）
読む範囲: {区画の全体／テーマ「{テーマ}」に関わる部分だけ。区画の全体については、構成と入口が分かれば十分}

# 書くファイル（これ 1 つだけ。ほかのファイルは変更しない）
`docs/code-atlas/sections/{S03}-{slug}.md`

# 先に読むもの
1. テンプレート: `{このスキルの置き場所}/templates/section-template.md`（見出しと表の形は、これに合わせる）
2. 規約のページ: `docs/code-atlas/conventions.md`（全体の規約と ID。この区画で規約から外れている場所を見つけたら、「CV-05 から外れている」のように ID で書く。新しい規約の候補は、ページには書かず、最後の報告で挙げる）
3. 図と根拠の基準: `{このスキルの置き場所}/references/diagrams-and-evidence.md` の「2-2 区画の中の流れ」「2-4 流れの書き方」「4. 根拠の書き方」

# 手がかり（根拠にはしない）
- 浅い調査で分かっていること: {役割・入口・使う区画。無ければ「なし」}
- 目録からの抜粋: {下位ディレクトリの行数、大きいファイル}
- 区画の一覧: {ID・場所・役割。ほかの区画は ID で書く}

# 調べること
1. 入口: 外から呼ばれる面（ルート・公開関数・イベント・ジョブ）。数が多ければ種類ごとに代表と件数。
2. 主要モジュール: この区画を変更するときに触りそうなファイルと、ほかから使われているファイル（10〜15 個）。それぞれ、責務・公開シンボル（実際のシグネチャ）・依存・固有の約束や落とし穴。
3. データ: この区画が定義・読み書きするデータ（スキーマ、保存先、キャッシュやグローバルな状態）。**同じデータを書く経路が複数あれば、すべて挙げる**（Grep で書き込みを洗う）。
4. 依存: この区画が使う相手と、この区画を使う相手。**ほかから使われている共用の部品や関数は、import しているファイルをすべて洗う**。
5. 固有の規約と注意: 繰り返し現れる実装の型、順序に依存する処理、トランザクションの有無、「〜しない」という趣旨のコメント。
6. テスト: 場所と種類、テストが無い場所。
7. 変更するときの手がかり: 「ここを変えると、どこに波及するか」が分かった組。
8. 主な流れ: この区画の中の主な処理を 0〜2 本、入口から出口まで順に追い、ページの「主な流れ」に図か手順の表と根拠の表で書く。状態を変える処理（書き込み・権限・解放・削除）を優先する。分岐（成功・失敗・権限なし）も書く。読み取りだけの区画なら 0 本でよい（理由を一言）。決まりは `{このスキルの置き場所}/references/diagrams-and-evidence.md` の 2-2 と 2-4（見出しは「### 流れ: 名前」）。**実際に順に読んで確かめた流れだけを書く**（Grep の結果だけで順番を組み立てない）。

名前の注意: 業務や画面の言葉と、コード上の名前が違うことがあります（例: 「タグ」が Bookmarks という名前で実装されている）。同義語・英語・略語でも探してください。見つけた対応は、最後の報告で「用語」として挙げてください。

{共通の決まり}

# ページの決まり
- 冒頭に、役割・**対象パス**（バッククォートで囲み、ディレクトリは / で終える）・**深さ**・**検証リビジョン** `{40桁の SHA}`・最終更新 {日付} を書く。
- 深さは「深い（全体）」または「深い（{読んだ範囲}）」と書く。読んでいない範囲は「未探索・分かっていないこと」に必ず書く。
- 300 行以内。

# 書いたら検証する（必ず実行する）
{メインの環境で動いた呼び出し方をそのまま入れる。例:}
bash "{このスキルの置き場所}/scripts/verify-atlas-evidence.sh" --file docs/code-atlas/sections/{S03}-{slug}.md

- 「失敗」が 0、「検証されない書き方の疑い」が 0 になるまで直す。直せない根拠は外し、その項目を 🟡 に下げる。
- スクリプトを実行できなかったときは、その旨を報告する（🔵 は付けたままにしない）。

# 最後の報告（300 語以内。ページの中身は繰り返さない）
- 書いたファイルと行数、検証の結果（根拠 N 件／失敗 0／疑い 0）
- この区画の役割（1 行）と、使う区画・使われる区画（ID と根拠 1 つずつ）
- 用語（業務・画面の言葉 → コード上の名前 → 場所）
- 規約の候補（全体の規約に足すべきもの。あれば）と、規約から外れていた場所の ID
- 規約のページの記述が、この区画のコードと違っていた点（例外の漏れ・事実の誤り。あれば。メインが規約のページを直す）
- 未探索の範囲
```

## 依頼文 4: 区画のページを更新する（general-purpose）

地図帳の更新と、power6 からの反映で使う。変更が少なければ（目安: 対象パスの中で 15 ファイル以下）、サブエージェントを使わずにメインで直してよい。

```
既存の「区画のページ」を、コードの変更に合わせて更新する仕事です。ページを直し、根拠の検証を通すところまでがあなたの仕事です。

# 対象
リポジトリ: {ルートのパス}
更新するファイル（これ 1 つだけ）: `docs/code-atlas/sections/{S03}-{slug}.md`
検証リビジョン: 今は `{古い SHA}`。更新後は `{今の HEAD の SHA}` に書き換える。

# 変更の材料
- この区画で変更されたファイル: {git diff --name-only <古い SHA> HEAD -- <対象パス> の結果}
- {あれば} 今回の機能の実装の索引: `docs/tasks/{機能名}/code-map.md`（足した・変えたモジュールと、その責務・公開シンボル）
- {あれば} 変更の設計: `docs/spec/{機能名}/design/change-plan.md`
- {あれば} 流れの鮮度: {鮮度の確認スクリプトが「流れ: 要確認」と出した流れの名前と、変わった根拠のファイル}
- {あれば} 持ち込む流れ: `docs/spec/{機能名}/understanding-brief.md` の {節の名前}（power2 が描いて検証した、この機能が乗る流れの図）

# すること
1. 今のページを読む。
2. 変更されたファイルを読み、ページのうち古くなった記述（入口・主要モジュール・主な流れ・データ・依存・注意・テスト・変更するときの手がかり）を直す。新しく足されたモジュールや書き込みの経路を足す。
   - **「流れ: 要確認」の流れ**は、変わったファイルを読んで、順番・分岐・参加者が今も同じかを確かめる。違えば描き直し、同じなら行番号だけ直す。
   - **持ち込む流れ**があれば、実装後の今のコードで順に読み直して描き、「主な流れ」に `### 流れ: {名前}（{機能名} の理解ブリーフから・{日付}）` として足す（ブリーフの図を写すだけにしない。根拠は今の HEAD で取り直す）。流れが 2 本を超えるなら、`{このスキルの置き場所}/references/diagrams-and-evidence.md` の 2-1 の観点で 2 本に絞り、外したものを「未探索・分かっていないこと」に一言残す。区画を 3 つ以上またぐ流れなら、ページには区画の中の部分だけを書き、全体を図B に入れるべきかを最後の報告で挙げる。
3. 変更されていない部分の記述は残す。ただし、行番号がずれた根拠は直す。
4. 冒頭の検証リビジョンと最終更新を書き換える。深さの範囲が広がったなら、それも直す。

{共通の決まり}

# 書いたら検証する（必ず実行する）
bash "{このスキルの置き場所}/scripts/verify-atlas-evidence.sh" --file docs/code-atlas/sections/{S03}-{slug}.md

# 最後の報告（200 語以内）
- 直した点（足した・消した・書き換えた項目）、検証の結果
- 全体像（区画どうしの関係・図）や、規約・用語のページに反映すべき変更があれば、その内容
```

## 返ってきた結果の扱い

- **依頼文 1・2 の報告は、そのまま貼らない**。テンプレートの形に整え、根拠が省略形で返ってきたら完全なパスに直す。区画をまたぐ食い違い（A の報告では「S03 が S05 を使う」、B の報告では逆）は、該当箇所を自分で読んで決める。
- **依頼文 3・4 のページは、検証の結果を確かめる**。報告の「失敗 0／疑い 0」をうのみにせず、step6 で全体をもう一度検証する。
- **根拠の無い項目は図に描かない**（DG-5）。🟡 のまま「分かっていないこと」に回す。
- **用語は glossary.md に集める**。区画ごとの報告に散らばったままにしない。
- サブエージェントが上限などで止まったら、同じエージェントに続きを頼む（やり直させない）。
