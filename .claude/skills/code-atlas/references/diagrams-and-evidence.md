# 図と根拠の基準

地図帳を **図（人が見て分かる）** と **根拠（機械が検証できる）** の両輪で残すための基準。作図の決まりには ID（DG-1 など）を振ってある。指摘や記録では ID で引用する。

code-atlas が地図帳を書くときと、power2-understand が理解ブリーフに機能のフローの図を描くとき、power6-verify が根拠を再検証するときに読む（図と根拠の基準は、ここが唯一の出典）。

## 1. なぜ図と根拠なのか

- **図は理解の検査になる**。散文は曖昧なまま書けてしまうが、図はノードと辺を決めないと描けない。描けないなら、理解できていない。
- **根拠は信頼の検査になる**。AI が書いたものを同じ AI が確認しても、同じ思い込みが入る。機械で検証できる形にしておけば、自己申告に頼らずに 🔵 を主張できる。
- **Mermaid で描く**。座標や配線を手で置く形式は、コードの理解に使うべき労力を取られるので使わない。

## 2. 図の種類

該当しない図は描かず、理由を一言残す。全部を描くことが目的ではない。

| 図 | 置き場所 | 答える問い | 描く目安 |
|---|---|---|---|
| **A. 構成** | architecture.md | 何がどこにあるか。区画・境界・外部への依存 | 原則として描く。ノードは区画の単位 |
| **B. 主要フロー** | architecture.md | 代表的な要求が、入口から出口まで**区画をまたいで**どう流れるか | 明確な入口（HTTP API・CLI・ジョブ・画面の操作）があるなら **1〜2 本**。選び方は 2-1 |
| **C. データの流れ** | architecture.md | データがどこから来て、どこへ書かれるか | 永続化や外部のデータ源があるなら描く |
| **D. 区画の中の流れ** | 区画のページの「主な流れ」 | その区画の中で、主な処理がどの順に進むか | 深く読んだ区画に **0〜2 本**。2-2 |

- B が最も効く。1 本の要求を入口から出口まで追えないなら、全体を理解できていない。
- **流れの価値は「ファイルをまたぐ処理の順番」と「それぞれの根拠」にある。** AI にとっては、何本ものファイルを探し回らずに、根拠の場所へ直接行ける索引になる。人にとっては図が読みやすい。だから図と根拠の表を必ず組にする。
- **機械が確かめられるのは「根拠の場所が実在するか」まで**で、「順番が正しいか」は確かめられない。流れを増やすほど、古くなったときに誤った順番を信じさせる危険も増える。だから本数を絞り、7 の「流れの鮮度」で古くなったものを見つける。

### 2-1. 主要フロー（図 B）の選び方

「中心的な機能」を AI の印象で決めない。**候補を並べ、4 つの観点で比べて選び、選んだ理由と選ばなかった候補を architecture.md に残す。**

1. **候補を並べる**: 区画のページの「入口」と、architecture.md の「エントリポイント」から、利用者や外部が起こす要求（画面の操作・API・ジョブ）を挙げる。似たものはまとめる（同じ機能の出題と採点は 1 つの候補）。多ければ、状態を変えるもの（書き込み・権限・削除）を優先して 8 個まで。
2. **4 つの観点で比べる**:

   | 観点 | 見ること | 測り方 |
   |---|---|---|
   | ① 壊れたときの影響 | 状態を変えるか（書き込み・権限・解放・課金・削除）。代わりの経路が無いか | コードを読んで 高・中・低 |
   | ② またぐ区画の数 | 区画をいくつ通るか（多いほど、全体の理解に効く） | 区画の数 |
   | ③ 変更の頻度 | これまで何回変えられたか（よく変わる場所ほど、次の改修でも触る） | 入口のファイルで `git log --oneline --follow -- <パス> \| wc -l` |
   | ④ 利用者にとっての中心 | 利用者が最もよく使う・プロダクトの目的そのもの | 現役の仕様（`docs/spec/current/`）や PRD。無ければコードから 🟡 |

3. **選ぶ**: 4 つの観点を総合して 1〜2 本。**① が高く、② が多いもの**を優先する（壊れると困り、全体の理解に効くため）。④ だけが高いもの（よく使うが単純な流れ）は、2 本目の候補か、区画の中の流れ（D）に回す。テーマを指定されているとき（power2 から呼ばれたとき）は、テーマが乗る流れを 1 本目にする。
4. **記録する**: architecture.md の「主要フローの選び方」の表に、候補ごとの 4 つの観点と、選んだか（選ばなかったなら、どこで読めるか: 区画のページの流れ・未探索）を書く。

### 2-2. 区画の中の流れ（図 D）

- **深く読んだ区画だけ**に書く。浅い・未探索の区画には書かない。
- **0〜2 本**。区画の入口から出口までのうち、2-1 の ① が高いもの（状態を変える処理）を優先する。単純な読み取りだけの区画なら 0 本でよい（理由を一言残す）。
- 区画をまたぐ流れの全体は図 B が持つ。区画のページには、**この区画の中の部分**を、図 B より細かい単位（関数・分岐）で書く。図 B と重なるときは、図 B へのリンクを添える。
- 形は Mermaid の図（`sequenceDiagram` か `flowchart`）か、番号つきの手順の表のどちらでもよい（AI にとって価値は同じ。分岐が多いなら図、まっすぐなら表が読みやすい）。どちらでも、**直下に根拠の表**を置く。
- 見出しは `### 流れ: {名前}` にする（鮮度の確認スクリプトが、この見出しで流れを見分ける）。

### 2-3. 機能の流れを地図帳へ持ち込む（power6 の反映）

power2 は、機能が乗る流れを理解ブリーフに図として描き、実コードで検証している。理解ブリーフは機能が完了すると spec-archive で片付けられるので、**そのままでは地図帳に残らない**。power6 の反映（`--from power6`）で次を行う:

- 理解ブリーフの流れの図のうち、**実装後のコードで描き直せるもの**を、主に通る区画のページの「主な流れ」へ移す（実装で変わった部分は描き直し、根拠を今の HEAD で取り直す）。見出しに出典を添える: `### 流れ: {名前}（{機能名} の理解ブリーフから・{日付}）`。
- 区画のページの流れが 2 本を超えるなら、2-1 の観点で比べて 2 本に絞る（外したものは「未探索・分かっていないこと」に一言残す）。
- 区画を 3 つ以上またぎ、2-1 の比較で今の図 B より上に来るなら、図 B の 2 本目に入れるか入れ替えを提案する（architecture.md の選び方の表も直す）。

### 2-4. 流れの書き方の共通の決まり

- 図 B は `## 図B1. 主要フロー: {名前}`・`## 図B2. 主要フロー: {名前}`、図 D は `### 流れ: {名前}` の見出しで始める。**見出しの直下に図（または手順の表）、その直下に根拠の表**を置き、次の見出しまでをその流れの範囲とする（鮮度の確認スクリプトが、この範囲の根拠を流れの根拠として数える）。
- 参加者（図のノード）ごとに、根拠を 1 つ以上書く。

## 3. 作図の決まり（DG-1〜DG-5）

- **DG-1 主役の流れを 1 本、先に作る** — 枝は、いちばん近い主役のノードから出す。全部を対等に並べると、何が主役かが消える。
- **DG-2 ノードは最大 12** — 超えるなら抽象度を上げる（ファイルではなくモジュール、モジュールではなく区画）。細部は区画のページが持つ。
- **DG-3 読みにくいときは、まず線を減らす** — 描き方を工夫する前に、描かなくてよい関係を消す。
- **DG-4 ラベルは情報** — 辺のラベル（プロトコル・向き・同期か非同期か）は装飾ではない。両端から自明な場合を除いて消さない。
- **DG-5 憶測を描かない（最重要）** — 図に描いてよいのは、実コードで確かめたものだけ。「たぶんこうなっている」は図にせず、「未探索・分かっていないこと」に書く。

## 4. 根拠の書き方

バッククォートで囲み、**リポジトリのルートからの相対パス**に、行または行の範囲を付ける。

```
`src/server/routes/tasks.ts:12`         単一行
`src/server/routes/tasks.ts:12-48`      行の範囲
`./main.py:10`                          ルート直下のファイル（./ を付ける）
```

検証スクリプトが根拠として拾う条件は、**バッククォートの中にある・`/` を含む・拡張子がある・`://` を含まない** の 4 つ。外れた文字列は散文とみなされ、検証されない。

- **`/` が必須** — `127.0.0.1:8080` のような「ホスト:ポート」を拾わないための決まり。ルート直下のファイルには `./` を付ける。
- **拡張子が必須** — `GET /api/tasks` のような文中のパスを拾わないための決まり。ディレクトリは根拠にできないので、代表のファイルを指す。
- **リポジトリのルートからの完全なパス** — ファイル名だけ（`` `b.ts:10` ``）は `/` が無いので検証されず、途中からのパス（`` `routes/b.ts:10` ``）は「ファイルが存在しない」で落ちる。同じファイルを続けて指すときも、毎回パスの全体を書く。
- **1 つのバッククォートに 1 つの根拠** — 次の書き方は検証されない。分けて書く。

| 書き方 | 検証 | 直し方 |
|---|---|---|
| `` `a/b.ts:10, 20-30` `` | されない | `` `a/b.ts:10` `` と `` `a/b.ts:20-30` `` に分ける |
| `` `a/b.ts:10` ``、`` `:20` `` | 2 つ目がされない | 2 つ目にもパスを書く |
| `` `b.ts:10` ``（ファイル名だけ） | されない | `` `src/a/b.ts:10` `` |
| `` `a/b.ts`（10 行目） `` | 行は見ない | `` `a/b.ts:10` `` |

- **根拠でない場所も、バッククォートで書くなら完全なパスにする** — 検証スクリプトは、バッククォートの中の「`/` を含み、拡張子がある文字列」をすべて根拠として扱う。「未探索」の欄に `` `types/agents.ts` `` のような途中からのパスを書くと、検証で落ちる。完全なパスで書くか、バッククォートを外す。
- **検証リビジョンの時点に無いファイルは根拠にできない** — 次のものはバッククォートで書くと「ファイルが存在しない」で落ちる。地の文で書くか、Markdown のリンクにする。
  - Git で追跡していないファイル（`.env.local`・`node_modules/` の中・`data/tasks.db`・`.claude/settings.local.json` など）
  - まだコミットしていないファイル（とくに、同じコミットで初めて入る地図帳のページ。理解ブリーフから参照するときはリンクにする）
  - URL のパス（`/robots.txt` のように `/` で始まるもの。絶対パスとして拒まれる）

- 絶対パス・`..`・`.git` 配下は不正で、検証で落ちる。
- 行番号は任意。パスだけでも、ファイルの実在は検証される。
- **根拠は図の中に書かず、図の直下の表に置く**。図の読みやすさを保ち、機械が拾いやすくするため。

## 5. 検証リビジョン

地図帳の各ファイルの冒頭に、**どの時点のコードに対して根拠を検証したか**を書く。

```markdown
> **検証リビジョン**: `<40桁の完全な commit SHA>`
```

- ファイルごとに持つ。区画のページは、別々の時点で深掘り・更新されるため。
- ファイルを更新したら、このリビジョンも更新して再検証する。放置すると「昔は正しかった根拠」が残る。

## 6. 検証と信頼性レベル

検証スクリプトは `scripts/verify-atlas-evidence.sh`。呼び出し方（スキルの置き場所からの辿り方）は code-atlas の SKILL.md の step1「スクリプトの呼び出し方」に従う。地図帳の全体は引数なしで、1 つのファイルだけ（区画のページ、理解ブリーフ）は `--file <パス>` で検証する。

| 検査 | 内容 |
|---|---|
| パスの安全性 | 絶対パス・`..`・`.git` 配下を拒む |
| ファイルの実在 | 記録したリビジョンの時点で、そのパスにファイルがあるか |
| 行の実在 | 書いた行（範囲なら末尾）が、その時点の行数に収まるか |
| 書き方の疑い | 検証されない書き方（省略形・複数指定）を数えて警告する |

**検証が見ているのは「その場所が実在するか」までで、「そこに書いてあることが主張どおりか」は見ない。** だから、根拠の行は自分で読んだ場所だけを書く。Grep の結果だけで行番号を書かない。

信頼性レベルとの関係:

- **🔵 を付けてよいのは、検証を通った根拠が付いている項目だけ**。「確認した」という自己申告だけでは 🔵 にしない。
- 検証で落ちた根拠は、パスや行を直す。直せなければ根拠を外し、**🟡 に下げる**。
- 根拠を付けられない理解（コードから読み取れない意図や経緯）は 🟡 か 🔴 のまま残し、「分かっていないこと」に書く。
- スクリプトが見つからない・実行できないときは「未検証」と書き、🔵 を付けない。
- スクリプトが報告する「検証した根拠: N 件」が、書いた数と大きく違わないかを見る。少なければ、書き方が外れて黙って漏れている。

## 7. 流れの鮮度

検証は「根拠の場所が実在するか」しか見ないので、**流れの順番が古くなっても検証は通る**（行の数が足りていれば落ちない）。そこで、鮮度の確認スクリプト `scripts/check-atlas-freshness.sh` は、ファイルの単位に加えて**流れの単位**でも調べる:

- 図 B（`## 図B…`）と図 D（`### 流れ: …`）の見出しから次の見出しまでにある根拠のファイルのうち、そのページの検証リビジョンから HEAD までに変更されたものを数える。
- 1 つでもあれば「流れ: 要確認」と出す。**そのファイルを読み、流れの順番・分岐・参加者が今も同じかを確かめ**、違えば描き直す。同じなら行番号だけ直す。
- 流れの根拠のファイルが変わっていなければ、ページの別の場所が古くなっていても、流れ自体は信じてよい。
