PRD・設計文書・タスクノートを参照しながら開発の要件を整理し、機能仕様を明確化します。各項目に信頼性レベル（🔵🟡🔴）を付与して要件定義を作成します。

# context

- 出力ディレクトリ: `docs/spec`
- 要件名: `{要件名}` （step1 で確定）
- PRDファイル: `docs/spec/{要件名}/product-requirements.md`
- タスクノート: `docs/spec/{要件名}/note.md`
- 作業規模: `{work_scope}` （引数。未指定の場合は `"フル機能開発"` をデフォルトとする）
- 信頼性評価: `[]`

# 変数表記の凡例

- `{要件名}` は step1 で確定する変数。実際のファイルパス生成時には具体値に置換する。
- `{work_scope}` は引数（"フル機能開発" / "軽量開発" / "カスタム" のいずれか）。
- `scope-options=on|off` は任意の第2引数。`on` なら step4c でスコープ4案マトリクスを生成する（未指定は off＝従来動作）。

## step1: 開発コンテキストの準備

- **要件名の確定**
  - Bash で `pwd` を実行し、basename をプロジェクトルートディレクトリ名として取得する
  - 取得したディレクトリ名を `{要件名}` として確定する

- **専用ルールの読み込み**
  - スキルディレクトリ内の `rules/rules.md` を読み込む

- **タスクノートの読み込み**
  - `docs/spec/{要件名}/note.md` を読み込む
  - ノートには技術スタック、開発ルール、関連実装、設計文書、注意事項が含まれる
  - **存在しない場合**: beam1-tasknote を先に実行する必要がある旨を警告し、AskUserQuestion で継続するか確認する

- **PRDファイルの読み込み**
  - `docs/spec/{要件名}/product-requirements.md` を読み込む
  - PRDには以下が含まれることを期待：
    - プロダクトビジョン
    - ターゲットユーザー
    - 主要機能
    - ビジネス要件
    - 成功指標

- **追加ルールの読み込み（存在する場合のみ）**
  - `docs/rule/` ディレクトリ
  - `docs/rule/beam/` ディレクトリ
  - `docs/rule/beam/requirements/` ディレクトリ

- **プロジェクト基本情報の収集**
  - `CLAUDE.md` の内容を読み込む（プロジェクト概要・技術スタック・制約）
  - プロジェクト構造（ディレクトリ構成）を把握

- **既存設計文書・仕様書の調査**
  - `docs/` ディレクトリ配下の関連設計文書を確認
  - **安全装置**: 該当ファイルが20件を超えた場合はファイル名一覧を表示し、AskUserQuestion で読み込み対象を絞る

- **収集情報のサマリー作成**
  - 定義済み要件・未定義部分の特定
  - 技術制約・非機能要件の整理
  - ギャップ分析（PRD vs 既存設計 vs ユーザー期待）

- **スコープ選定の確認（scope-options.md）**: `docs/spec/{要件名}/scope-options.md` が存在すれば読み込む。**選定記録が要望案以外**で、再整列チェックに requirements が未完了で残っている場合は**選択案モード**で動作する:
  - スコープの正は scope-options.md の**機能×案マトリクス（選択案の列）**とする（スコープの再ヒアリングはしない）
  - 採用レベルが要望案と同じ機能: 既存 requirements.md の該当 REQ を**流用**する
  - **簡易化**された機能: マトリクスの簡易実装内容に沿って REQ を書き直す
  - **追加**された機能（リッチ/フル）: **その機能についてのみ** step3 相当の差分ヒアリング（受け入れ基準・エッジケース・NFR 数値）を行う
  - interview-record.md は破棄せず**追記**する。生成完了後、scope-options.md の再整列チェックの requirements を ✅ に更新する
- 読み込み完了後、context の内容（要件名、作業規模、PRDサマリー、ノートサマリー）をまとめてユーザに宣言する
- step2 を実行する

## step2: 作業規模の確認

- `{work_scope}` の値に応じて分岐：
  - `"フル機能開発"`: そのまま step3 に進む
  - `"軽量開発"`: そのまま step3 に進む
  - `"カスタム"`: 以下の AskUserQuestion を実施してから step3 に進む

- カスタム時の質問:
  ```
  AskUserQuestion({
    questions: [{
      question: "要件定義書に含める項目を選択してください（複数選択可）",
      header: "含める項目",
      multiSelect: true,
      options: [
        { label: "詳細なユーザーストーリー", description: "包括的なユーザーストーリーを作成" },
        { label: "非機能要件の詳細化", description: "パフォーマンス・セキュリティ等の詳細な非機能要件" },
        { label: "エッジケースの洗い出し", description: "エラー処理・境界値等のエッジケース" },
        { label: "パフォーマンス要件", description: "詳細なパフォーマンス要件の定義" }
      ]
    }]
  })
  ```
- 選択結果を `custom_items` として保持し、step3, step4 で参照する

## step3: 既存情報ベースの差分ヒアリング

作業規模に応じてヒアリング項目を調整。

**重要**: 以下の質問は例示。実際のプロジェクト状況に応じて AskUserQuestion ツールを使用して適切な質問を作成すること。

### 共通ルール

- すべての質問は AskUserQuestion ツールで実施する
- すべての質問を一度に投げず、文脈に応じて段階的に質問する
- ユーザーの回答を受けて、必要に応じて追加質問を行う
- 質問は具体的で、選択肢から選べる形式にする（自由記述は「その他」オプションで対応 — 自動付与される）

### フル機能開発の場合

以下のカテゴリごとに、既存情報（PRD、設計文書、実装）から特定した具体的な課題・不明点について質問する：

**既存設計の妥当性・過不足確認**
- 既存の機能要件・非機能要件の確認
- 現在の制約事項（性能・データ制限等）の妥当性
- 技術スタック選択の妥当性
- 既存設計で実現困難・不適切な部分の代替案

例:
```
AskUserQuestion({
  questions: [{
    question: "現在のCLAUDE.mdで定義されている{具体的な制約事項}について、実際の運用で問題ないでしょうか？",
    header: "制約確認",
    multiSelect: false,
    options: [
      { label: "問題ない", description: "現在の制約事項で運用可能" },
      { label: "変更が必要", description: "制約の見直しが必要" }
    ]
  }]
})
```

**未定義・曖昧部分の詳細化**
- 設計文書で詳細が不明な機能の具体的な動作
- ユーザーの実際の業務フロー・ユースケース
- 入出力データの詳細仕様
- UI/UX の具体的な期待値

**追加・変更要件の特定**
- 既存設計にない新規機能要件
- 外部システム連携の追加需要
- レポート・分析機能等の追加需要
- 運用・メンテナンス要件の追加

**既存機能への影響範囲**
- 新規要件による既存機能への影響
- パフォーマンス要件への影響
- セキュリティ・アクセシビリティ要件への影響
- データ移行・互換性要件

**優先順位・スコープ調整**
複数の要件がある場合、優先順位を質問:
```
AskUserQuestion({
  questions: [{
    question: "以下の要件の優先順位を教えてください（複数選択可）",
    header: "優先順位",
    multiSelect: true,
    options: [ /* 実際の要件リストから動的に生成 */ ]
  }]
})
```

### 軽量開発の場合

**必須項目のみ確認** — 簡潔に質問する:
- 主要な機能要件の確認（3-5項目程度）
- 基本的な制約事項の確認
- 最低限のエラーケース確認
- 優先順位（Must Have のみ）

### カスタム開発の場合

step2 で選択された項目（`custom_items`）に関連するヒアリングのみ実施する。

### ヒアリング記録の作成

すべての質問と回答を記録する。各質問について以下を記録：
- 質問内容
- 質問日時
- カテゴリ（既存設計確認/未定義部分詳細化/追加要件/影響範囲/優先順位）
- 質問の背景（なぜこの質問が必要だったか）
- ユーザーからの回答
- 信頼性への影響（この回答により信頼性レベルがどう変化したか）

ヒアリング結果のサマリー：
- 確認できた事項
- 追加/変更要件
- 残課題
- 信頼性レベル分布（ヒアリング前後の比較）

この記録は step4 で `interview-record.md` として出力する。

- step4 を実行する

## step4: 統合要件定義書の作成

- 作業規模に応じたテンプレートを選択：
  - `"フル機能開発"`: `<full_requirements_template>`
  - `"軽量開発"`: `<minimal_requirements_template>`
  - `"カスタム"`: `<full_requirements_template>` をベースに、step2 で選択された `custom_items` の項目のみ含める

- context の情報でテンプレートを埋めて、以下のファイルを Write ツールで保存する
- **重要**: すべてのファイルのすべての項目に信頼性レベル（🔵🟡🔴）を記載

### 出力ファイル

1. `docs/spec/{要件名}/requirements.md`: 統合機能要件と関連文書へのリンク
   - 選択したテンプレートを使用
   - 各要件に信頼性レベルと出典を記載
   - **性能系 NFR の数値は相場を出どころにする**: NFR は数値必須だが、根拠のない数字を置かない。`beam5-implement/references/ui-performance-verification.md` の **§1（PERF-1〜4）** を読み、Core Web Vitals（LCP < 2.5秒 / CLS < 0.1 / INP < 200ms）・リソース量（JS < 200KB gzip）・API レイテンシ（**平均でなく p50/p95/p99**）を出発点にする（解決順: リポジトリ直下 `.claude/skills/` → `~/.claude/skills/`）。
     - **相場をそのまま写さない**。対象ユーザーの回線・端末・業務性質で妥当値は変わるので、**調整した理由を添えて**書く（例:「対象は社内 PC・有線のため TTFB は 400ms」）。
     - **検証できる形で書く**（指標・条件・数値）。「速いこと」ではなく「一覧画面の LCP が 1000 件のデータで 2.5 秒未満」。条件を欠くと beam5 の実環境検証で判定できない。
     - UI や HTTP API を持たないプロジェクト（CLI・ライブラリ等）では**この項目は非該当**。その旨を一言述べる。
   - **未解決事項の扱い**: PRD・タスクノートに明示がなく信頼性 🔴/🟡 で残った技術選定・アーキ・データ・設定等の決め事は、テンプレートの「**未解決事項（beam3-designで決定）**」表（区分 / 項目 / 信頼性 / 次フェーズでの取扱い）に集約する。該当が無ければそのセクションは省略する

2. `docs/spec/{要件名}/interview-record.md`: ヒアリング記録
   - `<interview_record_template>` を使用
   - step3 の質問と回答を記録
   - 信頼性レベルの変化を記録

3. **フル機能開発の場合のみ追加生成**:
   - `docs/spec/{要件名}/user-stories.md`: 詳細なユーザストーリー
     - `<user_stories_template>` を使用
     - 各ストーリーに信頼性レベルと出典を記載
     - 信頼性レベルサマリーを含める

   - `docs/spec/{要件名}/acceptance-criteria.md`: 受け入れ基準とテスト項目
     - `<acceptance_criteria_template>` を使用
     - 各受け入れ基準・テストケースに信頼性レベルと出典を記載
     - 信頼性レベル分布を含める

4. **カスタムで該当項目が選択されている場合のみ追加生成**:
   - `"詳細なユーザーストーリー"` 選択時: `user-stories.md`
   - `"エッジケースの洗い出し"` または `"パフォーマンス要件"` 選択時: `acceptance-criteria.md`

### 品質判定

作成した要件定義書について以下を評価する:
- 要件の曖昧さの有無
- 入出力定義の完全性
- 制約条件の明確性
- 実装可能性
- 信頼性レベル（🔵🟡🔴の分布） — すべてのファイルを通じて集計

品質判定結果をユーザーに表示する（全ファイル統合の信頼性レベル分布を含む）。

- step4b を実行する

## step4b: ユーザー準備タスクの抽出（prep.md）

step3（ヒアリング）および step4（要件定義書作成）で判明した「ユーザーが事前に用意・実施すべきこと」を別ファイルに書き出す。

### 抽出対象

以下のカテゴリに該当する項目をスキャンし、該当があれば prep.md を生成する。**該当が無ければスキップして step5 へ。**

- **APIキー・トークンの取得**: 外部サービスのAPIキー、OAuthクライアントID/Secret等（取得先URL・手順を添える）
- **外部サービスのアカウント作成・設定**: SaaS契約、サービス登録、プラン選択等
- **環境変数の設定**: 変数名と設定方法、設定先（.env、1Password、k8s Secret等）
- **DNS・ドメイン・証明書の準備**: ドメイン取得、DNS設定、SSL証明書
- **インフラストラクチャの準備**: サーバー構築、DB作成、ストレージバケット作成等
- **第三者への依頼・確認**: 権限申請、利用規約の確認、社内承認フロー等
- **データの準備**: マスターデータ、テストデータ、移行元データの用意
- **ライセンス・法務確認**: OSS ライセンス確認、プライバシーポリシー策定等

### 出力

- `docs/spec/{要件名}/prep.md` に `<prep_template>` を使用して書き出す
- **prep.md が既に存在する場合は上書きしない**。beam3 step5 と同じ3操作（追加🆕/変更✏️/不要化❌）で差分同期し、**チェック済み状態 `- [x]` を必ず保持**する（再実行・スコープ再整列でユーザーの完了作業を消さないため）
- 各タスクに優先度（必須/推奨/確認事項）と信頼性レベル（🔵🟡🔴）を記載
- step4c を実行する

## step4c: スコープ4案マトリクスの作成（scope-options=on の場合のみ）

- 引数に `scope-options=on` が指定されており、かつ**通常モード（要望案の初回生成）**の場合のみ: `Skill(skill="scope-options", args="define {要件名}")` を実行する
  - scope-options が（メインコンテキストで）コアジョブ確認・Kano 確認・マトリクス確認のヒアリングを行い、`docs/spec/{要件名}/scope-options.md`（機能×4案マトリクス。SP なし）を生成する
- `scope-options=off`・未指定・**選択案モード（再整列中）**の場合はスキップする
- step5 を実行する

## step5: 完了報告とTODO更新

- TodoWrite ツールで TODO ステータスを更新する
  - 要件定義フェーズを「completed」にマーク
  - 次のフェーズ「設計文書作成（beam3-design）」をTODOに追加
  - 品質判定結果をTODO内容に記録
  - TODO が存在しない場合は新規作成する

- 完了報告を表示：
  - 収集した既存プロジェクト情報のサマリー
  - step3 でのヒアリング結果と既存情報との差分
  - 作成したファイルのパス一覧（requirements.md, interview-record.md, user-stories.md, acceptance-criteria.md, prep.md のうち実際に生成されたもの）
  - prep.md が生成された場合、ユーザー準備タスクの件数と必須/推奨の内訳を表示
  - 各ファイルの信頼性レベル分布
  - 全体の信頼性レベル分布（すべてのファイルを通じた集計）
  - 既存要件からの変更点・追加点の件数
  - 各ファイル内のリンクが正しく設定されていることを確認
  - 既存設計書・実装との整合性確認を促すメッセージ

- 次のステップ表示: 「次の推奨ステップ: `beam3-design` で技術設計文書を作成します。」

## step6: Git 連携（フェーズブランチへコミット＋スタックド PR）

beam2 が生成した要件定義一式を**フェーズブランチ `beam2-{要件名}`**（前フェーズ `beam1-{要件名}` の上に分岐）へコミットし、**スタックド PR を作成**する（PR にはこのフェーズの生成物のみが入る）。Git 処理は `beam-sync` スキルに委譲する（冪等・秘密情報はコミットしない）。

- `Skill(skill="beam-sync", args="{要件名} beam2")` を実行する
- `beam-sync` が前提未達（`gh` 未認証・git identity 未設定・非 git リポジトリ）を報告した場合は、その案内をユーザーに伝えて**フェーズ自体は完了とする**（Git 連携のみスキップ）
- 結果（ブランチ／コミット／**PR の URL**）の要約をユーザーに伝える
