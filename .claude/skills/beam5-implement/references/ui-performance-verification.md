# UI・性能の検証リファレンス

「実際に動かして確かめる」ときの**目標値**と**手順**。各項目に ID（PERF-1 / QA-1 等）を振る——要件・レポートでは **ID で引用**すること。

## 0. 使い方（最優先）

- **beam2（要件定義）**: **§1 の目標値だけ**を読む。beam2 は「NFR は数値必須」なので、**その数値の出どころ（相場）**として使う。手順（§2）は読まなくてよい。
- **beam5 / power6（実環境検証）**: **§2 の手順**を、既存の「実データ・実環境での動作確認」の**中身**として使う。目標値は §1 を参照する。
- **適用条件（重要・種別で大きく変わる）**:

  | プロジェクト種別 | 該当する項目 | 非該当 |
  |---|---|---|
  | ブラウザ UI を持つ Web アプリ | **全項目** | — |
  | API のみ（UI なし） | PERF-3・QA-1 | PERF-1/2・QA-2〜4 |
  | CLI・ライブラリ・バッチ | （原則なし。必要なら PERF-3 の考え方だけ） | ほぼ全部 |

  **該当しない項目は黙って飛ばさず「なぜ不要か」を一言述べる**。
- **PERF-0 目標値は「相場」であって要件ではない**。対象ユーザーの回線・端末・業務性質で妥当値は変わる。**NFR には相場をそのまま写すのではなく、根拠を添えて数値を決める**（例:「対象は社内 PC・有線のため TTFB は 400ms を目標」）。
- **プロジェクト固有規約（CLAUDE.md・note.md・既存の SLA）が常に優先**する。

## §1. 性能目標（PERF-*）— beam2 が NFR の数値を決めるときの相場

- **PERF-1 Core Web Vitals（ユーザーの体感速度）** — ブラウザ UI がある場合の標準指標。

  | 指標 | 目標 | 何を表すか |
  |---|---|---|
  | **LCP**（Largest Contentful Paint） | < 2.5 秒 | 主要コンテンツが見えるまで |
  | **CLS**（Cumulative Layout Shift） | < 0.1 | 表示中のガタつき（誤タップの原因） |
  | **INP**（Interaction to Next Paint） | < 200 ms | 操作してから反応するまで |
  | FCP（First Contentful Paint） | < 1.8 秒 | 最初の描画まで |
  | TTFB（Time to First Byte） | < 800 ms | サーバー応答の速さ |

  - 上3つ（LCP・CLS・INP）が中核。FCP・TTFB は原因切り分け用の補助指標。

- **PERF-2 リソース量** — 体感速度の主因になりやすいので、指標と別に上限を決めておく。

  | 対象 | 目安 |
  |---|---|
  | 総ページ重量 | < 1 MB |
  | JS バンドル | < 200 KB（gzip 後） |
  | 画像・サードパーティスクリプト | 個別に把握し、増えたら気づける状態にする |

- **PERF-3 API レイテンシはパーセンタイルで測る（平均を使わない）** — **p50 / p95 / p99** を記録する。平均は少数の極端に遅い応答を隠してしまい、「大半は速いが一部の利用者だけ極端に遅い」状態を検出できない。
  - 出発点の目安: 対話的な操作は **p95 < 500 ms**、バックグラウンド処理はこの限りでない。
  - 測り方は QA-5 を参照。
- **PERF-4 目標値は「守れているか」を後から測れる形で書く** — NFR に「速いこと」ではなく「指標・条件・数値」を書く（例: 「一覧画面の LCP が、1000 件のデータで 2.5 秒未満」）。条件（データ量・回線）を欠くと検証不能になる。

## §2. 検証手順（QA-*）— beam5 / power6 の実環境確認の中身

上から順に実施する。**前段が落ちたら後段は意味がない**ので、失敗した時点で報告して先へ進まない。

- **QA-1 スモーク（起動して壊れていないか）** — UI の有無に関わらず最初に行う。
  - アプリを起動し、対象 URL / 主要エンドポイントに到達できる。
  - **コンソールエラーが出ていない**（アナリティクス等サードパーティ由来のノイズは除外して判断する）。
  - **4xx / 5xx のネットワークリクエストが無い**。
  - UI があれば、デスクトップとモバイルのファーストビューを1枚ずつ確認する。
- **QA-2 インタラクション（主要導線が実際に動くか）** — 「表示された」で終わらせない。
  - 主要なユーザージャーニー（要件の US-* に対応するもの）を最初から最後まで通す。
  - フォームは**正常系と異常系の両方**を送る（無効値でエラー表示が出るか）。
  - 認証があれば「ログイン → 保護ページ → ログアウト」を通す。
  - ナビゲーションのリンク切れが無い。
- **QA-3 レスポンシブ・表示崩れ** — **375 / 768 / 1440 px** の3ブレークポイントで主要画面を確認する。
  - 要素のはみ出し・重なり・欠落が無い。横スクロールが発生していない。
  - ダークモードがあるなら、同じ観点で一通り見る。
  - 変更前のスクリーンショットがあるなら差分を比べる（意図しないレイアウト変化の検出）。
- **QA-4 アクセシビリティ** ★ — 見落とされやすいが、後付けの修正コストが最も高い領域。
  - **axe-core 等の自動チェックを実行**し、**WCAG 2.1 AA 違反**を洗い出す（コントラスト比・フォームのラベル・見出し階層・ランドマーク）。
  - **キーボードだけで主要導線を完走できる**（Tab の順序が視覚順と一致・フォーカスリングが見える・モーダルからフォーカスが逃げない・Esc で閉じる）。
  - 画像の代替テキスト、アイコンのみのボタンのアクセシブル名。
  - ※ 自動チェックは「機械的に判定できる違反」しか出ない。**キーボード操作だけは必ず手で通す**。
- **QA-5 性能の実測** — §1 の目標値と突き合わせる。
  - **ページ**: 主要画面で PERF-1 の指標と PERF-2 のリソース量を測る。
  - **API**: 主要エンドポイントに**繰り返しアクセス**して p50 / p95 / p99 を出す（単発の計測は当てにならない）。必要なら同時実行も試す。
  - 目標未達なら、**数値と条件をそのまま報告**する（「遅い」ではなく「LCP 4.1 秒 / 目標 2.5 秒」）。

### 実行環境（どれで測るか）

| 環境 | 手段 |
|---|---|
| DevContainer 内（beam5・power6 の通常） | **Playwright**（テンプレの post-create で Chromium 導入済み） |
| ホスト側から確認する場合 | ブラウザ操作系の MCP ツール |
| どちらも使えない | **自動検証はできていないと明記**し、人間が手で確認する手順を提示する（黙って「確認済み」にしない） |

## 収録しない／参照に留めるもの（基準ドリフト防止）

- **セキュリティヘッダー・CSP・CSRF・トークン保存先** → `ai-security-guardrails.md`（P1）。QA で気づいても基準はそちら。
- **バンドルを生む側の設定（クリーンビルド・警告・生成物）** → `build-hygiene.md`（V 群・T 群）。本書は**出来上がったものを測る**側。
- **「テスト全通過 ≠ 動く」という原則そのもの** → beam5 / power6 の本体に既にある。本書はその**確認手順**を与えるだけ。
- **API の設計（ステータスコード・ページネーション等）** → `api-design.md`。本書は**速度**だけを見る。
