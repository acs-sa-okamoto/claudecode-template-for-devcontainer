あなたは実装フェーズのオーケストレーター（ディスパッチャ）です。**自分でコードを大量に書くのではなく**、beam4 が分解したタスクをフェーズ単位でサブエージェントに委譲し、結果サマリーだけを集約します。これによりメインコンテキストの肥大化を防ぎます。

# context

- 要件名: `{要件名}` （step1 で確定）
- タスクディレクトリ: `docs/tasks/{要件名}/`
- 設計ディレクトリ: `docs/spec/{要件名}/design/`
- タスクDB: `data/tasks.db`（テーブル名 = `{要件名}`）
- 実装インデックス: `docs/tasks/{要件名}/code-map.md`
- 実装ターゲット: `{ターゲット}` （引数。後述のとおり解釈）

# 変数表記の凡例

- `{要件名}` は step1 で確定する変数。実際のパス生成時には具体値に置換する。
- `{ターゲット}` は引数。空 / `TASK-XXXX` / `Phase N` のいずれか。

# 引数（実装ターゲット）の解釈

| 引数 | 動作 |
|---|---|
| 空、または作業規模キーワード（"フル機能開発" 等） | 残りの全フェーズを順に実装（フル実行） |
| `TASK-XXXX`（例: `TASK-0003`） | 当該タスク1件のみ実装 |
| `Phase N`（例: `Phase 2`） | 当該フェーズのみ実装 |

> オーケストレーター（beam）から呼ばれる場合は作業規模が渡されるため、フル実行として扱う。

# 設計思想（重要）

- **会話の記憶ではなく、ファイル（コード＋契約＋code-map）を state とする。**
- **フェーズ単位でサブエージェントを起動**し、フェーズ境界でコンテキストをリセットする。
- フェーズ内タスクは同一コンテキストで実装するため一貫性が保たれる。
- フェーズ間の知識は `code-map.md`（現状インデックス）と設計契約で引き継ぐ。
- セキュリティ（P0）は記憶に頼らず、各サブエージェントが `docs/rule/ai-security-guardrails.md` を毎回読み込んで遵守する。

# 呼び出しモデル（重要）

- **新しいコンテキストでの実行を推奨**: 本スキルは note.md / requirements.md / design/* / tasks.db / TASK-*.md など**ファイルからすべての状態を読み直す**ため、beam1〜4 の会話履歴は不要。beam（オーケストレーター）でタスク分解まで終えた後は、**`/clear`（または新しいセッション）でコンテキストをリセットしてから** `/beam5-implement` を実行すると、ディスパッチャ本体が最も軽量に保たれる。
  - ※ リセット前に、beam4 までの生成物（要件・設計・タスク・tasks.db）が**ファイルに保存済み**であることを確認する。
- 本スキルは**ディスパッチャ**として、呼び出し元コンテキスト（通常はメイン）で動作し、自前でフェーズ実装サブエージェントを起動する。
- そのため**サブエージェントでは包まない**。`/beam5-implement` で**直接**起動する（オーケストレーター `beam` の対象外。実装は個別実行）。
- ディスパッチャ本体は軽量（フェーズサマリーと code-map の調整のみ）に保ち、重い実装は各フェーズサブエージェントに委譲する。
- フェーズ実装サブエージェントは**非対話**で動かす。実装に必要な判断は beam1〜4 で確定済みであることが前提。サブエージェント内では AskUserQuestion はユーザーに届かないため、判断が要る場合は処理を中断してディスパッチャ（メイン）に差し戻し、メインで AskUserQuestion を行う。

## step1: 準備（ディスパッチャ初期化）

- **要件名の確定**
  - Bash で `pwd` を実行し、basename をプロジェクトルートディレクトリ名として取得し `{要件名}` とする

- **専用ルールの読み込み**
  - スキルディレクトリ内の `rules/rules.md` を読み込む

- **規約・制約の読み込み**
  - `CLAUDE.md`（技術スタック・コーディング規約・コマンド・DoD）
  - `docs/rule/ai-security-guardrails.md`（**セキュリティ P0/P1**。存在する場合は必読）
  - `docs/rule/` 配下のその他ルール

- **コンテキストの読み込み**
  - `docs/spec/{要件名}/note.md`（技術スタック・関連実装・注意事項）
  - `docs/spec/{要件名}/requirements.md`（要件）
  - `docs/spec/{要件名}/design/architecture.md`（プロジェクト構造・実装先の判断材料）
  - `docs/spec/{要件名}/design/` の契約（`interfaces.ts` / `database-schema.sql` / `api-endpoints.md` / `dataflow.md`）が存在する場合は把握

- **タスク情報の読み込み**
  - `docs/tasks/{要件名}/overview.md`（フェーズ構成・依存・クリティカルパス）
  - **タスクDBの確認**:
    - Bash で `sqlite3 -version` を確認
    - 利用可能なら `data/tasks.db` の `"{要件名}"` テーブルから全タスクの `phase / task_id / status / blocked_by / task_type / task_file` を取得
    - 利用不可なら `overview.md` と `TASK-*.md` をファイルベースで読み、status は管理しない（フォールバック）

- **実装インデックスの読み込み**
  - `docs/tasks/{要件名}/code-map.md` が存在すれば読み込む（前回までの実装状況）。無ければ step3 の初回フェーズで新規作成する

- **整合ドリフトの確認（git 管理下の場合・warn）**
  - 仕様・設計（`docs/spec/{要件名}/`）の最終コミットが、下流成果物（`docs/tasks/{要件名}/`・`src/`）の最終コミットより新しい場合（未コミット変更は「最新」扱い・両方に触れた同一コミットは除外）、**上流だけが改定され下流が未追随の疑い**として警告し、**先に `/revise` の実行を提案**する（実行は継続可）

- **引数の解釈**: 上記「引数の解釈」に従い `{ターゲット}` を確定する

- 読み込み内容（要件名・対象フェーズ・既存実装の有無）をまとめてユーザに宣言し、step2 を実行する

## step2: 実行計画の決定

- **対象タスクの抽出**
  - タスクDBがある場合: `status != 'done'` かつ `is_deleted = 0` のタスクを対象とする
  - `{ターゲット}` が単一タスク/単一フェーズ指定の場合は、その範囲に絞る

- **順序の決定**
  - フェーズ順（Phase 1 → 2 → ...）に並べる
  - フェーズ内は `blocked_by`（依存）を解決し、依存の無いものから順に並べる
  - **依存の前提タスクが未 `done` の場合は警告**し、AskUserQuestion で「依存を先に実装 / このまま続行 / 中止」を確認

- **実行計画の表示**
  - 実装予定のフェーズとタスク一覧、各タスクの `task_type`（TDD/DIRECT）を表示
  - 既に `done` のタスクはスキップする旨を表示（再開可能性）

- AskUserQuestion で実行可否を確認（「実行する / 中止」）。"実行する" なら step3 へ

## step3: フェーズ実装ループ（★フェーズ境界でコンテキストリセット）

対象フェーズを順番に実装する。**各フェーズを `beam5` 自身ではなくサブエージェントに委譲**する。

### 各フェーズの処理

1. **DBステータス更新**: 当該フェーズのタスクを `status = 'in_progress'` に更新（タスクDBがある場合）

2. **TodoWrite 更新**: 「Phase N 実装中」をTODOに反映

3. **フェーズ実装サブエージェントの起動**（Task ツール）
   - 1フェーズ = 1サブエージェント（fresh context）
   - プロンプトに以下を**過不足なく**含める（サブエージェントは追加のコンテキスト収集を最小化できるようにする）:

   ```
   あなたは実装担当エンジニアです。以下のフェーズの全タスクを実装してください。

   ## 厳守事項
   - セキュリティ: docs/rule/ai-security-guardrails.md を読み、P0 を必ず遵守する。
     適用しない規則は理由を一言述べる。P0 違反は実装完了とみなさない。
   - コーディング規約: CLAUDE.md と docs/spec/{要件名}/note.md に従う。
   - 設計契約: docs/spec/{要件名}/design/ の interfaces.ts / database-schema.sql /
     api-endpoints.md を遵守する。実装で契約変更が必要なら、該当ファイルを更新し理由を記録する。

   ## 実装前に把握すること
   - docs/tasks/{要件名}/code-map.md（既存実装の現状インデックス。重複実装を避ける手がかり）
   ※ 各タスクの詳細（TASK-XXXX.md・要件・設計契約）は、下記の実装スキルが自身で読み込むため、ここで全文を抱える必要はない。

   ## 対象タスク（依存順）
   - {TASK-XXXX のリストと、各 task_id・task_type・依存}

   ## 実装手順（タスクごとに Skill ツールで実装スキルを呼ぶ）
   各タスクを依存順に1件ずつ、task_type に応じて実装スキルで実装する:
   - task_type = TDD:    Skill(skill="tdd-implement",   args="{要件名} {TASK-ID}")
   - task_type = DIRECT: Skill(skill="direct-implement", args="{要件名} {TASK-ID}")
   これらのスキルが Red→Green→Refactor→完全性検証（TDD）/ setup→verify（DIRECT）まで実行し、
   テスト・実装・記録（docs/implements/{要件名}/{TASK-ID}/）・tasks.db の status 更新を行う。
   1タスク完了（返却サマリー受領）後に次のタスクへ進む。未達なら理由を記録して次へ（または中断）。
   ※ このサブエージェントは **Skill ツール**を使えること。実装の詳細手順は各実装スキルに委ねる。

   ## フェーズ完了時
   - フェーズ全体で build / 全test / typecheck / lint を実行し、すべて通す
   - **要件カバレッジ確認**: 各タスクがカバーする受け入れ基準・要件が 1:1 でテスト化されているか（列挙は全項目アサート）を確認し、テスト未対応の AC/REQ があれば報告する
   - 失敗が残る場合は原因と対処を報告に含める

   ## 返却（簡潔に。実装コードの全文は貼らない）
   - 実装/変更したファイルのパス一覧
   - 新規に公開した主要シンボル（関数・型・クラス）とファイル
   - 確立した規約・再利用ポイント（後続フェーズへの申し送り）
   - 設計契約を変更した場合はその内容と理由
   - test/typecheck/lint の結果（成功/失敗）
   - 担当タスクの AC/REQ カバレッジ（テスト未対応の項目があれば一覧）
   - P0 遵守状況（適用外とした規則があれば理由）
   - 各タスクの完了状況（完了/未完了とその理由）
   ```

4. **サマリーの受領・レビュー・反映**
   - サブエージェントから受け取ったサマリー（実装/変更ファイル一覧・公開シンボル・test/lint 結果・カバレッジ・P0 遵守状況）を確認する
   - **コードレビュー・ゲート（`/code-review`）★終了条件 = CRITICAL/HIGH ゼロ**: このフェーズで実装したコードを、`beam-sync` で PR 化する**前に**レビューする（`power6-verify` のレビューループと同じ方式）。**最大2ラウンド**:
     1. `Skill(skill="code-review")`（引数なし＝ローカル変更）を実行する。**この時点でフェーズの変更は未コミット**（beam-sync 未実行）なので、レビュー対象はこのフェーズの差分になる。生成レポートを読み、**反証されていない CRITICAL/HIGH** を抽出する。前フェーズは自分のフェーズブランチにコミット済み・各フェーズで対応済みのため、**このフェーズが変更したファイル**（サブエージェントの返却ファイル一覧）の指摘に注目する。
     2. CRITICAL/HIGH があれば**修正**する（直接 Edit、または集中サブエージェント Task に委譲）。修正後 build / 全test / typecheck / lint を再実行して green を確認する。
        - **修正には再発防止テストを添える**: 直した不具合に対して、**それを検知するテストを1本書く**。テスト名に対象を明示する（coding-principles の E-1〜E-4 に該当するなら `E-1 リグレッション: …` のように ID を含める）。カバレッジ率を上げるためではなく、**同じ盲点の再発を機械的に止めるため**——AI は同じ種類のミスを繰り返すので、一度テストで固定すればその形の再発は起きなくなる。
     3. **修正差分に絞って再レビュー**（フルスキャンしない＝ノイズ・非決定性を抑える）。
     - 終了条件は **CRITICAL/HIGH = 0**（指摘ゼロではない）。残る LOW/MEDIUM は「既知・許容」としてこのフェーズのサマリーに記録する（人間の最終判断に委ねる）。
     - ※ code-review は P0/P1・coding-principles（H/I）・build-hygiene（L）を自前で読み込むため、beam5 側の準備は不要。差分が `package.json`・設定・CI・`.devcontainer` 等を触る場合は観点 L も自動で効く。
     - **★順序を入れ替えないこと（機械的検査が先）**: このゲートに入る時点で、サブエージェントが build / 全test / typecheck / lint を通して green にしている。**AI が書いたコードを同じ AI がレビューすると同じ盲点が入る**ため、レビューは機械的検査の**代わりにはならない**。必ず「機械的検査 green → AI レビュー」の順で回し、テストが赤いままレビューに進まない。
   - レビュー後の最終コードを `code-map.md` に反映する（新規/変更モジュールの「責務・公開シンボル・規約・申し送り」を `<code_map_template>` の形式で**現状インデックスとして上書き更新**。履歴は残さない）
   - タスクDB更新: 完了タスクを `status = 'done'`、`update_badge = 1` に更新（未完了タスクは `status = 'in_progress'` のまま残し、理由を記録）
   - フェーズサマリー（実装内容＋**レビュー結果: CRITICAL/HIGH=0、残 LOW/MEDIUM {n} 件**）をユーザーに簡潔に表示
   - **Git 連携（実装フェーズごとに別 PR）**: `Skill(skill="beam-sync", args="{要件名} beam5-phase{現在のフェーズ番号}")` を実行し、当該実装フェーズの**レビュー済み**成果（`src` / `tests` / `docs/implements` / `code-map.md`）を**フェーズブランチ `beam5-phase{N}-{要件名}`**（前フェーズの上に分岐）へコミットし、**スタックド PR を作成**する（実装フェーズごとに別 PR）。`beam-sync` が前提未達（`gh` 未認証等）を報告したら、その案内を伝えてフェーズは続行する
     - **実装フェーズの PR は、全フェーズ完了・検証まではマージしない**（スタックに保持したまま積み上げ、最後に `gh stack merge` でアトミックに落とす）。こうすることでトランクが「機能が半分だけ入った状態」を経由せず、**常にリリース可能**に保たれる

5. **エラー/未完了時**
   - フェーズ内に未完了・失敗があれば、内容を表示し AskUserQuestion で「再試行 / 次フェーズへ進む / 中止」を確認

6. 次フェーズへ（→ サブエージェント破棄＝コンテキストリセット）

- 全フェーズ完了後、step4 を実行

## step4: 統合チェックと完了報告

- **最終統合チェック**
  - プロジェクト全体で build / 全test / typecheck / lint を実行（CLAUDE.md のコマンドを使用）
  - すべて通ることを確認。失敗があれば一覧化

- **実データ・実環境での動作確認（必須）**

  > **重要な原則**: **「テスト全通過 ≠ 動く」**。ユニットテストは*想定した*スキーマ・入力に対して書かれているため、
  > 実際の外部データ（既存DB・外部API・実ファイル）の*本当の形*と乖離していても全部 green になりうる。
  > テストだけで完了とせず、**実データ・実環境で主要フローを実際に動かして確認する**こと。

  - **確認の中身は `<ui_perf_ref>`（`references/ui-performance-verification.md`）の §2 に従う**——QA-1 スモーク（起動・コンソールエラー・4xx/5xx）→ QA-2 主要ジャーニー（正常系＋異常系）→ QA-3 レスポンシブ（375/768/1440px）→ **QA-4 アクセシビリティ（WCAG AA・キーボードだけで完走）** → QA-5 性能実測（LCP/CLS/INP・API の p50/p95/p99）。**種別に応じて非該当の項目は理由を一言述べてスキップ**する（API のみなら QA-1 と性能だけ、CLI・ライブラリなら本節そのものが原則非該当）。
    - 実行手段は DevContainer 内の **Playwright**（post-create で Chromium 導入済み）。使えない場合は**「自動検証できていない」と明記**し、人間向けの手動確認手順を示す（黙って「確認済み」にしない）。
  - 実際にアプリを起動し（CLAUDE.md の起動コマンド）、主要なエンドポイント／画面が**実データで期待どおり動く**ことを確認する
    - 例: サーバーを起動して主要 API を実際に叩き、空でない正しい応答が返るか
    - 例: 既存DB・外部入力を読む機能は、**実際のソース（モックでない）**に対して動かす
  - **外部データソース（既存DB・他システムの出力等）を読む実装は特に注意**:
    - 実際のスキーマ（テーブル名の命名規則・列の型・ID の表現）と、実装側の前提が一致しているか実物で確認する
    - 例: 識別子の文字種（ハイフン等）、ID が数値か文字列か、列の有無
  - 不一致を見つけたら、テストではなく**実物に合わせて実装（および設計契約）を修正**する

- **要件適合ゲート（最終・必須）**

  > beam4 のカバレッジ行列（タスクの有無）と TDD/DIRECT の AC→テスト対応（タスク内の充足）を経ても、
  > 「全要件が最終成果物で実際に満たされているか」は別問題。実装完了時に**要件単位で突き合わせる最終ゲート**を必ず通す。

  - `docs/spec/{要件名}/requirements.md` と `docs/spec/{要件名}/acceptance-criteria.md` を**再読**する
  - **すべての要件 ID（REQ-*・NFR-*。EDGE-* も推奨）**について、最終成果物が満たすかを判定し**根拠**を添える:
    - ⭕ **満たす**: 根拠を必ず示す（テスト名 / 実装ファイル:行 / 実機での確認結果のいずれか）
    - ❌ **未達**: 満たせていない（根拠を示せない場合も未達とみなす）
    - 🟢 **タスク不要（N/A）**: beam4 4.8 で正当化済みの要件を理由付きで再掲
