# rules

## ファイル・出力のルール

### 実装コードの出力先

- 実装コードの配置は**プロジェクトの構造に従う**（`CLAUDE.md` / `docs/spec/{要件名}/design/architecture.md` / `note.md` のディレクトリ構造を参照）
- 典型例: `src/`（実装）、`tests/` または各ソースに併設（テスト）
- **新しい構造を勝手に作らず**、既存・設計済みの構造に合わせる

### 管理ファイルのパス

- 実装インデックス: `docs/tasks/{要件名}/code-map.md`
- タスクDB: `data/tasks.db`（テーブル名 = `{要件名}`、beam4 が作成）

### ファイルパスの記載ルール

- **プロジェクトルートを基準とした相対パスを使用する**（絶対パス禁止）
- 例: ❌ `/Users/name/app/src/x.ts` → ✅ `src/x.ts`

## code-map.md の運用（フェーズ間の知識引き継ぎ）

- **現状インデックスのみ**を保持する（実装の履歴・ログは残さない）
- 各フェーズ完了時に、新規・変更されたモジュールのエントリを**上書き更新**する
- 1エントリは高シグナルに保つ: ファイルパス / 責務 / 公開シンボル / 規約 / 後続への申し送り
- 新フェーズのサブエージェントは**実装前に必ず code-map.md を読む** → 既存の公開関数・型を再利用し、重複実装を避ける（**ただし偶然の一致まで共通化しない**。coding-principles の C-2 DRY と C-3 AHA / C-4 Rule of Three の張力で判断する）

## タスクステータスの管理（タスクDB）

`data/tasks.db` の `"{要件名}"` テーブルの `status` を更新しながら進める。

| status | 意味 | 遷移 |
|---|---|---|
| `ready` | 未着手・実装可能 | 開始時 → `in_progress` |
| `in_progress` | 実装中 | 完了 → `done` / 失敗 → 据え置き |
| `in_review` | レビュー待ち（任意。人間レビューに回す場合） | レビュー後 → `done` |
| `done` | 完了 | — |

- 完了時は `status = 'done'`、`update_badge = 1`（Notion 未同期フラグ）に更新
- 日時更新は不要（トリガーで `updated_at` が自動更新される。明示する場合は JST = `datetime('now', '+9 hours')`）
- **再開可能性**: 再実行時は `status = 'done'` のタスクをスキップし、未完了から再開する
- `sqlite3` が使えない環境では status 管理を省略し、`overview.md` のチェックボックスで進捗を管理する（フォールバック）

## タスクタイプ別の実装プロセス（実装スキルに委譲）

beam4 が各タスクに付与した `task_type` に従い、**専用の実装スキルを `Skill` ツールで呼び出す**（実装方法論はそのスキルに集約）。

| task_type | 呼び出すスキル | 内部フロー |
|---|---|---|
| **TDD** | `tdd-implement` | tasknote→requirements→testcases→Red→Green→Refactor→完全性検証 |
| **DIRECT** | `direct-implement` | setup→verify |

呼び出し例（フェーズ実装サブエージェント内）:

```
Skill(skill="tdd-implement",   args="{要件名} {TASK-ID}")   # TDD タスク
Skill(skill="direct-implement", args="{要件名} {TASK-ID}")  # DIRECT タスク
```

- 各実装スキルが、テスト・実装・記録（`docs/implements/{要件名}/{TASK-ID}/`）・`tasks.db` の status 更新まで担う
- beam5 側は「どのタスクをどの順で実装スキルに渡すか」の**オーケストレーション**に専念する
- フェーズ実装サブエージェントは **Skill ツール**を使える状態で起動すること

## セキュリティ（P0 厳守）

- 各フェーズ実装サブエージェントは `docs/rule/ai-security-guardrails.md` を読み込み、**P0 を必ず遵守**する
- 適用しないと判断した規則は、黙って飛ばさず「なぜ不要か」を一言述べる
- セキュリティ要件と機能要件が衝突する場合は、勝手に決めず人間に確認する
- **P0 違反は実装完了とみなさない**

## コードレビュー・ゲート（各実装フェーズ）

各実装フェーズは、`beam-sync` で PR 化する**前に** `/code-review` を通す（`power6-verify` と同じ方式。実装エンジン `tdd-implement`/`direct-implement` ではなく、フェーズ単位のオーケストレーション層＝beam5 のゲートとして行う）。

- **終了条件は「CRITICAL/HIGH = 0」**（指摘ゼロではない）。`/code-review` は LLM 推論ベースで非決定的・主観指摘が尽きないため、ゼロまでループしない。残る LOW/MEDIUM は「既知・許容（人間判断）」として記録する。
- 修正は**最大2ラウンド**。再レビューは**修正差分に絞る**（フルスキャンしない）。
- レビュー対象はそのフェーズの差分（beam-sync 前なので未コミット＝当該フェーズ）。code-review が P0/P1・coding-principles（H/I）・build-hygiene（L）を自前で読み込むため、beam5 側の準備は不要。
- **AI は最終承認者ではない**: レビュー・修正まで行うが、マージ判断は人間。

## Definition of Done（完了条件）

各タスク・各フェーズ・全体で以下を満たして「完了」とする。

- [ ] 対象タスクの完了条件を満たしている
- [ ] test・typecheck・lint がすべて成功している
- [ ] **実データ・実環境で主要フローが動作することを確認した**（「テスト全通過 ≠ 動く」。ユニットテストは想定スキーマに対して書かれているため、実際の外部データ・既存DB・外部APIの本当の形に対して実際に動かして確認する）
- [ ] **P0 セキュリティ要件に違反していない**（P1 逸脱がある場合は理由を明記）
- [ ] **各実装フェーズで `/code-review` を通し CRITICAL/HIGH = 0**（残 LOW/MEDIUM は既知・許容として記録）
- [ ] code-map.md が最新化されている
- [ ] 設計契約（interfaces.ts 等）と実装が整合している（変更時は契約側も更新）

> **AI 生成コードは人間がレビューし、最終責任を持つ。AI は最終承認者ではない。**

## 設計契約との整合

- `docs/spec/{要件名}/design/` の `interfaces.ts` / `database-schema.sql` / `api-endpoints.md` を実装の契約として扱う
- 実装過程で契約変更が必要になった場合:
  - 該当する設計ファイルを更新する
  - 変更内容と理由を完了報告・code-map.md に記録する
  - 既に実装済みの依存箇所への影響を確認する
