# 機能要求定義書（Feature Requirements）出力テンプレート

このファイルは `power1-scope` スキルが `feature-requirements.md` を生成する際に参照する書式・記法・必須項目の定義です。後続の power 工程（理解→設計→実装→検証）が機械的に読める構造化ドキュメントを作るため、以下を厳密に守ること。

**PRD（product-requirements.md）との違い**: プロダクト全体ではなく **既存システムへの「追加」** を記述する。① プロダクト全体の項目（全体ビジョン・ターゲット全体・予算/KPI）は **落とす**。② ブラウンフィールド特有の項目（**統合点・回帰リスク・既存制約・データ変更**）を **必須化**する。

> インタビューの進め方（起点・質問順序・情報源の使い分け・完了条件）は `SKILL.md` 側に定義。本ファイルは **記法と出力フォーマット** に専念する。

---

## 1. 記法ルール（必須）

### 1.1 ID付与ルール

各要件には以下の規則でIDを付ける。連番（ゼロパディング2桁）で一意に振る。

| 種類 | プレフィックス | 例 | 備考 |
|------|--------------|-----|------|
| 機能要件（Functional Requirement） | FR- | FR-01 | PRD と共通 |
| 非機能要件（Non-Functional Requirement） | NFR- | NFR-01 | PRD と共通 |
| ユーザーストーリー（User Story） | US- | US-01 | PRD と共通 |
| 受け入れ条件（Acceptance Criteria） | AC- | AC-01 | PRD と共通 |
| **統合点（Integration point）** | INT- | INT-01 | **機能追加で新設** |
| **回帰リスク（Regression risk）** | REG- | REG-01 | **機能追加で新設** |
| **既存制約（Constraint）** | CON- | CON-01 | **機能追加で新設** |

> INT / REG / CON は下流（設計・タスク分解・コードレビュー）が参照するアンカーになる。例: 設計時に「INT-02 の API に接続」、検証時に「REG-01 が壊れていないか確認」。

### 1.2 優先度ラベル（MoSCoW）

FR・NFR・US には必ず優先度ラベルを付ける:

- `[Must]` 必須。これがないと機能として成立しない
- `[Should]` 重要。あった方がよいが初期リリースは可能
- `[Could]` できれば
- `[Won't]` 今回はやらない（スコープ外と同義）

### 1.3 信頼性レベル（必須・Beam 準拠）

全項目に信頼性レベルを付す:

- 🔵 **確実**: ユーザーが明言した、または事実として確認済み
- 🟡 **妥当な推測**: 文脈からの推測。確認が望ましい
- 🔴 **推測**: 仮説。要確認

### 1.4 情報源タグ（機能追加特有・重要）

各項目の **出所** を明示する。ブラウンフィールドでは「誰が言ったのか／どこから来たのか」が品質に直結する。

- `[U]` … ユーザー発言 or 元ドキュメント由来
- `[C]` … **コード探索**で AI が調べて記載

ルール:
- **`[C]` で埋めた項目は原則 🟡（ユーザー未確認）** とする。ユーザーが追認したら 🔵 に上げる。
- これにより「AI がコードから推測した統合点」と「ユーザーが明言した要件」が一目で区別でき、確認すべき箇所が明確になる。

### 1.5 各記述の書式

```
US:  **US-NN** [優先度] As a <誰>, I want <何>, so that <価値>
       - 受け入れ条件: AC-XX, AC-YY
AC:  **AC-NN**: <タイトル>
       - Given <前提> / When <操作・イベント> / Then <期待結果>
FR:  **FR-NN** [優先度] 🔵[U] <一文でできることを記述>
NFR: **NFR-NN** [優先度] 🔵[U] <測定可能な定量条件>
INT: **INT-NN** 🟡[C] <接続先（既存モジュール/API/画面/データ）> — <接続の仕方・方向>
REG: **REG-NN** 🟡[C] <影響しうる既存機能> — <壊さないための条件／確認方法>
CON: **CON-NN** 🔵[U] <継承する制約（スタック/規約/データモデル/認証/性能 等）>
```

### 1.6 非機能要件・受け入れ条件は計測可能な数値で

「速い」「安全」などの曖昧表現は禁止。必ず数値・基準を含める。不明ならユーザーに聞き直す。

## 2. 出力テンプレート

以下のテンプレートに従って `docs/spec/{機能名}/feature-requirements.md` を生成する。`[...]` は実際の内容で置き換える。

````markdown
# 機能要求定義書（Feature Requirements）

**機能名（Feature Name）:** [kebab-case-name]
**対象プロダクト / リポジトリ:** [repo 名 / プロダクト名]
**作成日:** YYYY-MM-DD
**バージョン:** 1.0
**参照ソース:** [元ドキュメント / Issue / 会話へのリンク。なければ「なし（ユーザー直接入力）」]

---

## 1. 機能の目的・背景（なぜ追加するか）

[この機能を「今」追加する理由・トリガーを2〜3文で。プロダクト全体のビジョンではなく、この追加の動機に絞る]

**見本:**
> 既存のタスク一覧アプリに CSV エクスポート機能を追加する。月次報告のために手作業でタスクをコピペしている運用を自動化し、報告準備の時間をゼロにすることが目的。トリガーは月次報告業務の負荷が顕在化したこと。

---

## 2. ユーザーストーリー

- **US-01** [Must] 🔵[U] As a <誰>, I want <何>, so that <価値>
  - 受け入れ条件: AC-01

**見本:**
- **US-01** [Must] 🔵[U] As a レポート担当者, I want 表示中のタスク一覧を CSV で出力したい, so that 月次報告にそのまま貼れる
  - 受け入れ条件: AC-01, AC-02

---

## 3. 受け入れ条件

書式: Given-When-Then

**見本:**

**AC-01**: CSV エクスポートの実行
- **Given** タスク一覧画面が表示されている
- **When** 「CSVエクスポート」ボタンを押す
- **Then** 表示中の全タスクが UTF-8 (BOM付き) の CSV としてダウンロードされる

**AC-02**: エクスポート対象の範囲
- **Given** フィルタが適用された一覧が表示されている
- **When** エクスポートを実行する
- **Then** フィルタ後に表示されているタスクのみが出力される

---

## 4. 機能要件（FR）

書式: `**FR-NN** [優先度] {信頼性}{情報源} <一文>`

**見本:**
- **FR-01** [Must] 🔵[U] ユーザーは一覧画面から CSV エクスポートを実行できる
- **FR-02** [Must] 🔵[U] エクスポートは現在表示中（フィルタ適用後）のタスクを対象とする
- **FR-03** [Should] 🟡[U] 出力カラムは一覧の表示カラムと一致させる

---

## 5. 非機能要件（NFR）※この機能で増える分のみ

> 既存プロダクトから継承する NFR は再掲しない。**この機能の追加で新たに必要になる**性能・上限などだけを数値で書く。

**見本:**
- **NFR-01** [Must] 🔵[U] 1,000 件のエクスポートを 3 秒以内に完了する
- **NFR-02** [Should] 🔵[U] 文字コードは Excel で文字化けしない UTF-8 (BOM付き) とする

---

## 6. 統合点・依存する既存機能（INT）★ブラウンフィールド必須

> この機能が **接続・依存する既存のモジュール / API / 画面 / データ**。多くは AI がコード探索で候補を挙げ（`[C]` 🟡）、ユーザーが追認する（🔵 に昇格）。

**見本:**
- **INT-01** 🔵[C] `src/web/taskList.tsx`（既存のタスク一覧コンポーネント） — エクスポートボタンをこの画面に追加する
- **INT-02** 🟡[C] `src/db/taskRepo.ts:listTasks()` — 表示中タスクの取得に既存の取得関数を再利用する（フィルタ条件を引き回す）
- **INT-03** 🟡[C] 既存の SQLite スキーマ `tasks` テーブル — 読み取りのみ。書き込み・変更はしない

---

## 7. 既存の振る舞いへの影響・回帰リスク（REG）★ブラウンフィールド必須

> この変更で **壊れうる既存機能** と、**壊さないための条件／確認方法**。Phase4 の回帰検証の入力になる。

**見本:**
- **REG-01** 🟡[C] 一覧の描画パフォーマンス — ボタン追加でレンダリングが重くならないこと（既存の表示速度 NFR を維持）
- **REG-02** 🔵[U] 既存のフィルタ機能 — フィルタの挙動を変更しない（エクスポートはフィルタ結果を読むだけ）

---

## 8. 既存制約との整合（CON）★ブラウンフィールド必須

> この機能が **従わなければならない既存の制約**（技術スタック・コーディング規約・データモデル・認証・性能予算 等）。新規に選び直せない前提。

**見本:**
- **CON-01** 🔵[C] 技術スタック: 既存の TypeScript + React + SQLite に従う（新規ライブラリ追加は最小限）
- **CON-02** 🔵[U] 認証: 既存の localhost バインド・認証なしの方針を踏襲する
- **CON-03** 🟡[C] コーディング規約: 既存の ESLint/Prettier 設定と命名規則に従う

---

## 9. データ / スキーマ変更（該当する場合）

> テーブル・カラム追加、マイグレーション、既存データの変更、後方互換性の有無。**データに触れない機能なら「変更なし」と明記**。

**見本:**
> 変更なし（既存 `tasks` テーブルを読み取るのみ。マイグレーション不要）。

---

## 10. スコープ外

この機能追加で明示的に「やらない」こと。特に **「既存の○○は変更しない」** を明示する。

**見本:**
- PDF・Excel 形式での出力（CSV のみ）
- エクスポート履歴の保存
- 既存のタスク登録・編集・削除フローの変更（一切触らない）
- Notion 連携への影響（このバージョンでは連動しない）

````
