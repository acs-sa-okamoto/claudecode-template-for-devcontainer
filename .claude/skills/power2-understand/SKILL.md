あなたは既存コードベースを読み解くシニアエンジニアです。`power1-scope` が作った `feature-requirements.md` を入力に、**この機能追加が安全に統合できるよう既存システムを理解**し、後続の設計（`power3-design`）が拠り所にする **理解ブリーフ（`understanding-brief.md`）** を生成します。既存システムの地図は、`code-atlas` が作る **コードの地図帳（`docs/code-atlas/`）** を使います。

これは **power ワークフローの工程2（既存理解）** であり、**このワークフロー最大の差別化ポイント**です。「全部読む」でも「ドキュメントだけ」でもなく、**全体は浅くつかみ、この機能が乗る場所だけを深く読み、統合面は実コードで検証**します。

# 原則（最優先）

- **コードが ground truth**。ドキュメントは古い前提で扱い、**統合面は必ず実コードで確認**する（「テスト全通過 ≠ 動く」の理解フェーズ版）。地図帳も同じで、書かれていることを出発点にし、統合点は自分で読んで確かめる。
- **役割を分ける**: 既存システムの地図（全体像・規約・用語・区画のページ）は **地図帳**に、この機能に固有のこと（統合点・フロー・影響範囲・矛盾）は **理解ブリーフ**に書く。同じことを 2 か所に書かない。
- **探索量は、規模とドキュメント信頼度で調整**する: 強制契約（型/スキーマ/OpenAPI/テスト）が揃うほど軽く、散文/無いほど重く。大きいリポジトリほど、深く読む区画を絞る。
- **重い探索はサブエージェントに委譲**する（code-atlas が行う）。メインは集約とユーザー確認に徹し、肥大化を防ぐ。
- 各 finding に **信頼性レベル 🔵🟡🔴** を付ける。power1 の 🟡[C] 候補を実コードで検証し、確認できたら 🔵 に上げる／不一致は修正する。
- **🔵 は自己申告で名乗らない**。`file:line` の根拠を添え、**検証スクリプトを通ったものだけを 🔵** とする。AI が書いたものを同じ AI が確認しても**両方に同じ前提＝同じ盲点**が入るため、機械的検査でしか担保できない。
- **理解は図にする**。散文は曖昧なまま書けてしまうが、図はノードと辺を決めないと描けない。**描けない ＝ 理解できていない**、のシグナルとして使う。
- **読み取り中心。コードは変更しない**（実装は power5）。

> **オーケストレーター連携**: `power` から呼ばれた場合もメインコンテキストで実行され、AskUserQuestion が正常に機能する。

## step1: 入力の読み込み

- `pwd` で対象リポジトリ名を把握する。
- `{機能名}` を確定する（引数があればそれ。無ければ `docs/spec/*/feature-requirements.md` を Glob。1件ならそれ、複数なら AskUserQuestion で選択）。
- `feature-requirements.md` を読み、**INT/REG/CON 候補・FR・AC** を把握する（＝何を・どこを理解すべきかの地図）。
- `CLAUDE.md` / `docs/rule/ai-security-guardrails.md` があれば読む。
- **Git ブランチの確保**（git 管理下の場合）: 作業は `feature/{機能名}` ブランチ上で行う。未作成ならデフォルトブランチを基点に作成、既存ならチェックアウト。非 git／git 不在ならスキップ。

## step2: プロジェクト種別とドキュメント信頼度の判定

- **Beam 製判定**: `docs/spec/*/requirements.md` / `design/` / `docs/tasks/*/code-map.md` / `data/tasks.db` の有無で判定。spec-archive で片付け済みなら、これらは無くなっているので、`docs/spec/ARCHIVE.md` の「種類」が beam の行と、現役の仕様 `docs/spec/current/` の有無でも判定する。
- **ドキュメント信頼度ティアを判定**:
  - **高**: 型定義・OpenAPI・DB スキーマ・テスト・設計契約が揃う（＝コード結合で信頼できる）
  - **中**: 手書きのアーキテクチャ／設計ドキュメントがある
  - **低**: 散文 Wiki・コメントのみ・古い・無い
- このティアで step3〜4 の **探索の深さを決める**（高 → 軽め＝契約を信頼し、統合点が乗る区画だけを深く読む / 低 → 重め＝関係しそうな区画を広めに深く読む）。判定結果をブリーフに記録する。

## step3: 地図帳の用意（★山場。code-atlas を呼ぶ）

### step3-1: テーマを決める

feature-requirements から、**この機能が触る場所を表すテーマ**を作る。機能名、INT 候補の接続先（モジュール・画面・データ）、業務の言葉とその同義語・英語を入れる。

> 例: 「会話に付けるタグ（画面ではブックマーク）。タグの付け外しの API、会話の保存・複製・取り込み、ヘッダーのメニュー」

要件の言葉とコード上の名前は違うことがある（「タグ」が `Bookmarks` という名前で実装されている、など）。power1 の探索で見つけた名前があれば、テーマに含める。

### step3-2: code-atlas を実行する

```
Skill(skill="code-atlas", args="--from power2 {テーマ}")
```

code-atlas は、地図帳の状態に応じて次のように動く（詳細は code-atlas の SKILL.md）:

| 地図帳の状態 | code-atlas がすること |
|---|---|
| 無い | 新規に作る。目録 → 区画に分ける → 全体を浅くつかみ、規約を調べる → **テーマに関わる区画だけ**を深く読む |
| 有る | 鮮度を確かめ、古くなった区画を直す。テーマに関わる区画のうち、まだ深く読んでいないもの（「浅い」「未探索」、または「深い（範囲）」の範囲外）を深掘りする |

- **「地図帳があるから探索を省く」は、深く読んである範囲に限る。** この機能が乗る場所が「浅い」「未探索」、または「深い（別の範囲）」なら、必ず深掘りさせる。地図に書かれていないことは、存在しないことを意味しない。
- 規模が中・大のとき、code-atlas は「深く読む区画の案」を示して確認を求める。**step2 のティア**（高なら絞る・低なら広め）を踏まえた案になっているかを見る。
- beam で作ったリポジトリでは、code-atlas が設計書（`docs/spec/*/design/`）と実装の索引（`docs/tasks/*/code-map.md`）を手がかりとして読む（spec-archive で片付け済みなら無い。そのときは現役の仕様 `docs/spec/current/README.md` を手がかりにする）。
- 旧版の power2 が作った `docs/code-map.md` が残っているリポジトリでは、code-atlas がそれを手がかりとして一度読み、削除の提案を申し送ってくる（step7 で確認する）。

### step3-3: 地図帳を読む

- `docs/code-atlas/index.md` を読み、この機能が乗る区画を特定する。
- その区画のページ（`sections/`）、`conventions.md`、`glossary.md` を読む。全体の流れが要るときは `architecture.md` も読む。
- 「この機能が乗る区画」と、その深さ（読んだ範囲）を控えておく（ブリーフの 0 節に書く）。

## step4: 統合面の精読と検証

- feature-requirements の **INT/CON 候補を実コードで精読・検証**する。区画のページの「入口」「主要モジュール」「データ」を出発点にし、**ページの記述をそのまま写さず、該当のコードを自分で読む**:
  - 接続先の関数/型/スキーマの **実シグネチャ・契約**
  - 踏襲すべき **実装パターン・エラー処理・命名**（代表例を `file:line` で。全体の規約は `conventions.md` の ID で引用する）
- power1 の 🟡[C] を実コードで確認 → **🔵 に昇格／不一致は修正**する。
- **ドキュメントと実コードが食い違う点は「実コード優先」で記録**し、要検証として残す（ground truth はコード）。地図帳の記述がコードと食い違っていたら、地図帳の側を直す（該当のページを Edit し、検証リビジョンは書き換えずに、step6 の検証で確かめる）。

### step4-1: 既存要件との矛盾チェック（★ここで見つけなければ誰も見つけない）

**この機能の FR/NFR が、既存の要件と正面から矛盾していないかを明示的に確認する。**

- **探す場所**:
  - **現役の仕様 `docs/spec/current/`**（完了した機能の要件をまとめたもの。あれば最初に読む）: `README.md` の領域の表から、この機能が触る領域のファイルを開く。**「しないこと」の節が最有力**（理由と前提が書いてあるので、前提が変わっていないかを見る）
  - まだ現役の仕様にまとめていない仕様: 既存プロジェクトの仕様（`docs/spec/{要件名}/requirements.md` の**スコープ外・否定的制約**の節が最有力）、既存機能の `feature-requirements.md`（作業中の機能と、片付けていない完了済みの機能）。片付けた機能の文書は Git の履歴にあり、読まない（中身は現役の仕様にある）
  - **古い記述の手がかり**: spec-archive の `find-stale-spec.sh` を、この機能が触る領域のファイルに実行する（今は無いコードを書いている節は、要件が今の動きとずれている可能性がある。ずれていれば矛盾と同じく扱う）
  - **地図帳の `conventions.md`**: 「禁止・制約」（NG-）と、「規約の文書」の決まり。**規約の文書には、コードを読むだけでは分からない決まりがある**（例: 「新しい上限は設定で変えられるようにし、既定値は今の挙動を再現する」という決まりは、「上限は 3 個に固定」という要件とぶつかる）
  - **実装コード中の「〜してはならない」「〜しない」というコメント**。要件 ID を伴って書かれていることが多く（例: `// REQ-405: 例文穴埋め形式は作らない`）、**grep で機械的に見つかる**
  - **この機能と同じことをする既存の機能**。別の名前で既に実装されていないか（用語の対応 `glossary.md` を引く）。あれば、「既存を使う・広げる」のか「別物を作る」のかを要件側に確認する
- **典型的な形**: 「システムは X を実装してはならない」という否定的制約に対し、今回の機能が **X そのものを実装しようとしている**。制約が誤っていたのではなく、**制約が前提としていた条件（データの性質・外部サービスの仕様・利用者の状況）が変わった**ために陳腐化している、というのが多い。だから「古い要件だから無視してよい」ではなく、**前提が変わったことを要件側に記録する**必要がある。

> **⚠️ この矛盾を拾う機構は、このワークフローに他に1つも無い。**
> - **power5 / power6 の整合ドリフト検知**は `docs/spec/{機能名}/` の**コミット時刻の比較**であり、(1) 意味の矛盾は見えず、(2) そもそも既存プロジェクト側の仕様（`docs/spec/{要件名}/`）を監視していない。
> - **power6 の要件適合ゲートも拾わない**。判定対象は「**feature-requirements の** 全 FR/NFR/AC」＝今回の機能自身の要件だけで、既存の REQ-* は評価しない。
> - **power6 の回帰検証も拾わない**。禁止されていた機能を**実装する**のは既存挙動を**壊す**変更ではないため、REG の検証方法に掛からない。
>
> つまり**ここで見落とすと、自動フローのどこにもバックストップが無いまま出荷される**。「最後は power6 が拾ってくれる」は成り立たない。

**見つけた矛盾は、記録して終わりにしない。** understanding-brief の「リスク・未解決の論点」に 🔴 で載せたうえで、**`/revise` をいつ実行するかを AskUserQuestion でユーザーに確定させる**（既定の推奨は「power4 完了後・power5 着手前」＝設計とタスクは矛盾を記録したまま進め、実装に入る前に上流を整合させる）。**「あとで直す」と書くだけで担い手と時期を決めないと、そのまま実装へ流れて power6 で詰まる。**

矛盾が 1 件も無ければ、その旨を一言述べる（確認したこと自体を残す）。

### step4-2: この機能が乗るフローを図に描く（★ここで理解を検証する）

**`code-atlas/references/diagrams-and-evidence.md` を読んでから描く**（解決順: リポジトリ直下 `.claude/skills/` → `~/.claude/skills/`）。

- **この機能が乗る要求 1 本**を、入口から出口まで Mermaid のシーケンス図に描き、図の直下に根拠の表（`file:line`）を置く。書く場所は理解ブリーフの 1 節の「この機能が乗るフロー」。
- 地図帳の `architecture.md` に同じ流れの図が既にあれば、それを参照し、この機能で**変わる・足す**場所だけを示す図にする。
- 作図の決まり DG-1〜DG-5 に従う（**憶測を描かない**。確かめていない経路は図にせず、未解決の論点に回す）。
- 明確な入口が無い機能（内部のリファクタなど）では、変更の中心になる構成の図（flowchart）に替える。図が該当しなければ、理由を一言述べて飛ばす。

## step5: 影響範囲分析（blast radius）

統合点が出そろってから、次の順に洗う。**Grep と Read で確かめたものだけを REG にする。**

1. **書き込む経路をすべて挙げる** — 統合点のシンボル（関数・メソッド・API・保存先のフィールド）ごとに、呼び出し箇所と書き込み箇所を Grep で洗う。同じデータを書く経路は、画面からの手操作だけではない（一括処理、取り込み、複製、移行、ほかの機能からの間接的な書き込み）。同じ名前の関数が複数あるときは、import 先を見て区別する。区画のページの「データ」に経路の一覧があれば出発点にし、**一覧に無い経路が無いかを Grep で確かめる**。
2. **共用部品の利用元を挙げる** — 手を入れる可能性のある部品や関数について、それを import しているファイルをすべて洗う。今回の機能と関係の無い画面や処理が同じ部品を使っていないかを見る。
3. **既定で動く自動処理と既存データを確かめる** — 設定の既定値で有効になっていて同じデータを書き換える処理、移行・取り込みなどで既に入っているデータが、今回の要件と食い違わないかを確かめる（例: 個数の上限を足すなら、既に上限を超えたデータがあるか、あったときにどう振る舞うか）。
4. **隠れた結合・暗黙の依存を洗う** — グローバル状態・副作用・順序依存・派生値（件数のキャッシュなど）の手動の同期・同時実行。

- 変更で影響しうる既存機能を特定し、feature-requirements の **REG を実コードで拡張・確定**する（`file:line` ＋ 「なぜ影響するか」＋ 検証方法）。これが power6 の回帰ガードの入力になる。
- **「呼び出しが見つからない」を「影響が無い」と読み替えない。** 動的な呼び出し、文字列での参照、別の名前での再エクスポートがある。見つからなかったことは、確かめた方法と一緒に「未解決の論点」に書く。
- **2つ目以降の機能**: 既にマージ済みの過去機能の挙動も「壊してはいけない既存挙動」に含める（REG に過去機能の主要動線を加える）。必要なら power0 の characterization テストを当該挙動に**追記して回帰ネットを育てる**。

## step6: understanding-brief.md の生成と検証

- `templates/understanding-brief-template.md` に従って `docs/spec/{機能名}/understanding-brief.md` を生成する:
  - プロジェクト種別・ドキュメント信頼度ティア・**検証リビジョン**（`git rev-parse HEAD` の 40 桁）
  - **この機能が乗る区画**（地図帳の区画の ID と、読んだ深さ）
  - **統合面**（確定 INT・契約・`file:line`・信頼性）
  - **この機能が乗るフロー**（step4-2 の図と根拠の表）
  - **踏襲すべき規約・パターン**（全体の規約は `conventions.md` の ID を引用し、この機能に固有のものを `file:line` で）
    - 画面に触る機能なら、**UI の規約**（部品・トークン・余白・文言）も書く。power3 の ui-design plan（追従）がこれを元に `docs/ui/standard.md` を作る（まだ無い場合。既存の決まりの抽出であって、新しい見た目は決めない）。
    - 種別が「UI 一新」なら、「UI の作り」を独立した節にする。値を直接書いている色・文字サイズの数と多い場所（`file:line`）、共通の部品を通さずに作っている画面を数える。これが power3 の change-plan と power4 のフェーズ分けの材料になる。
  - **データモデル・スキーマの現状**
  - **影響範囲・回帰リスク**（確定 REG・なぜ影響するか・検証方法）
  - **リスク・未解決の論点**（設計前に解消すべき疑問）
- 各項目に信頼性レベルを付す。根拠は、リポジトリのルートからの完全なパスで、1 つのバッククォートに 1 つだけ書く。

**書いたら必ず検証する**（git 管理下の場合）:

```bash
# スクリプトは「このスキルの置き場所」から辿る（作業ディレクトリや $HOME を基準にしない）
B='<このスキルのベースディレクトリ>'   # Claude Code が「Base directory for this skill」で示す値をそのまま入れる
B="$(printf '%s' "$B" | tr '\134' '/')"                    # \ を / に揃える（\134 はバックスラッシュ）
if command -v wslpath >/dev/null 2>&1; then                # WSL の bash のときだけ変換する
  case "$B" in
    //wsl.localhost/*/*|//wsl[$]/*/*) B="/${B#//*/*/}" ;;   # \\wsl.localhost\<distro>\x → /x
    [A-Za-z]:/*) B="$(wslpath -u "$B")" ;;                  # C:\x → /mnt/c/x
  esac
fi
V="$B/../code-atlas/scripts/verify-atlas-evidence.sh"
bash "$V" --file "docs/spec/{機能名}/understanding-brief.md"   # 理解ブリーフの根拠
bash "$V"                                                      # 地図帳の全体（step4 で直した場合に備えて）
```

- **スクリプトが見つからない・実行できない（終了コード 127 など）ときは「未検証」として扱い、項目を 🔵 にしない。**
- **失敗した根拠は必ず直す**（パス誤り・行ずれ）。直せないものは根拠を外し、その項目を **🟡 に格下げ**する。
- **「検証されない書き方の疑い」が 0 になるまで直す**（省略形で書くと、黙って検証対象から漏れる）。
- git 管理外なら「未検証」と明記し、項目は 🔵 にしない。
