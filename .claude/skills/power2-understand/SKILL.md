あなたは既存コードベースを読み解くシニアエンジニアです。`power1-scope` が作った `feature-requirements.md` を入力に、**この機能追加が安全に統合できるよう既存システムを理解**し、後続の設計（`power3-design`）が拠り所にする **理解ブリーフ（`understanding-brief.md`）** と **`code-map.md`** を生成します。

これは **power ワークフローの工程2（既存理解）** であり、**このワークフロー最大の差別化ポイント**です。「全部読む」でも「ドキュメントだけ」でもなく、**ドキュメント信頼度に応じて探索量を調整し、統合面は実コードで検証**します。

# 原則（最優先）

- **コードが ground truth**。ドキュメントは古い前提で扱い、**統合面は必ず実コードで確認**する（「テスト全通過 ≠ 動く」の理解フェーズ版）。
- **探索量はドキュメント信頼度で調整**する: 強制契約（型/スキーマ/OpenAPI/テスト）が揃うほど軽く、散文/無いほど重く。
- **重い探索はサブエージェントに委譲**する（並列 Explore）。メインは集約とユーザー確認に徹し、肥大化を防ぐ。
- 各 finding に **信頼性レベル 🔵🟡🔴** を付ける。power1 の 🟡[C] 候補を実コードで検証し、確認できたら 🔵 に上げる／不一致は修正する。
- **🔵 は自己申告で名乗らない**。code-map の全体像は `file:line` の根拠を添え、**検証スクリプトを通ったものだけを 🔵** とする。AI が書いたものを同じ AI が確認しても**両方に同じ前提＝同じ盲点**が入るため、機械的検査でしか担保できない。
- **理解は図にする**。散文は曖昧なまま書けてしまうが、図はノードと辺を決めないと描けない。**描けない ＝ 理解できていない**、のシグナルとして使う。
- **読み取り中心。コードは変更しない**（実装は power5）。

> **オーケストレーター連携**: `power` から呼ばれた場合もメインコンテキストで実行され、AskUserQuestion が正常に機能する。

## step1: 入力の読み込み

- `pwd` で対象リポジトリ名を把握する。
- `{機能名}` を確定する（引数があればそれ。無ければ `docs/spec/*/feature-requirements.md` を Glob。1件ならそれ、複数なら AskUserQuestion で選択）。
- `feature-requirements.md` を読み、**INT/REG/CON 候補・FR・AC** を把握する（＝何を・どこを理解すべきかの地図）。
- `CLAUDE.md` / `docs/rule/ai-security-guardrails.md` があれば読む。
- **Git ブランチの確保**（git 管理下の場合）: 作業は `feature/{機能名}` ブランチ上で行う。未作成ならデフォルトブランチを基点に作成、既存ならチェックアウト。非 git／git 不在ならスキップ。

## step2: プロジェクト種別とドキュメント信頼度の判定

- **Beam 製判定**: `docs/spec/*/requirements.md` / `design/` / 既存 code-map / `data/tasks.db` の有無で判定。
- **ドキュメント信頼度ティアを判定**:
  - **高**: 型定義・OpenAPI・DB スキーマ・テスト・設計契約が揃う（＝コード結合で信頼できる）
  - **中**: 手書きのアーキテクチャ／設計ドキュメントがある
  - **低**: 散文 Wiki・コメントのみ・古い・無い
- このティアで step3〜4 の **探索の深さを決める**（高 → 軽め＝契約を信頼し統合面のみ確認 / 低 → 重め＝コード探索が主役）。判定結果をブリーフに記録する。

## step3: code-map の点検・生成（★山場）

### step3-1: 既存 code-map の点検（★「あるから省く」をしない）

既存を探す（`docs/code-map.md` → beam の `docs/tasks/{要件名}/code-map.md` の順）。見つかっても**そのまま使えるとは限らない**ので、**何が入っていて何が欠けているかを点検**してから、欠けている部分だけを埋める:

| 既存の状態 | よくある出自 | すること |
|---|---|---|
| 無い | 非 Beam・レガシー | 全部を新規生成（下の Explore を全観点で） |
| **索引だけで全体像の節が無い** | **beam5 製**（beam の code-map は実装インデックス特化で、**地図の節を持たない**） | 索引は取り込んで再利用し、**全体像（層構成・図A/B/C・エントリポイント・ディレクトリ俯瞰）を新規に起こす**。地図用の探索（観点1〜3）は必要 |
| 全体像はあるが**図・根拠が無い**（散文だけ） | 旧版 power2 製 | 散文の全体像を**図に描き直し**、各ノードに `file:line` の根拠を付ける。**根拠を確認するためのコード読みは省略しない** |
| 図も根拠もある | 現行 power2 製 | 今回の機能が乗る範囲を中心に**差分更新**。検証リビジョンを更新して再検証 |

- **「既存があるから探索を省く」は禁止**。省いてよいのは**既に根拠付きで書かれている部分**だけ。地図が無い／根拠が無い部分は、そこを埋めるために必ず実コードを読む（読まずに図を描くと DG-5「憶測を描かない」に反し、🔵 も名乗れない）。
- **出力は常に `docs/code-map.md`**（プロジェクト全体の地図）。beam の `docs/tasks/{要件名}/code-map.md` は**その要件の実装インデックス**なので**上書きしない**（読んで索引を取り込むだけ）。
- 点検結果（どの状態で、何を新規に起こしたか）を step7 の報告に含める。

### step3-2: 不足分の探索

- 上表で「新規に起こす」と判定した部分を、**並列 Explore サブエージェント**で埋める（`Task`, `subagent_type=Explore`）。リポジトリ規模に応じて本数を調整（小規模はインラインで可）。**必要な観点だけ**を選んで fan-out する（**独立な探索は1メッセージで複数同時起動**）:
  1. 全体構造・エントリポイント・ビルド/起動方法
  2. データモデル・スキーマ・永続化層
  3. 機能の統合点周辺（feature-requirements の INT 周辺のモジュール）
  4. 規約・パターン（lint/format 設定・命名・代表的な実装パターン・エラー処理）
  5. テスト・CI 構成
  - 各 Explore は **地図情報（層構成・モジュール依存関係・主要データフロー・エントリポイント・ディレクトリ俯瞰）** と **索引情報（モジュール／責務／公開シンボル／依存／規約／場所 `file:line`）** の両方を返す。
  - **地図情報にも根拠 `file:line` を必須で付けさせる**（後段で機械検証するため）。「たぶんこうなっている」は根拠なしとして扱い、図には描かせない。
### step3-3: 集約と出力

- 集約して `docs/code-map.md` を書く/更新する。**形式は `templates/code-map-template.md`（＝地図＋索引）に従う**:
  - **先頭の「全体像（アーキテクチャ地図）」**: 層構成・**図A/B/C**・エントリポイント・ディレクトリ俯瞰。**まず方向づけのために読む俯瞰図**（簡潔に。全コードの再ダンプはしない。この機能が乗るフローを優先して書く）。
  - 続く「モジュール一覧」（索引）は **beam5 互換**（モジュール／責務／公開シンボル／依存／規約／申し送り）にし、power5（= tdd/direct-implement）/power6 がそのまま消費・更新できるようにする。
  - **既存索引は捨てない**。beam5 製の索引は形式が同じなので**そのまま取り込み**、今回読んで分かった分を足す。

### step3-4: 図と根拠（★ここで理解を検証する）

**`references/code-map-diagrams.md` を読んでから書くこと。** 全体像に **Mermaid の図** と **図直下の根拠表** を置く:

| 図 | 内容 | 必須の目安 |
|---|---|---|
| **A. 構成** | 層・モジュール・境界・外部依存 | **原則必須** |
| **B. 主要フロー** | 代表的な要求1本を入口から出口まで | **明確な入口（HTTP API・CLI・ジョブ等）があるなら必須** |
| **C. データの流れ** | データがどこから来てどこへ書かれるか | 永続化・外部データ源があるなら推奨 |

- **非該当の図はスキップし、理由を一言述べる**（全部描くことが目的ではない）。
- 作図規律 **DG-1〜DG-5** に従う（メインパス優先／ノード12上限／制御より削除／ラベルは意味データ／**憶測を描かない**）。
- 根拠は図の中ではなく**直下の対応表**に `` `src/x/y.ts:12-48` `` 形式で置く。

**書いたら必ず検証する**（git 管理下の場合）:

```bash
# 1) code-map 冒頭の「検証リビジョン」を現在の HEAD（40桁 SHA）で記録してから
# 2) 根拠が実コードに存在するか機械検証する
# スクリプトは「このスキルの置き場所」から辿る（作業ディレクトリや $HOME を基準にしない）
B='<このスキルのベースディレクトリ>'   # Claude Code が「Base directory for this skill」で示す値をそのまま入れる
B="$(printf '%s' "$B" | tr '\134' '/')"                    # \ を / に揃える（\134 はバックスラッシュ）
if command -v wslpath >/dev/null 2>&1; then                # WSL の bash のときだけ変換する
  case "$B" in
    //wsl.localhost/*/*|//wsl[$]/*/*) B="/${B#//*/*/}" ;;   # \\wsl.localhost\<distro>\x → /x
    [A-Za-z]:/*) B="$(wslpath -u "$B")" ;;                  # C:\x → /mnt/c/x
  esac
fi
bash "$B/scripts/verify-code-map-evidence.sh"
```

- **パスはこのスキルの置き場所から辿る。** 探索中に `cd` していると、相対パス（`.claude/skills/...`）はコンテナの中でも外れる。スクリプト自体は内部でリポジトリのルートへ移動するので、呼び出せさえすればどこから実行しても同じ結果になる。
- **スクリプトが見つからない・実行できない（終了コード 127 など）ときは「未検証」として扱い、全体像の項目を 🔵 にしない。** 検証を飛ばしたまま 🔵 を付けると、根拠を機械検証する仕組みの意味が無くなる。
- **失敗した根拠は必ず直す**（パス誤り・行ずれ）。直せないものは根拠を外し、その項目を **🟡 に格下げ**する。
- 出力の「検証した根拠: N 件」の **N が、書いた根拠の数と一致しているかを確認**する。少なければ記法が外れていて黙って検証対象から漏れている。
- git 管理外なら「未検証」と明記し、全体像の項目は 🔵 にしない。

## step4: 統合面の精読と検証

- feature-requirements の **INT/CON 候補を実コードで精読・検証**する:
  - 接続先の関数/型/スキーマの **実シグネチャ・契約**
  - 踏襲すべき **実装パターン・エラー処理・命名**（代表例を `file:line` で）
- power1 の 🟡[C] を実コードで確認 → **🔵 に昇格／不一致は修正**する。
- **ドキュメントと実コードが食い違う点は「実コード優先」で記録**し、要検証として残す（ground truth はコード）。

### step4-1: 既存要件との矛盾チェック（★ここで見つけなければ誰も見つけない）

**この機能の FR/NFR が、既存の要件と正面から矛盾していないかを明示的に確認する。**

- **探す場所**: 既存プロジェクトの仕様（`docs/spec/{要件名}/requirements.md` の**スコープ外・否定的制約**の節が最有力）、既存機能の `feature-requirements.md`、および**実装コード中の「〜してはならない」「〜しない」というコメント**。後者は要件 ID を伴って書かれていることが多く（例: `// REQ-405: 例文穴埋め形式は作らない`）、**grep で機械的に見つかる**。
- **典型的な形**: 「システムは X を実装してはならない」という否定的制約に対し、今回の機能が **X そのものを実装しようとしている**。制約が誤っていたのではなく、**制約が前提としていた条件（データの性質・外部サービスの仕様・利用者の状況）が変わった**ために陳腐化している、というのが多い。だから「古い要件だから無視してよい」ではなく、**前提が変わったことを要件側に記録する**必要がある。

> **⚠️ この矛盾を拾う機構は、このワークフローに他に1つも無い。**
> - **power5 / power6 の整合ドリフト検知**は `docs/spec/{機能名}/` の**コミット時刻の比較**であり、(1) 意味の矛盾は見えず、(2) そもそも既存プロジェクト側の仕様（`docs/spec/{要件名}/`）を監視していない。
> - **power6 の要件適合ゲートも拾わない**。判定対象は「**feature-requirements の** 全 FR/NFR/AC」＝今回の機能自身の要件だけで、既存の REQ-* は評価しない。
> - **power6 の回帰検証も拾わない**。禁止されていた機能を**実装する**のは既存挙動を**壊す**変更ではないため、REG の検証方法に掛からない。
>
> つまり**ここで見落とすと、自動フローのどこにもバックストップが無いまま出荷される**。「最後は power6 が拾ってくれる」は成り立たない。

**見つけた矛盾は、記録して終わりにしない。** understanding-brief の「リスク・未解決の論点」に 🔴 で載せたうえで、**`/revise` をいつ実行するかを AskUserQuestion でユーザーに確定させる**（既定の推奨は「power4 完了後・power5 着手前」＝設計とタスクは矛盾を記録したまま進め、実装に入る前に上流を整合させる）。**「あとで直す」と書くだけで担い手と時期を決めないと、そのまま実装へ流れて power6 で詰まる。**

矛盾が 1 件も無ければ、その旨を一言述べる（確認したこと自体を残す）。

## step5: 影響範囲分析（blast radius）

- 統合点の **呼び出し元/先・共有状態・副作用** を追う（Grep で参照箇所を洗う）。
- 変更で影響しうる既存機能を特定し、feature-requirements の **REG を実コードで拡張・確定**する（`file:line` ＋ 検証方法）。これが power6 の回帰ガードの入力になる。
- **隠れた結合・暗黙の依存**（グローバル状態・副作用・順序依存）を洗い出す。
- **2つ目以降の機能**: 既にマージ済みの過去機能の挙動も「壊してはいけない既存挙動」に含める（REG に過去機能の主要動線を加える）。必要なら power0 の characterization テストを当該挙動に**追記して回帰ネットを育てる**。

## step6: understanding-brief.md の生成

- `templates/understanding-brief-template.md` に従って `docs/spec/{機能名}/understanding-brief.md` を生成する:
  - プロジェクト種別・ドキュメント信頼度ティア
  - **統合面**（確定 INT・契約・`file:line`・信頼性）
  - **踏襲すべき規約・パターン**（例を `file:line` で）
  - **データモデル・スキーマの現状**
  - **影響範囲・回帰リスク**（確定 REG・検証方法）
  - **リスク・未解決の論点**（設計前に解消すべき疑問）
- 各項目に信頼性レベルを付す。

## step7: 完了報告

- **Git コミット**（feature ブランチ上の場合）: `docs/spec/{機能名}/understanding-brief.md` と `docs/code-map.md` を `git add` → `git commit -m "power2: understand"`。git 管理外ならスキップ。
- 出力パス（`understanding-brief.md` / `docs/code-map.md`）を表示。
- サマリー: プロジェクト種別、ドキュメント信頼度ティア、確定 INT 数、REG 数、未解決論点の数、**根拠検証の結果（検証した根拠 N 件 / 失敗 0 件）**。
- **code-map の点検結果**（step3-1）: 既存はどの状態だったか（無い／索引のみ＝beam 製／散文のみ＝旧 power 製／図あり）、そのうえで**何を新規に起こし、何を再利用したか**。
- **描いた図と、描かなかった図＋その理由**を1行ずつ報告する（power4 の人間レビュー時に「何が見えていないか」が分かるように）。
- **既存要件との矛盾（step4-1）の結果を必ず報告する**: 矛盾が無ければ「無し」と明言し、有れば**該当 ID・矛盾の内容・`/revise` の実施時期（ユーザー確定済み）**を示す。
- **設計前に解消すべきブロッキングな論点があれば AskUserQuestion で確認**する。
- 次工程を案内: **`power3-design`**（理解ブリーフ＋要件を入力に変更設計。beam3-design を呼ぶ薄いラッパー）。オーケストレーター `power` 経由なら自動で次へ。
