beam の入口が to-prd であるように、**ui-renewal は「UI の一新」の入口**です。受け持つのは**診断・ヒアリング・要求書・方向決め**までで、実装・検証・PR は power に任せます。

# 原則

- **一新するのは、レベル1（見た目）とレベル2（画面の中の使いやすさ）。**
  - レベル3（メニューの構成・画面の統合と分割・導線の変更）は機能の変更なので、1件ずつ通常の power の機能にする。
  - レベル3の候補は、要求書に載せておく。
- **変えてはいけないものを先に決める。** 主要な導線の結果・URL・入力項目・出力（CSV・帳票・印刷）・権限を決め、power の REG（壊してはいけない既存機能）にする。
- **新しい見た目の決まり（`docs/ui/standard.md`）は feature ブランチに載せる。** 一新がマージされた時点で切り替わるので、作業中にほかの機能が新しい決まりを先取りしない。
- **大きなアプリは段階に分ける。** 1段階は1回の power（1マージ単位）にする。
  - 段階1: トークンと共通部品。トークン経由で全画面の見た目が一度に変わるので、途中の段階でも新旧が混ざりにくい。
  - 段階2以降: 画面のまとまりごと（よく使う画面から）。
- **UI ライブラリの乗り換えは、既定で対象外。** 要るときは、別の判断として理由と見積もりを要求書に書く。
- **好みは人間が決める。** モックと review.html を人間が承認する。AI は最終承認者ではない。
- **新規開発（まだ画面が無い）なら使わない。** beam を使う（beam3 で ui-design plan〔新規〕が動く）。

# 流れ

```
/ui-renewal
 step0 前提 ………… 同梱スキルの更新・power の準備度・ui-shots・アプリの起動・進行中の一新の有無
 step1 棚卸し ……… 画面台帳（docs/ui/screens.json）を作る／確かめる。よく使う画面と主要な導線
 step2 診断 ………… ui-design audit（全画面と主要な導線）＋ backlog の取り込み
 step3 ヒアリング … 目的・範囲・レベル・変えてはいけないもの・見た目の土台・段階
 step4 要求書 ……… renewal-brief.md（下書き）
 step5 power1 ……… 要求書を元ドキュメントにして feature ブランチを作る（種別: UI 一新）
 step6 方向決め …… ui-design plan（一新）→ 新しい standard ＋ 新旧を並べたモック → 承認
 step7 引き継ぎ …… 診断・要求書・新しい決まりをコミット → /power で power2〜（推奨は power4 まで → レビュー）
```

ブランチができるまで（step1〜4）の下書きは `.ui-shots/renewal/` に置く。ここは git の対象外で、`capture.cjs` が `.git/info/exclude` に足す。

---

## step0: 前提

- **同梱スキルを更新する:** `/power` と同じく、最初に `power/SKILL.md` の「1-0. 同梱スキルの更新」のブロックを実行する（スクリプトは power のスキルの置き場所から辿る）。
- **準備度を確かめる:**
  - power の readiness ゲート（`power/SKILL.md` の 1-1 の①〜⑥）と同じ基準で確かめる。
  - 未整備なら、先に `/power0-onboard` を案内する（一新は既存の画面を壊しやすいので、回帰ネットは必須）。
- **撮影の道具を確かめる**（撮影できないまま進めない。診断が一新の土台になるため）:
  - **設定:** devcontainer.json の `features` に `"./ui-shots"` があり、`.devcontainer/ui-shots/` があるか。
  - **動くか（コンテナ内のとき）:** `ui-shots --check` で「`[ui-shots] 準備完了`」が出るか。
  - **設定が無いとき:** `Skill(skill="power0-onboard")` を実行する。今回より前にテンプレートから作った repo や、ui-shots ができる前に power0 で準備した repo が当たる。
    - power0 は「土台は整っていて、ui-shots の設定だけが無い」ことを見つけ、ui-shots だけを足してコミットする（`.gitignore` に掛かったファイルを `-f` で入れる確認も含む）。そのうえで再ビルドを案内して止まる。
    - ui-shots はコンテナのイメージを作るときに入る道具なので、**人が再ビルド（Rebuild Container）するまでは撮影できない**。ui-renewal もここでいったん終え、「再ビルドの後に `/ui-renewal` をやり直す」と案内する。スキルの更新（skills-update）は `.devcontainer/` を変えないので、この手順でしか入らない。
  - **設定はあるのに `--check` が通らないとき:** 表示された指示に従う（多くは再ビルド）。
  - **コンテナの外で実行しているとき:** 撮影はコンテナの中でしかできない。設定が無ければ上と同じく power0 で足す。そのうえで「Reopen in Container」で開き直し、`/ui-renewal` をやり直すよう案内する。
- **アプリを起動する:** CLAUDE.md の起動コマンドで起動する。ログインが要るなら、テスト用アカウントを `.env` に置いてもらう（値は聞き取らない・表示しない）。
- **進行中の一新を確かめる:** `docs/spec/*/feature-requirements.md` に「種別: UI 一新」があり、まだマージされていないものがあれば、AskUserQuestion で次のどれにするか聞く。
  - **続きをする:** `/power` で再開する。
  - **次の段階を始める:** 前の段階がマージ済みのとき。step3 から始め、診断は対象の画面だけを撮り直す。
  - **新しい一新を始める**

## step1: 棚卸し

- `docs/ui/screens.json` があれば使う。無ければ、ui-design の audit モードの手順1で作る（ルート定義とナビのリンクから画面を洗い出す）。
- 画面ごとに、よく使うかどうか（`frequency`）を AskUserQuestion で確かめる。多いときは、案を表で示してまとめて確かめる。
- 主要な導線（毎日の仕事の流れ）を3〜5本、要件・README・人間への質問から書く。各導線の今の手数は、撮影で数える。

## step2: 診断

- `Skill(skill="ui-design", args="audit")` を、出力先 `.ui-shots/renewal/audit` で実行する。課題一覧の下書きは `.ui-shots/renewal/ui-audit.md`（`templates/ui-audit.md` の形）。
- `docs/ui/backlog.md` の未対応の課題と、既存の `docs/ui/standard.md`（あれば）を取り込む。
- 結果の要点を示す: 一番大きな問題3つ、層ごとの課題の数、よく使う画面の課題、直す大きさごとの数（見た目だけ／画面の中／構成）。あわせて review.html の場所を示す。

## step3: ヒアリング

AskUserQuestion で1問ずつ聞く。診断の結果から推奨を選び、選択肢の先頭に置く。

1. **目的（複数選択）:** 古く見える／画面ごとにばらばら／使いにくい（手数・迷い）／スマホでも使いたい／アクセシビリティを満たしたい／社内標準にそろえたい。
2. **範囲:** 全画面／よく使う画面だけ／画面を指定する。
3. **レベル:** レベル1（見た目だけ）／レベル1＋2（推奨。画面の中の使いやすさも）。
4. **変えてはいけないもの（複数選択）:** URL／入力項目と順番／CSV・帳票・印刷の出力／用語／画面の並び。候補は診断と既存のテストから挙げる。
5. **見た目の土台:**
   - 社内標準（推奨）。
   - 指定の見本: standard-default.md の手順でリファレンス翻訳する。
   - 今の見た目を整えるだけ: 今の色と部品を正にし、ばらつきだけを直す。
6. **段階:** 診断の結果から案を出して確かめる。
   - 例: 段階1 トークンと共通部品／段階2 よく使う画面／段階3 残りの画面。
   - 画面が少なければ1段階でよい。

レベル3の候補（診断で「構成」とした課題）は、ここで「別の機能の候補」として要求書に載せることを伝える。

## step4: 要求書（下書き）

- `templates/renewal-brief.md` の形で `.ui-shots/renewal/renewal-brief.md` を書く。
- 各項目に信頼性（🔵🟡🔴）と出典（診断の課題 ID・ヒアリング）を付ける。
- 「直す課題」は、診断の課題 ID を、このあと power1 が FR にまとめやすい粒度でまとめる（同じ部品の同じ問題は1つ）。
- 段階を分けたときは、**この回で行う段階**を明記する。

## step5: power1（feature ブランチを作る）

- `Skill(skill="power1-scope", args=".ui-shots/renewal/renewal-brief.md")` を実行する。
- power1 は、要求書を元ドキュメントとして feature-requirements.md を作り、`feature/{機能名}` を作る。その際、種別を「UI 一新」にし、変えてはいけないものを REG の候補にする。
- 機能名の例: `ui-renewal-stage1`。
- power1 の後、下書きをブランチへ写す:
  - `.ui-shots/renewal/ui-audit.md` → `docs/spec/{機能名}/ui-audit.md`
  - `.ui-shots/renewal/renewal-brief.md` → `docs/spec/{機能名}/renewal-brief.md`

## step6: 方向決め（新しい見た目の決まりとモック）

- `Skill(skill="ui-design", args="plan {機能名} 一新")` を実行する。土台は step3 の選択（社内標準／指定の見本／今の見た目）。
- **新しい決まり:**
  - `docs/ui/standard.md` を新しい決まりに置き換える。今あるものは変更履歴に「一新の前」として要点を残す。
  - 診断の「良いところ（残すもの）」は、新しい決まりに引き継ぐ。
- **モック:**
  - `docs/ui/mock.html` は、よく使う画面2〜3枚に新しい決まりを当てたもの。本物の言葉と本物らしいデータを使う。
  - 診断のときの画像（変更前）を、新旧の比較として並べて見せる。
- **承認:**
  - モックを開いてもらい、AskUserQuestion で聞く。選択肢は「この方向で進める（推奨）」「直したい点がある（自由記述）」「土台から変える」。作り直しは2回まで。
  - **できれば実際の利用者1〜2人にもモックを見てもらう**よう勧める。

## step7: 引き継ぎ

- feature ブランチにコミットする: `docs/spec/{機能名}/ui-audit.md`・`renewal-brief.md`・`docs/ui/standard.md`・`docs/ui/mock.html`・`docs/ui/screens.json`。
  - メッセージは `ui-renewal: audit, brief and new standard`。
  - `.env` と `.ui-shots/` はコミットしない。
- 完了報告:
  - 診断の要点と、要求書の要点（目的・範囲・レベル・段階・変えてはいけないもの・レベル3の候補）。
  - 承認された方向。
- 次の進め方を AskUserQuestion で確かめる。
  - **続けて `/power` で power2 から進める（推奨は power4 まで → 成果物のレビュー → `/clear` → power5・power6）**
  - ここで止めて、要求書と見本をレビューする
- 続けるなら `Skill(skill="power")` を実行する。power は進行中の機能として検出するので、「再開」→ power2 を選ぶ。

# power での扱い（種別: UI 一新）

feature-requirements.md の「種別: UI 一新」を見て、各工程は次のように動く（詳しくは各スキルの UI 一新の節）。

| 工程 | 一新のときの扱い |
|---|---|
| power1 | 要求書の「直す課題」を FR に、「変えてはいけないもの」を REG の候補に、「成功の基準」を AC・NFR にする。UI ライブラリの乗り換えは既定で対象外 |
| power2 | スタイルの置き場所・ハードコードされた色と大きさの数・共通部品の有無・UI ライブラリを重点的に見て、understanding-brief の「UI の作り」に書く |
| power3 | standard.md は step6 で承認済み（作り直さない）。change-plan を「トークン導入（今の値 → トークンの対応表）→ 共通部品 → 画面」の順に組む。画面のタスクは screens.md の画面 ID で書く |
| power4 | フェーズ1を「回帰ネットの補強」にする。主要な導線の E2E を、見た目に左右されない書き方（ロール名・ラベルで探す）で先に用意する。続けてトークン → 共通部品 → 画面のフェーズ |
| power5 | 通常どおり（standard.md と screens.md をサブエージェントに渡す） |
| power6 | 範囲内の全画面を polish する（触った画面だけに絞らない）。比較元は診断のときの画像（`.ui-shots/renewal/audit` が残っていれば） |

# 段階2以降

- 前の段階がマージされた後に、`/ui-renewal` から始める（step0 で「次の段階を始める」を選ぶ）。
- 新しい決まりは段階1で切り替わっている。step6 は ui-design plan（**追従**）になり、必要なら決まりに追記するだけにする。
- step2 の診断は、その段階の対象の画面だけを撮り直す。段階1の要求書の残りの課題と、その後の backlog を使う。

> **AI 生成の画面は人間が確かめ、最終責任を持つ。AI は最終承認者ではない。**
