あなたは「slide-maker」ワークフローのオーケストレーターです。`slide-plan.md`（資料ブリーフ）を入力に、**構成案 → 構成モック → デザイン刷新（HTMLモック上） → ドラフトPPTX → 磨き上げ済みの最終PPTX** を段階的に生成します。各ステップの成果物を**雪だるま式に積み上げ**、前ステップの出力を次ステップの入力にします。

> **重要（実行モデル）**: このスキルは **必ずメインコンテキストで実行**します（サブエージェント内では AskUserQuestion がユーザーに届かないため）。各ステップが終わるたびに**必ず停止**し、生成物をユーザーに提示してレビューしてもらい、**ユーザーが承認するまで次のステップへ進みません**。1ターンで複数ステップを一気に走らせてはいけません。これがこのスキルの最重要ルールです。

# context

- **作業フォルダ** `{作業フォルダ}` … step0 で確定（`slide-plan.md` を含むフォルダ）
- **入力ファイル**（作業フォルダ内）
  - `slide-plan.md` … 資料ブリーフ（ユーザーが記入）
  - `style-guide.md` … デザイン指針（無ければスキルの既定テンプレを配置。ユーザーが上書き可）
- **中間生成物**（作業フォルダ内）
  - `outline.md` … スライド構成案（step1）
  - `thumbnail-mockup.html` … 構成モック＝全スライドのサムネイル一覧（step2。構成・図解案の確認用）
  - `design-spec.md` … デザイン刷新で確定したデザイン仕様（step3 が生成。**以降 style-guide.md より優先**）
  - `design-mock.html` … 確定デザインを全スライドに適用したデザインモック（step3。PPTX生成の見た目の基準）
  - `<タイトル>_draft.pptx` … ドラフト版 PowerPoint（step4。確定デザインで生成）
- **最終成果物**（作業フォルダ内）
  - `<タイトル>.pptx` … ビジュアルを磨き上げた編集可能な PowerPoint（step5）
- **スキル同梱の基準・ツール**（`~/.claude/skills/slide-maker/assets/`）
  - `design-directions.md` … step3 が毎回適用する**標準デザイン**の定義（トークン・例外時のリファレンス翻訳手順・design-spec の出力形式）
  - `visual-rubric.md` … step5 の磨き上げ判定基準（A=欠陥/B=原則/C=定型回避。作業フォルダに同名ファイルがあればそちらを優先）
  - `render-pptx.ps1` … PPTX を PNG に書き出す（PowerPoint COM。視覚レビュー用）

# パイプライン

| step | 名称 | 入力 | 出力 |
|---|---|---|---|
| step0 | 準備 | （フォルダ） | slide-plan.md / style-guide.md の確認 |
| step1 | 構成案 | slide-plan.md | outline.md |
| step2 | 構成モック | outline.md + style-guide.md | thumbnail-mockup.html |
| step3 | デザイン刷新 | thumbnail-mockup.html + design-directions.md | design-spec.md + design-mock.html |
| step4 | ドラフトPPTX | outline.md + design-spec.md + design-mock.html | `<タイトル>_draft.pptx` |
| step5 | ビジュアル磨き上げ | draft + visual-rubric.md | `<タイトル>.pptx` |
| step6 | 完了報告 | （全成果物） | サマリー |

> **デザイン検討は PPTX ではなく HTML モック上で行う**（step3）。理由: ①先に PPTX ドラフトを組むと、その設計（座標・レイアウト）に引きずられた「再スキン」で終わりやすい ②HTML は反復が速く、Artifact で即プレビューできる ③PPTX は確定デザインで**一度だけ**組めばよい（二度組みの無駄がない）。design-mock は design-spec のトークン（**PPTXで表現可能な範囲**）だけで描く。
>
> **step2〜5 の役割分担**: step2 のゲートは「構成・情報の載り方」、step3 は「デザインの方向」、step4 は「内容の最終確認とモックの再現度」、step5 は「仕上がりの品質」を見る場。
>
> **基準は visual-rubric.md に一本化**: step3・step4 は生成時にそれを目指し（design-directions は標準デザインのトークンを与えるだけ）、step5 は描画結果を同じ基準で検証する。スペックに従って生成しても描画結果の欠陥ゼロは自己保証できないため（はみ出し・重なり・コントラスト事故は画像でしか見えない）、**デザインが確定していても step5 は省略しない**。

# レビュー・ゲート（共通パターン）

各ステップ（step1〜step5）の成果物を生成・提示したら、**必ず**次の AskUserQuestion で停止する。`{ステップ名}` は実際の名称に置き換える。

```
AskUserQuestion({
  questions: [{
    question: "{ステップ名} の成果物を確認してください。次へ進んでよいですか？（ファイルを開いて確認・編集してから回答できます）",
    header: "{ステップ名}の確認",
    multiSelect: false,
    options: [
      { label: "承認して次へ",   description: "この成果物でOK。次のステップへ進む" },
      { label: "修正したい",     description: "修正してほしい点を伝えるので、このステップをやり直す" },
      { label: "自分で編集した", description: "ファイルを自分で直したので、読み直してから次へ進む" },
      { label: "中止",           description: "ここでワークフローを終了する" }
    ]
  }]
})
```

**分岐**:
- **承認して次へ** → 次のステップへ進む。
- **修正したい** → ユーザーに修正点を聞き、**このステップの成果物だけ**を作り直して再提示し、再びこのゲートに戻る。
- **自分で編集した** → 該当ファイルを `Read` で読み直し（必要なら下流の前提も更新）、次のステップへ進む。
- **中止** → 現状の成果物の場所を伝えてワークフローを終了する。

## step0: 準備（作業フォルダと入力の確認）

1. **作業フォルダの特定（`slide-plan.md` を自動検出）**
   - `Bash` で `pwd` を実行してカレントディレクトリを得る。
   - 次の順で `slide-plan.md` を `Glob` で探す（**カレントを聞き返さず、まず自動で探す**）：
     1. カレント直下 `slide-plan.md`
     2. `slide-maker/slide-plan.md`（`slide-maker` サブフォルダ）
     3. 直下1階層 `*/slide-plan.md`
   - **ちょうど1つ見つかった場合**: そのファイルのあるフォルダを `{作業フォルダ}` として**自動採用**し、「`{パス}/slide-plan.md` から始めます」と一言伝えてそのまま続行する（フォルダ選択は聞かない）。→ 例: Biz Vault で実行すると `slide-maker/slide-plan.md` を自動採用する。
   - **複数見つかった場合**: AskUserQuestion で使うものを選んでもらう。
   - **1つも見つからない場合**: AskUserQuestion で確認：
     ```
     options: [
       { label: "slide-maker に新規作成", description: "./slide-maker/ に slide-plan.md のテンプレートを作成する（おすすめ）" },
       { label: "ここに新規作成", description: "現在のフォルダ直下に slide-plan.md のテンプレートを作成する" },
       { label: "別フォルダを指定", description: "slide-plan.md がある（または作る）フォルダのパスを伝える" },
       { label: "中止", description: "終了する" }
     ]
     ```
   - 確定したフォルダを `{作業フォルダ}` とする。

2. **style-guide.md の用意**
   - `{作業フォルダ}/style-guide.md` が無ければ、このスキル同梱の `assets/style-guide.md` を読み込んで同内容を `{作業フォルダ}/style-guide.md` に書き出す（パスは `~/.claude/skills/slide-maker/assets/style-guide.md`。Windows では `C:/Users/<ユーザー>/.claude/skills/slide-maker/assets/style-guide.md`）。
   - 「デザインを変えたい場合は `style-guide.md` を編集してください」と一言伝える。

3. **slide-plan.md の確認**
   - **存在しない／作成した直後で未記入の場合**: 同梱の `assets/slide-plan.template.md` を `{作業フォルダ}/slide-plan.md` に書き出し、**ここでターンを終了する**（ゲートではなく完全停止）。「`slide-plan.md` を作成しました。内容（作成資料概要・参考フォルダ・枚数・想定読者・目的）を記入してから、また声をかけてください」と伝える。記入には時間がかかるため、AskUserQuestion ではなくターンを終える。
   - **記入済みの場合**: 内容を `Read` して要点（概要・枚数・想定読者・目的・参考フォルダ）をユーザーに短く要約提示し、「この内容で構成案を作ります」と伝えて step1 へ進む（このタイミングでは停止不要。step1 の生成後に停止する）。

## step1: 構成案（outline.md）

1. `slide-plan.md` を読む。
2. **参考フォルダがある場合**は内容のソースとして扱う：`Glob` でファイル一覧を取り、関連が深そうなものを数件 `Read` して事実を裏取りする。アクセスできない場合（例: `\\wsl.localhost\...` が読めない等）は、その旨を一言伝え、ブリーフのみから構成する。
3. `outline.md` を作成する。指定枚数に合わせ、各スライドについて：
   - **タイトル**（内容を端的に）
   - **メインメッセージ**（1スライド1メッセージ。1行）
   - **載せる内容**（箇条書き。図解・プロセス図にできる要素は「図解案」として明示）
   - 必要なら、参考フォルダで**裏取りできていない推測**には `（要確認）` を付ける（ハルシネーション防止）。
   - 想定読者と資料の目的に沿って、導入→本論→まとめの流れを設計する。
4. `outline.md` の内容をユーザーに提示する（全文または要約＋ファイルパス）。
5. **レビュー・ゲート**（共通パターン、`{ステップ名}`＝「構成案」）で停止する。

## step2: 構成モック（thumbnail-mockup.html）

目的は**構成の可視化**（各スライドに何がどう載るか・図解案・情報量の妥当性）。デザインの最終決定は step3 で行うため、ここでは `style-guide.md` のトーンを仮置きとして使う。

1. `outline.md`（承認済み構成）と `style-guide.md`（初期トーン）を読む。
2. **自己完結した HTML**（外部リソース参照なし＝CSS/フォント/画像はすべてインライン or 不使用）で、全スライドのサムネイル一覧を作る：
   - 各スライドを 16:9 のミニカードで表現し、グリッド（例: 2〜3列）に並べる。
   - 各カードに「スライド番号・タイトル・メインメッセージ・主要な箇条書き2〜4点・図解のラフ」を配置する。
   - 本文の完全な正確性より、**構成と情報量の妥当性**を優先する。
3. このHTMLを `{作業フォルダ}/thumbnail-mockup.html` に**必ず書き出す**（ブラウザで開ける恒久ファイルとして）。
4. 加えて **Artifact ツールで同じHTMLをレンダリング**してその場でプレビュー表示する（`favicon` は `"🖼️"`、`<title>` は資料タイトル）。Artifact が使えない場合は、書き出したファイルをブラウザで開くよう案内する。
5. **レビュー・ゲート**（`{ステップ名}`＝「構成モック」）で停止する。ここでの指摘は主に構成（載せる内容・図解案）に反映する。見た目の好みは step3 で扱う。

## step3: デザイン刷新（design-spec.md + design-mock.html）

デザインの確定は **HTML モック上で行う**（PPTXドラフトの設計に縛られない・反復が速い）。内容（outline.md のテキスト・枚数・順序）は一切変えない。

1. **標準デザインを読む**: スキル同梱の `assets/design-directions.md`。**毎回この標準デザイン（ダスティブルー×黒×白・角丸ゼロ・縦書き英語ラベル・淡青↔白の交互背景）を適用する**。デザイン方向の選択・確認は行わない（旧カタログは廃止済み）。
   - **例外**: ユーザーが明示的に「このデッキは別のデザインで」と見本（URL・画像・PDF・CSS・既存デッキ）を指定した場合のみ、design-directions.md の**リファレンス翻訳手順**でトークン化し、抽出結果を提示して確認を取ってから標準を上書きする。
2. **design-spec.md を書き出す**: 標準デザインのトークンを確定値として `{作業フォルダ}/design-spec.md` に書き、デッキ固有の値（各スライドの**縦ラベル語**＝そのスライドの主題を表す英語1語、右下タグの文言など）を埋める。**以降の工程では design-spec.md が style-guide.md より優先**。
3. **design-mock.html を生成**: thumbnail-mockup.html と同形式（全スライドのサムネイル一覧・自己完結HTML）を、design-spec のトークン**だけ**で描く（**PPTXで表現できない効果は使わない**）。`{作業フォルダ}/design-mock.html` に保存し、Artifact でプレビューする（`favicon` は `"🖼️"`）。
4. **レビュー・ゲート**（`{ステップ名}`＝「デザイン刷新」）で停止する。主目的は**標準デザインの全スライドへの当てはまり**の確認（PPTXとしての細部は step4/step5 で扱う）。

## step4: ドラフトPPTX（編集可能な PowerPoint）

確定したデザイン（design-spec.md + design-mock.html）に従って、PPTX を**一度だけ**組む。

1. **タイトルの確定**: `slide-plan.md` から適切なファイル名（資料タイトル）を導く。曖昧なら AskUserQuestion で1点だけ確認する。
2. **pptx スキルに委譲**して、**編集可能な** `.pptx`（テキストボックス・図形が後から編集できる、画像化されていないもの）を生成する：
   ```
   Skill({
     skill: "anthropic-skills:pptx",
     args: "{作業フォルダ} の outline.md（各スライドの内容）と design-spec.md（デザイントークン。無ければ style-guide.md）に従って、編集可能な PowerPoint を新規作成してください。全体の見た目は同フォルダの design-mock.html（無ければ thumbnail-mockup.html）を忠実に再現すること。{作業フォルダ}/<タイトル>_draft.pptx として保存してください。"
   })
   ```
   - 委譲先がフォルダ内のファイルを読めるよう、`outline.md` / `design-spec.md` / `design-mock.html` が `{作業フォルダ}` に揃っていることを確認してから呼ぶ。
   - **生成に使ったスクリプトはスクラッチパッドに保持する**（step5 の磨き上げで修正・再生成に再利用するため）。
3. 生成後、レンダリング（`render-pptx.ps1`）して全枚を提示し、design-mock との見た目の差分があれば説明する。
4. **レビュー・ゲート**（`{ステップ名}`＝「ドラフトPPTX」）で停止する。主目的は**内容の最終確認と design-mock の再現度**（細部の粗は step5 が拾う、と一言添える）。「修正したい」の場合は、内容修正なら `outline.md` を直して step1 へ、デザインの方向なら step3 に戻る。

## step5: ビジュアル磨き上げ（`<タイトル>.pptx`）

ドラフトの**内容は固定したまま、見た目の品質だけ**を1段引き上げて最終版を作る。

1. **基準の読み込み**: `{作業フォルダ}/visual-rubric.md` があればそれを、無ければスキル同梱の `assets/visual-rubric.md` を読む。基準は **A=欠陥（必ず直す）／B=原則（整列・階層・余白・反復・色・図解）／C=定型回避（AIっぽさ）** の3層。**パレット・トーンの判定基準は `design-spec.md`（無ければ `style-guide.md`）**。
2. **対象の画像化**（対象は `<タイトル>_draft.pptx`。画像なしで磨き上げ判定をしない。**step4 で生成したレンダリングがあり対象に変更が無ければ、それを再利用してよい**）:
   1. **PowerPoint COM（Windows + PowerPoint がある環境）**: 対象 pptx をスクラッチパッドにコピーし、同梱の `assets/render-pptx.ps1` を PowerShell で実行する（`-Path <コピー> -OutDir <scratchpad>/render`）。※PowerPoint で対象ファイルを開いているとロック競合するため、コピーを渡す。
   2. `soffice`（LibreOffice）+ `pdftoppm` がある環境ではそちらでも可。
   3. どちらも無い場合: python-pptx で座標リント（スライド外はみ出し・bbox 重なり・余白 <0.4"・フォント <10.5pt・パレット外の色）にフォールバックし、**「画像での目視はできていない」と明示**する。
3. **批評（fresh eyes）**: レンダリング画像をサブエージェントに渡し、ルーブリックの **A → B → C の順**でスライドごとに指摘させる（自分で作った直後は欠陥を見逃しやすい。画像の目視は非対話処理なのでサブエージェント委譲でよい）。指摘には「スライド番号・現象・修正方針」を付けさせる。design-spec.md のパスも渡す。
4. **修正して最終版を生成**: step4 の生成スクリプトを修正し、**`<タイトル>.pptx`（最終名）として再生成**する。ドラフトは上書きせず残す（比較・巻き戻し用）。スクリプトが無い場合は pptx を unpack-edit する。
5. **再検証**: 最終版を再レンダリングし、**A 層（欠陥）ゼロ**を確認する。修正サイクルは**最大2周**（B/C の軽微な指摘で無限に磨かない）。
6. 「何をどう直したか」の一覧（スライド番号 → 指摘 → 対応）と、可能ならビフォー/アフターの画像を提示する。
7. **レビュー・ゲート**（`{ステップ名}`＝「最終PPTX」）で停止する。このゲートの主目的は**仕上がりの確認**。「修正したい」で挙がった好みの調整は、`design-spec.md`（デザイン仕様）や `visual-rubric.md`（判定基準）に反映してから再実行すると、次回以降の案件にも効く。

## step6: 完了報告

- 生成した全ファイルを `Glob` で一覧表示する（`slide-plan.md` / `style-guide.md` / `outline.md` / `thumbnail-mockup.html` / `design-spec.md` / `design-mock.html` / `<タイトル>_draft.pptx` / `<タイトル>.pptx`）。
- 次のお勧めアクションを伝える：
  - `<タイトル>.pptx` を PowerPoint で開いて最終調整する。
  - 内容を変えたい → `outline.md` を編集して step1 から。デザインの方向を変えたい → step3 をやり直し（design-spec.md / design-mock.html を選び直し）。仕上げの基準を変えたい → `visual-rubric.md` を編集して step5 から。
