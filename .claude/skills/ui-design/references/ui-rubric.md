# UI の判定基準（ルーブリック）

> ui-design の **polish（磨き上げ）** と **audit（診断）** が使う。slide-maker の visual-rubric と同じ3層（A 欠陥・B 原則・C 定型回避）に、**使いやすさ（U）** を加えた。
> 好み・トーンは範囲外。`docs/ui/standard.md` と人間のレビューに委ねる。**standard.md で決めたことは、ここ（特に C 層）より優先する。**
> 案件ごとに基準を変えたいときは `docs/ui/rubric.md` に写して編集する（あればそちらが優先）。

## A. 欠陥 — 1つでも残れば不合格（多くは機械判定）

`capture.cjs` の `checks.json` / `summary.md` に候補が出る。**機械判定は候補**なので、画像で確かめてから直す（誤検知なら理由を書いて外す。例: 意図して横に動かす表）。

| ID | 欠陥 | 判定 |
|---|---|---|
| A-1 | はみ出し・文字の切れ | 機械（clipped・offscreen）＋画像 |
| A-2 | 狭い画面（375px）での画面全体の横スクロール | 機械（hscroll） |
| A-3 | 押せる物どうしの重なり | 機械（overlaps）＋画像 |
| A-4 | コントラスト不足（文字 4.5:1、大きな文字と部品の輪郭 3:1） | 機械（axe の color-contrast）＋ standard.md の表 |
| A-5 | フォーカスが見えない・キーボードで届かない | 機械（focus）＋ Tab で主要な導線を通す |
| A-6 | ラベル・名前の無い入力・ボタン・リンク | 機械（axe の label・button-name・link-name） |
| A-7 | 小さく、しかも隣と近すぎる押せる範囲（24px 未満で間隔も無い） | 機械（axe の target-size） |
| A-8 | 文字化け・豆腐（□）・ダミー文字（undefined・NaN・{{ }}）・壊れた画像 | 機械（dummy・brokenImages）＋画像 |
| A-9 | トークン外の色・段階外の文字サイズ | 機械（palette・typeScale） |
| A-10 | 画面のエラー（コンソールのエラー・4xx / 5xx・通信の失敗） | 機械（log）。今回の変更が原因でなければ既知として backlog へ |
| A-11 | その他の axe の違反（WCAG 2.2 AA） | 機械（axe） |

- 実環境の確認の QA-3（レスポンシブ）と QA-4（アクセシビリティ）は、A-1〜A-7 と A-11 に含まれる。基準の出典は `beam5-implement/references/ui-performance-verification.md`。
- 機械では分からない A 層（豆腐、画像の中の切れ、重なって読めない文字）は画像で見つける。

## B. 原則 — 磨き上げの中核（画像で判定する。直さないなら理由を書く）

画面ごとに、375px と 1440px の画像で判定する（768px は機械判定だけ）。

- **B-1 整列:** 見えない縦の線にそろっている。同じ種類の部品の左端・上端がそろう。
- **B-2 階層:**
  - 画面の主役が1つで、主ボタンも1つ。
  - 題名・見出し・本文の大きさの差が見える。
  - 視線が「題名 → 主役 → 補足」の順に流れる。
- **B-3 余白:**
  - 関係の強いものが近く、弱いものが遠い。
  - 余白は段階の値だけを使う。
  - 片側に寄った空白や、下だけ間延びした所が無い。
- **B-4 統一:** 同じ役割の部品は、全画面で同じ見た目・同じ位置にある（ボタン・表・題名・知らせ・ページ送り）。
- **B-5 色の規律:** 決めた色だけを使う。強調は1か所。色だけで意味を伝えない。
- **B-6 情報の密度:**
  - 業務の画面として、情報量と読みやすさが釣り合っている（詰めすぎ・空きすぎが無い）。
  - 数値は右揃え・桁区切り。表の列が細すぎて1〜2字ずつ折れていない。
- **B-7 日本語の組み方:**
  - 行間と、1行の文字数（本文 40 字前後まで）が守られている。
  - 見出しやボタンが不自然な位置で折れていない（「削／除」のような割れ方）。1〜2字だけの行が無い。
  - 全角・半角がばらついていない。
- **B-8 状態の見せ方:** 読み込み中・0件・エラー・完了・権限なしが、screens.md で決めたとおりに見える。

## U. 使いやすさ — 導線を1手ずつ歩いて判定する

`capture.cjs` が導線（journeys）を動かして撮った画像を、1手ずつ見る。**各手で次の4つを問う**（認知的ウォークスルー）。

- **U-1:** 利用者は、次に何をすべきか分かるか。
- **U-2:** そのための操作が目に入るか（探さないと見つからない／スクロールの先に隠れている、が無いか）。
- **U-3:** 操作の名前から、押した結果が予想できるか。
- **U-4:** 操作の後、進んだこと・成功したことが分かるか。

加えて、導線と画面全体で次を見る。

- **U-5 手数:** 主要な導線が、screens.md の予算に収まる（`checks.json` の hands / budget）。
- **U-6 やり直し:** 取り消す・戻ることができる。取り消せない操作の前には確認がある。
- **U-7 失敗を防ぐ:** 入力の制約・既定値・確認がある。エラーには「何が違うか」と「どう直すか」が書いてある。
- **U-8 覚えなくてよい:** 選択肢を見せる。入力済みの値をエラーで消さない。
- **U-9 一貫した言葉:** 同じ操作は同じ言葉。完了の知らせも同じ言葉（「保存する」→「保存しました」）。
- **U-10 利用者の言葉:** システムの用語（ID・レコード・null・コード値）を利用者に見せない。

## C. 定型回避 — AI っぽさの排除（見つけたら直す。standard.md で決めたことは対象外）

- **C-1:** 意味のないグラデーション・ぼかし・影。
- **C-2:** 内容に関係なく、どの情報も同じ角丸カードに入れて並べる。
- **C-3:** 見出しの上の英字の小ラベル・全部大文字のラベル・題名の下の飾りの罫線。
- **C-4:** 中黒でつないだ補足（A · B · C）、ボタン名の「→」、順番ではないものへの番号付け（01 / 02 / 03）。
- **C-5:** 全部の要素がふわっと現れる、全部のカードが乗せると動く。
- **C-6:** 飾りのアイコン・絵文字を多用する。
- **C-7:** 中身の無い売り文句（「かんたん」「スマートに」「次世代の」）・大げさな見出し。
- **C-8:** 製品と関係なく、ありがちな配色を使う（クリーム色の地にテラコッタ色、黒地に蛍光色の一色）。
- **C-9:** 等幅の書体を、コードでない小さなラベルに使う。

出典: frontend-design（Anthropic の公開スキル。Biz Vault の写し）にある「AI が作った見た目に出やすい癖」と、slide-maker の visual-rubric の C 層。本文は写さず、日本語の業務画面向けに書き直した。

## 指摘の書き方（findings.json）

```json
{ "items": [
  { "id": "F-01", "screen": "SCR-01", "state": "default", "width": 375, "layer": "A", "rule": "A-2",
    "issue": "375px で画面全体が横に動く（金額の欄が 600px で固定）", "fix": "欄を max-width: 100% にする",
    "status": "fixed" },
  { "id": "F-02", "journey": "J-01", "step": 3, "layer": "U", "rule": "U-4",
    "issue": "保存しても何も表示されず、保存できたか分からない", "fix": "一時的な知らせ「保存しました」を出す",
    "status": "fixed" },
  { "id": "F-03", "screen": "SCR-02", "layer": "U", "rule": "U-5",
    "issue": "申請までに5手かかる（予算3）", "fix": "一覧から直接申請できるようにする",
    "status": "proposal", "reason": "導線を変えるので、別の機能として power で行う" }
] }
```

- **書く項目:** 画面 ID（導線なら導線 ID と手の番号）・状態・幅・層・基準の ID・現象・直し方を必ず書く。
- **status（結果）:**
  - `fixed`: 直した。
  - `kept`: 残した（`reason` 必須）。
  - `backlog`: `docs/ui/backlog.md` へ送った。
  - `proposal`: 導線・機能の変更が要る提案（直さない）。
- **まとめ方:** 1つの原因から出た指摘は1件にまとめる（同じ部品の同じ問題を、画面ごとに数えない）。

## 運用ルール

1. **画像なしで B・U・C を判定しない。** A は機械判定と画像の両方で見る。
2. **判定の順は A → B → U → C。** A が残っている画面の B 以降は後回しにしてよい。
3. **直すのは見た目と文言だけ。**
   - 直してよいもの: トークン、部品の見た目、文言、状態の表示。
   - 導線・API・データ・権限を変える直しはしない（`proposal` にして backlog へ）。仕様の変更は `/revise`。
4. **直したら撮り直す。** A = 0 を確かめ、テスト（E2E を含む）・型チェック・lint を通す。テストを書き換えないと通らない直しは、理由を報告に書く。
5. **周回は最大2周。** 2周で残った B・U・C は理由を書いて backlog へ送る（完璧より一貫性）。人間から受けた直しの指示は、この上限に数えない。
6. **好みの問題は直さない。** 色味・余白・言い回しの好みは、人間の確認（review.html）に回す。
7. **既存改修（power）では今回触った画面だけを直す。** 元からある問題は backlog へ送る（今回の変更が原因なら直す）。
