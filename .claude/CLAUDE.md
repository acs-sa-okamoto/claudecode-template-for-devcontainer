## ディレクトリ構造

本プロジェクトは beam ワークフローで生成・管理される。主要ディレクトリ：

```
.
├── CLAUDE.md                         # このファイル
├── docs/
│   ├── rule/                         # 開発ルール（AIが常時参照）
│   │   └── ai-security-guardrails.md # セキュリティ・ガードレール
│   ├── spec/{要件名}/                # 要件フェーズの成果物
│   │   ├── product-requirements.md   #   PRD（to-prd）
│   │   ├── note.md                   #   コンテキストノート（beam1）
│   │   ├── requirements.md           #   要件定義（beam2）
│   │   ├── user-stories.md           #   ユーザーストーリー（beam2）
│   │   ├── acceptance-criteria.md    #   受け入れ基準（beam2）
│   │   ├── prep.md                   #   ユーザー準備タスク（beam2 生成・beam3 が設計確定で更新）
│   │   └── design/                   #   設計文書（beam3）
│   │       ├── architecture.md
│   │       ├── dataflow.md
│   │       ├── interfaces.ts
│   │       ├── database-schema.sql
│   │       └── api-endpoints.md
│   └── tasks/{要件名}/               # タスク分解（beam4）
│       ├── overview.md
│       └── TASK-XXXX.md
├── data/                             # ⚠️ 予約済み（Git 管理外）。下記の注意を必読
│   └── tasks.db                      # タスク管理 SQLite（beam4）
└── src/                              # 実装コード（beam5）
```

> ### ⚠️ `data/` は使用済み（予約フォルダ）。製品のデータを置いてはならない
>
> `data/` は **beam のタスク管理 SQLite（`tasks.db`）専用**に予約されており、**ディレクトリごと `.gitignore` で除外**されている（`.gitignore` の `/data/`。「Local development database directory」）。`.beam/dashboard/` のタスクビューアがこの `data/tasks.db` を読む。
>
> **したがって、コミットが必要な製品のソースデータ（CSV・JSON・辞書・マスタ等）を `data/` に置いてはならない。** 置くと `.gitignore` に弾かれて Git に入らず、**ローカルでは動くのに本番ビルドだけがデータ不在で失敗する**（原因が分かりにくい類の事故）。実際にこの事故が起きたことがある。
>
> - **コミットが必要な入力データ** → `content/` などの専用ディレクトリを用意する（設計で決める）
> - **ビルドで生成される出力** → `public/` など（Git 管理外）
> - **マシンローカルな作業用 DB** → `data/`（Git 管理外）
>
> なお `.gitignore` のパターンは **`/data/`（先頭にスラッシュ）**でなければならない。無印の `data/` はスラッシュを含まないため **どの階層の `data/` にもマッチ**し、`src/data/` や `docs/data/` まで黙って除外してしまう。

> **ルート直下の `package.json` / `tsconfig.json` / `.prettierrc` は「既定のスターター」です**（TypeScript/Node 向け＝pnpm・ESM・strict・Vitest・Prettier）。**特定の言語・スタックを限定するものではありません。** 設計（beam3）で別のスタックを選んだ場合（例: Python/FastAPI など）は、これらを置き換え・削除して構いません。`.beam/dashboard/`（タスクダッシュボード）は独立した設定を持つため、ルートのこれらとは無関係です。

> ### ⚠️ スタックを置き換えるときも壊してはならない3つの不変条件
>
> スターターを別スタックへ差し替えるのは自由だが、以下は**どのスタックでも守る**。いずれも「ローカルでは動くのに本番だけ壊れる」類の事故に直結する。
>
> **1. lockfile をコミットする（`pnpm-lock.yaml`）**
>
> 依存を変えたら必ず `pnpm install` を実行し、生成された lockfile をコミットする。lockfile が無いと **Vercel はパッケージマネージャを判定できず、`packageManager` の pnpm 指定を無視して `npm install` にフォールバックする**（[Vercel の検出順](https://vercel.com/docs/functions/runtimes/node-js#node.js-dependencies)に明記）。結果としてローカルと本番、あるいは本番の2回のビルドで別バージョンが入り得る。ガードレール P1「依存関係は lockfile で固定」に反する。
>
> **2. Node のバージョンを閉じた範囲で指定する**
>
> `engines.node` は `"24.x"` のように**上限を閉じる**。`">=22"` のような開いた範囲は、Vercel では**常に「利用可能な最新メジャー」に解決される**（公式ドキュメントの表で `>=20.0.0` → 最新 24.x と明記）。つまり新メジャーが公開された瞬間に、コミットを何もしていないのに実行環境が変わる。ある日突然ビルドが壊れて直前のコミットに原因がない、という最も追いにくい壊れ方をする。
>
> **3. `engines.node` と DevContainer の Node を一致させる**
>
> 現在は両方 **24** に固定している（`engines: "24.x"` / `devcontainer.json` の node feature `"version": "24"` / Dockerfile の `javascript-node:24`）。DevContainer 側を `"lts"` のような可変指定にすると、LTS が上がった時点でローカルだけ別バージョンになり、`engines` との不一致が黙って発生する。**片方を変えるときは必ずもう片方も変える。**

## 開発ワークフロー（beam）

このプロジェクトは段階的に進める。各フェーズの成果物は前フェーズを入力とする。

| 順序 | スキル | 役割 | 主な成果物 |
|---|---|---|---|
| 1 | `beam1-tasknote` | コンテキスト収集 | `note.md` |
| 2 | `beam2-requirements` | 要件定義（EARS） | `requirements.md` ほか |
| 3 | `beam3-design` | 技術設計 | `design/*` |
| 4 | `beam4-tasks` | タスク分解・SP見積もり | `tasks.md`, `TASK-XXXX.md` |
| 5 | `beam5-implement` | 実装 | `src/` のコード |

- 各フェーズの全項目には**信頼性レベル（🔵 確実 / 🟡 妥当な推測 / 🔴 推測）**を付す。
- ファイルパスは**プロジェクトルートからの相対パス**で記載する（絶対パス禁止）。

## セキュリティ原則（必読）

このプロジェクトでコードを書く際は、以下のセキュリティ・ガードレールを必ず遵守する。

@docs/rule/ai-security-guardrails.md

**最低基準（P0 = 絶対遵守。違反は実装完了とみなさない）:**

- 認証・認可は必ずサーバー側で実施する（IDOR/BOLA 対策、所有者検証を含む）。
- シークレット（APIキー・秘密鍵・トークン）を直書きせず、Git／クライアントに含めない。
- インジェクション対策（ORM/Prepared Statement、`eval()`禁止、出力エスケープで XSS 防止）。
- 暗号・ハッシュを自前実装しない（パスワードは bcrypt/Argon2）。
- 機密情報・個人情報をログに出力しない。

詳細・P1（原則）・完了条件は上記インポートファイルを参照。**適用しないと判断した規則は、黙って飛ばさず「なぜ不要か」を一言述べること。** セキュリティ要件と機能要件が衝突する場合は、勝手に決めず人間に確認すること。

## 完了条件（Definition of Done）

実装は以下をすべて満たして「完了」とする。

- [ ] 要件（`docs/spec/{要件名}/requirements.md`）を満たしている。
- [ ] テスト・型チェック・Lint がすべて成功している。
- [ ] **P0 セキュリティ要件に違反していない。** P1 の逸脱がある場合は理由が明記されている。
- [ ] 関連するタスク（`docs/tasks/{要件名}/`）の完了条件を満たしている。
- [ ] **要件適合レポート（`docs/tasks/{要件名}/conformance-report.md`）で全要件（REQ/NFR）が ⭕、または正当な 🟢（タスク不要）であり、❌ が 0 件である。**
- [ ] **（デプロイ工程がある場合）リリース工程の検証**：モックDBや自前 migrate のテストでは検知できない「本番（実環境）でのみ出る不具合（マイグレーション漏れ・必須環境変数・ビルド/デプロイ設定差）」に対し、**(1) デプロイ設定の静的チェック**（migrate/build 手順・必須 env が揃っているか）と、**(2) 自前セットアップせず実環境を叩く薄いスモークテスト**（資格情報が無ければ安全側にスキップ）を用意している。該当しない場合は理由を一言述べる。
- [ ] （CI ゲート）依存脆弱性チェック・シークレットスキャンが成功し、人間レビューが完了している。

> **AI 生成コードは人間がレビューし、最終責任を持つ。AI は最終承認者ではない。**
