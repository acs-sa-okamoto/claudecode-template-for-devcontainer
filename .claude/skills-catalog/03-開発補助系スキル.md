# 開発補助系スキル（8個）

「ゼロから開発」（to-prd / beam 系）と「途中から開発」（power 系）の両ワークフローから**内部的に呼び出される共有エンジン**、およびワークフローを横断して使う**単独ツール**のグループ。いずれも**単独での実行も可能**。

## 前提用語（初見の方向け）

| 用語 | 意味 |
|---|---|
| beam | ゼロからアプリを作る開発ワークフロー（要件定義→設計→タスク分解→実装） |
| power | 既存システムに機能を追加する開発ワークフロー |
| `{要件名}` / `{機能名}` | プロジェクト名（＝リポジトリ名）／power で追加する機能の名前。成果物の保存先フォルダ名になる |
| TASK-XXXX | タスク分解フェーズが発行する実装タスクの ID（例: TASK-0003） |
| tasks.db | タスクの状態（ready / in_progress / done 等）を管理する SQLite データベース |
| SP（ストーリーポイント） | 工数（時間）ではなく、タスクの相対的な規模・複雑さを表す見積もり値 |
| 信頼性レベル | 成果物の各項目に付くラベル。🔵 確実 ／ 🟡 妥当な推測 ／ 🔴 推測 |

## 一覧

| スキル | 一言でいうと | 主な呼び出し元 |
|---|---|---|
| tdd-implement | 1タスクをテスト駆動で実装する | beam5 / power5（自動） |
| direct-implement | 1タスクの環境構築・設定作業を実行する | beam5 / power5（自動） |
| estimate-storypoint | タスクの規模を SP で見積もる | beam4 / power4 / scope-options / revise（自動） |
| code-review | コード変更を多観点でレビューする | 人間 / beam5・power5・power6（自動） |
| scope-options | 1つの要望から松竹梅＋フルの4案を導出・比較する | beam2 / beam4（自動） |
| service-boundary | サービス分割の要否を判定する | beam3（自動） |
| revise | 確定済み仕様の変更を影響分析つきで反映する | 人間 |
| skills-update | このリポジトリの同梱スキルをテンプレートの最新に更新する | 人間 / power step1-0・power0（自動） |

## tdd-implement

### 目的
1つの実装タスク（TASK-XXXX）を**テスト駆動開発（TDD）**で確実に実装する。「テストを先に書いて失敗させる（Red）→ 通す最小実装（Green）→ 品質改善（Refactor）→ 完全性検証」の順で進め、**受け入れ基準1つにつきテスト1つ以上**（テストの無い受け入れ基準を残さない）を機械的に保証する。モック・スタブで「通しただけ」にすることを禁止し、実データ・実 DB で動くコードを作る。あわせて、**実装中に見つけたバグ（受け入れ基準由来のテストに無かったもの）は、直す前にそれを検知するテストを1本足す**——カバレッジ率のためではなく、AI は同じ種類のミスを繰り返すので、一度テストで固定すればその形は二度と通らなくなるため。

### 使用法
- 通常は **beam5 / power5（実装フェーズ）から自動で呼ばれる**（`task_type = TDD` のタスクが対象）。人間が直接呼ぶ必要はない
- 単独実行も可能: `/tdd-implement {要件名} {TASK-ID}`（例: `/tdd-implement task-bridge TASK-0003`）
- 前提: タスク分解（beam4 / power4）が済んでいて `docs/tasks/{要件名}/TASK-XXXX.md` が存在すること

### 生成物
- **テストコードと実装コード**（プロジェクトの `src/`・`tests/` 等、既存構造に従って配置）
- 実装記録一式（`docs/implements/{要件名}/{TASK-ID}/` 配下）:
  - `requirements.md` — このタスク用に詳細化した要件
  - `testcases.md` — 洗い出したテストケース一覧
  - `memo.md` — Red / Green / Refactor の作業ログ
  - `verify-report.md` — 受け入れ基準の網羅率と完了判定（✅／⚠️／❌）
- tasks.db の status 更新（完了時 `done`）

## direct-implement

### 目的
テスト駆動になじまない**準備系のタスク**——環境構築・設定ファイル作成・依存パッケージ導入・DB 初期化・ビルド設定など——を「setup（実施）→ verify（動作確認）」の2段階で実行する。やったことと確認結果を必ず記録に残し、シークレット（API キー等）を直書きしない等のセキュリティ原則を守る。

### 使用法
- 通常は **beam5 / power5 から自動で呼ばれる**（`task_type = DIRECT` のタスクが対象）
- 単独実行も可能: `/direct-implement {要件名} {TASK-ID}`
- 前提: tdd-implement と同じ（タスク分解済み）

### 生成物
- 設定ファイル・環境ファイル等の成果物（`.env.example`・各種 config など）
- 実施記録（`docs/implements/{要件名}/{TASK-ID}/` 配下）: `setup-report.md`（何をしたか）／`verify-report.md`（動作確認の結果と根拠）
- **README.md への追記**（環境変数・設定手順・トラブルシューティング）と **CLAUDE.md への追記**（判明した開発コマンド）
- tasks.db の status 更新

## estimate-storypoint

### 目的
実装タスクの規模を、工数（○時間）ではなく**相対的なストーリーポイント**で見積もる。フィボナッチ数列は使わず小数第一位まで算出し（例: 2.8）、あわせて**不確実性バッファ**（仕様の曖昧さを%で表現）と**複雑度**（Low〜Very High）を返す。チーム共通のアンカー（基準タスク）との相対比較で判断するため、見積もりのブレが小さい。

### 使用法
- 通常は **beam4 / power4（タスク分解）、scope-options（4案比較）、revise（改定後の再見積もり）から自動で呼ばれる**
- 単独実行も可能:
  - ファイル指定: `/estimate-storypoint docs/tasks/foo/TASK-0001.md`
  - インライン: タスク内容（タスク名・実装詳細・テスト要件）をそのまま渡す。複数タスクの一括見積もりも可

### 生成物
- **JSON のみ**（ファイルは作らない。記録は呼び出し元が行う）:
  - `story_point`（小数第一位）／`buffer_percent`（不確実性%）／`complexity`／`reason`（根拠の説明）
- 13.1 SP 以上は「タスク分割を推奨」、バッファ 51% 以上は「要件再確認推奨」と明記される

## code-review

### 目的
コード変更を**多観点で徹底レビュー**し、信頼できる指摘だけを残したレポートを作る。観点はセキュリティ（P0/P1 ガードレール）・ロジックバグ・非同期/競合・エラー処理・既存コードとの整合・実データ整合・要件適合・可読性・設計健全性・パフォーマンス・テスト/CI・**ビルド/デプロイ設定**（差分が `package.json`・設定・CI・`.devcontainer` 等を触るときだけ効く条件付き観点）の12系統。見つけた指摘は**一度疑ってかかる品質検証**（本当にバグか？文脈で否定できないか？）を通してから、重大度（CRITICAL〜LOW）と信頼性（🔵🟡🔴）付きで報告する。誤検知の洪水を防ぐ設計。

> **このスキル自身の限界を設計原則に明記している点が重要**: **AI が書いたコードを同じ AI がレビューすると、両方に同じ前提＝同じ盲点が入る**。敵対的検証はこれを緩和するが消しはしない。そのため **build / test / typecheck / lint のような機械的検査は必ずこのスキルより前に通す**（beam5・power5・power6 はそう構成されている）。レビューは機械的検査の代わりではなく、**機械が捕まえられないものを見るため**に使う。この限界が具体的に出るのが coding-principles の **E-1〜E-4（AI が繰り返す機能バグ）**で、一見動くコードに見えるためレビューでは安定して捕まらない——該当したら修正提案に**リグレッションテストの追加まで含める**。

### 使用法
- レビュー対象を自動判別する。いずれも人間がそのまま実行できる:
  - `/code-review 123` — GitHub の PR 番号（他人の PR も可）
  - `/code-review feature/foo` — ブランチをベースブランチと比較
  - `/code-review` — ローカルの未コミット変更
  - `/code-review src/api/` — 特定パスの変更
- **beam5（各実装フェーズ）・power5（各実装フェーズ）・power6（検証フェーズ＋PR 差分の再レビュー）から自動で呼ばれ**、「CRITICAL/HIGH がゼロになるまで修正（最大2ラウンド）」のループに使われる

### 生成物
- レビューレポート: `docs/reviews/review-{対象}-{日付}.md`（`docs/` が無いリポジトリでは `reviews/`）
  - 重大度別サマリー／指摘一覧（場所 `file:line`・根拠・修正提案・信頼性）／要件適合表（beam/power プロジェクトの場合）／総評
- **コードは一切変更しない**（読み取り専用）。GitHub への投稿も既定では行わない（依頼時のみ）

## scope-options

### 目的
1つの要望から「**ミニマム案／要望案／リッチ案／フル案**」の4つのスコープ案を**系統的に**導出し、SP 比較と案の選択まで支援する（見積もりの松竹梅提案）。AI の思い付きに依存しないよう、案の導出は固定規則——ミニマム＝全ユーザーストーリーを最小で1本通す構成、リッチ＝強化チェックリスト、フル＝発見チェックリスト＋スコープ外の再評価——と、機能ごとの Kano 分類（当たり前品質／魅力的品質などを質問→表引きで判定）に基づく。すべての判断に出典 ID を必須化している。

### 使用法
- 通常は **`/beam` 開始時に「4案提案を含める」を選ぶと自動で動く**:
  - beam2 から `define`（機能×4案マトリクスの作成。コアジョブ確認や Kano 確認の質問が数問入る）
  - beam4 から `estimate`（要望案の正式見積もりを基準に他3案の SP を導出→比較表→**どの案で実装するかを選択**）
- 要望案以外を選ぶと、要件・設計・タスクが選択案として作り直される（再整列）。PRD・ヒアリング記録・prep のチェック状態は保持される
- 単独実行: `/scope-options define {要件名}` ／ `/scope-options estimate {要件名}`

### 生成物
- `docs/spec/{要件名}/scope-options.md`:
  - 機能棚卸し＋Kano 分類表／**機能×4案マトリクス**（各セルに 採用レベル・理由・出典）／各案のコンセプト／整合チェック結果／**SP 比較表**（案ごとの合計±バッファ・精度内訳 🔵継承/🟡再見積/🔴新規）／**選定記録**（選んだ案と再整列の進捗）

## service-boundary

### 目的
プロダクトの機能群を**サービス境界（Bounded Context）**に整理し、「マイクロサービスに分けるべきか、1つのアプリ内のモジュール分割で足りるか」を判定する。**既定はモジュラモノリス**（1デプロイ＋内部モジュール境界）で、物理的な分割（別リポジトリ・別デプロイ）は明確な正当化があるときだけ薦める——つまり**過分割を防ぐブレーキ**として働く。「別製品級」と判定した境界は「別プロダクトとして PRD から分けるべき」というシグナルも出す。

### 使用法
- 通常は **beam3（技術設計）から自動で呼ばれ**、結果が `architecture.md` の「サービス境界／モジュール構成」節に取り込まれる
- 単独実行も可能: `/service-boundary {要件名}`（beam の成果物を読む）、または機能一覧を直接渡す
- 判定に必要な観点（アクター・変更理由・データの整合性要件）が不足していれば1つずつ質問される

### 生成物
- **境界マップ**（チャットに提示。beam3 経由なら architecture.md に反映）:
  - 機能棚卸し表／推奨構成（境界ごとの責務・所有データ・結合度）／境界間の連携方式／BFF の要否／物理 or 論理の判定／将来の独立サービス候補（引き金条件付き）／**却下した分割候補と理由**
- 独立したファイルは作らない（呼び出し元が記録する）

## revise

### 目的
一度確定した仕様・設計への**変更を安全に反映する「再入口」**（beam / power 共通）。変更が波及する範囲を、フロントマター等の新しいメタデータではなく**既存の成果物**（要件カバレッジ行列・適合レポート・タスクの要件リンク等）から ID レベルで導出し、🔵確実／🟡妥当な推測／🔴推測（＝「影響あり」という判断の確からしさ）で提示。承認を得てから、上流ドキュメントの更新→下流の部分再生成→影響タスクの再キュー化（ダッシュボードに「更新あり」表示）まで行う。**再実装そのものはしない**（実装フェーズに委譲）。

### 使用法
- 意図先行（推奨）: `/revise REQ-05 通知の集約ウィンドウを5秒から10秒に変えたい`
- 事後: 仕様ファイルを手で編集した後に `/revise`（git 差分から変更点を検出して確認）
- 実装フェーズ・検証フェーズは「仕様だけが新しい」状態を検知すると `/revise` の実行を促す（自動検知・手動実行）
- ID は番号維持・削除は廃止マーク・追加は末尾連番（リンクを壊さない）

### 生成物
- 更新された仕様・設計・TASK ファイル、tasks.db の再キュー
  - **行の書き直し**: TASK-*.md を書き換えたタスクは、その内容で **DB の行も書き直す**（タスク名・要約・SP など。状態はここでは変えない）。ファイルだけ直して DB を放っておくと、ダッシュボードに「更新あり」が出ているのに内容の列は古い要約のまま、という紛らわしい状態になるため
  - 状態遷移（書き直しのあと）: `done` / `in_review` → `ready`（ダッシュボードに「更新あり」）。`in_progress` は警告して個別確認、`ready` は状態を変えない
  - 廃止: 原則 `is_deleted = 1`（論理削除＋TASK ファイルに廃止マーク）。ただし**実装済みコードの撤去が必要な廃止は is_deleted ではなく「削除タスク」を新規起票**する
  - **★例外: 再実装を担う下流タスクが別に存在する場合は再キューしない**（例: power 機能が同じ変更を実装予定で、beam 側の done タスクが同じ要件を指す）。二重積みを避けるため beam タスクは `done` のまま据え置き、改定記録の「再キューしたタスク」節に担い手（どの機能のどの TASK か）を名指しする
- 適合レポートの該当行を「⏳ 要再検証」化
- **改定記録**: `docs/revisions/{日付}-{変更概要}.md`（変更前後・影響リスト・実施アクション・残作業）
- **Git 反映**（対象の系統で方式が変わる。git 管理外ならスキップ）
  - **power 機能**: `feature/{機能名}` ブランチ上で変更一式（仕様・設計・TASK・改定記録）を `revise: {対象ID} {要約}` としてコミット（**tasks.db と `.env` は含めない**）
  - **beam プロジェクト（通常）**: 自分ではコミットせず **beam-sync** を呼び、改定用ブランチ `revise-{slug}-{要件名}`（トランク基点）へのコミットとトランクへの PR を作らせる
  - **交差ケース（対象は beam の仕様だが、引き金が power 機能）**: beam-sync を呼ばず、いま居る power のスタックの段へ直接コミットする（要件改定と実装を同じマージ単位に載せるため）

## skills-update

### 目的
**いま作業しているリポジトリに同梱されているスキル一式を、テンプレートリポジトリの最新に更新する**単独ツール。スキルは各リポジトリに同梱して配る方式なので、**放っておくと配布先ごとに古くなり、しかも古いことに誰も気づけない**（バージョンという概念が無いため）。その唯一の更新口がこれにあたる。

対象は `.claude/skills/`（スキル一式）・`.claude/skills-catalog/`（このカタログ）・`docs/rule/ai-security-guardrails.md`（セキュリティ基準。スキル外に配られる派生コピーなので、外すと「ここだけ古い」が再発する）。

### 使用法
- `/skills-update`（更新を適用）／ `/skills-update --check`（**上書きせず差分だけ見る**）
- 典型的な場面: **オーケストレーター（power / beam）自体を直したので作業中のリポジトリに反映したい**／運用中に改良したスキルを先に取り込みたい／**beam で作ったリポジトリ**を久しぶりに触る（beam には power のような起動時の自動更新が無いため、ここが更新口になる）
- power では起動時（step1-0）に同じ処理が自動で走るので、**power を通す限りは明示的に呼ばなくてよい**

### ふるまい（3つの約束）
- **テンプレートが正本**。差分のあるファイルだけを上書きする。「持っているか」「新しいか」は判定しない——正本が1つで、配布先が「より新しい／より正しい」版を持つ筋書きが存在しないため。**条件を増やすほど判定漏れの穴ができる**（実際に「一部だけ古い」で取り残された前例が2件ある）
- **リポジトリ独自に足したスキルは消さない**。テンプレートに無いファイルは警告として一覧するだけで、削除は人間が判断する
- **取得に失敗しても止まらない**（fail-open）。テンプレートは非公開なので認証が要るが、認証切れやオフラインで作業全体が止まる方が害が大きい

### 注意
- **リポジトリ側でテンプレート由来のスキルを直接編集していた場合、その変更は上書きで失われる**（`.claude/` は Git 管理下なので `git diff` で確認・復元できる）。スキルを恒久的に変えたいなら、**正本を直してテンプレートへ同期する**のが正しい経路
- **いま実行中のスキルには効かない**。スキルの本文は呼び出した時点で読み込まれるため、更新しても**動いているものは古い指示のまま**進む。ファイル自体は新しくなっているので、**次に呼び出すときから**新版になる。進行中のワークフローがあるなら一度区切って呼び直す
- 更新は機能の差分に混ぜず、**`chore: sync skills from template` の単独コミット**に分ける

### 生成物
- 更新された `.claude/skills/`・`.claude/skills-catalog/`・`docs/rule/ai-security-guardrails.md`（差分のあったものだけ）
- 追加・更新されたファイルの一覧と、テンプレートに無いファイルの警告
