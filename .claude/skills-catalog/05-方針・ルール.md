# 方針・ルール — スキルが参照するリファレンス（9個）

ここまでの4ファイルは**スキル**（人間が `/名前` で起動するもの）の説明だった。このファイルは毛色が違い、**スキルが実行時に読み込む「基準・ルール」のドキュメント**をまとめる。人間が直接起動するものではなく、各スキルが「判断のよりどころ」として参照する。すべてスキルのフォルダ内に同梱されているため、テンプレートから作った新規リポジトリや、レガシーへのスキル一式コピーにも一緒に配布される。

## 前提用語（初見の方向け）

| 用語 | 意味 |
|---|---|
| リファレンス | スキルが実行時に読む基準・ルールの文書（本ファイルの対象）。SKILL.md とは別に `references/` や `rules/` に置かれる |
| P0 / P1 | セキュリティ規則の優先度。P0＝絶対遵守（違反＝一発アウト）／P1＝原則（逸脱時は理由明記） |
| 信頼性レベル | 成果物の各項目に付くラベル。🔵 確実 ／ 🟡 妥当な推測 ／ 🔴 推測 |
| Kano モデル | 機能を「当たり前／一元的／魅力的」等に分類し、顧客満足への効き方を見分ける品質分類の考え方 |
| Bounded Context | サービス/モジュールの境界。「ここからここまでが1つのまとまり」という業務上の区切り |
| スコープ4案 | 1つの要望から作る ミニマム／要望／リッチ／フル の4つの案（scope-options が生成） |
| beam / power | ゼロから開発／既存に機能追加 の2つのワークフロー（→ 01・02 参照） |

## coding-principles.md

### 一言でいうと
コードを**書く・直す・レビューするときの「判断基準の語彙集」**。各技法に ID（A-1 等）と確立した名前（ガード節・デメテルの法則・DRY 等）を付け、指摘や記録では ID か技法名で引用する。機械的なチェックリストではなく、判断のための共通言語。

### 場所
`code-review/references/coding-principles.md`

### 参照するスキル・タイミング
- **code-review** — レビュー時、H（可読性）・I（設計）レンズの語彙の出典。指摘の根拠を技法 ID で引用する
- **tdd-implement** — Refactor フェーズで「どの改善の手を打つか」のチェックリスト、コメント方針（A-1）の根拠
- **beam5-implement**（rules）— 重複排除の判断（C-2 DRY と C-3/C-4 の張力）
- **service-boundary** — クラス/関数レベルは本ドキュメント、境界レベルは microservice-boundary-rules と役割分担（相互参照）
- **power0-onboard** — レガシー用に生成する CLAUDE.md に「ベースライン」として記載

### 主な内容（技法 ID 体系）
- **A. 読みやすさ** — A-1 背景コメント（Why を書く）／A-2 要約変数／A-3 説明変数とデメテルの法則／A-4 意図の関数化／A-5 ガード節（早期リターン）／A-6 驚き最小の原則
- **B. 変更に強い構造** — B-1 不変優先／B-2 実装を見ずに使える公開面（カプセル化）／B-3 境界での隠蔽（Facade/Factory）／B-4 コンポジション優先／B-5 依存性注入(DI)／B-6 依存性逆転(DIP)／B-7 型で守る(Generics)
- **C. 凝集・結合と抽象化の張力** — C-1 高凝集×疎結合（**最優先原則**）／C-2 DRY ↔ C-3 AHA（早すぎる共通化を避ける）／C-4 三度目の法則／C-5 YAGNI
- **D. アーキテクチャ指針** — D-1 依存は中心へ（Clean/Onion）／D-2 読み書き分離(CQS)／D-3 契約から生成（Contract-First）
- **E-a. LLM がやりがちな「書き方」の逸脱**（ID なし）— 過剰コメント／早すぎる共通化／浅いラッパー乱造／巨大関数／不要な防御的コード／既存パターンの無視。各項目が A〜C の ID を参照
- **E-b. LLM が繰り返す「機能バグ」の反復パターン（E-1〜E-4）** — **E-1 多重コードパスの不整合**（★最頻出。本番/モック・feature flag・キャッシュ有無など経路が2つ以上あるとき片方だけ直す）／**E-2 契約フィールドの取得漏れ**（戻り値に足したが取得側の射影・SELECT・DTO 変換に足し忘れ、型は通るのに常に undefined）／**E-3 失敗時に古い状態が残る**（エラー表示だけして古いデータを消さず、成功に見える）／**E-4 楽観的更新のロールバック欠如**

### 特筆点
- **迷ったら C-1（高凝集×疎結合）を最優先**。これが満たされれば他の多くは自然に満たされる、という一原則を置く
- **C-2 DRY と C-3/C-4（AHA・三度目の法則）は「張力」**として明示的に扱い、「即共通化」も「一切共通化しない」もどちらも誤りとする
- **プロジェクト固有規約（CLAUDE.md・note.md・既存コード・code-map）が常にこのドキュメントより優先**。適用しない判断も、理由を一言添えれば正当
- **E-1〜E-4 だけは「主観の押し付けを避ける（LOW〜MEDIUM に留める）」の対象外**。好みの問題ではなく実害のある機能バグなので、実害に応じた重大度を付け、**修正＋ ID 名を含むリグレッションテスト**まで求める。レビュー観点も H/I ではなく B・D・E・F 側で効く
- **なぜ E-b を別枠にするか**: E-a はレビューで見つけやすいが、E-1〜E-4 は**一見動くコードに見える**。しかも **AI が書いたコードを同じ AI がレビューすると両方に同じ盲点が入る**ため、レビューでは安定して捕まらない——テストで固定するしかない、という前提に立っている
- 着想は Ishiyama「良いコードを書くために意識している17のTips」＋一般的設計原則（SOLID / DRY / YAGNI / AHA / Rule of Three / Law of Demeter）。**E-1〜E-4 は AI 支援開発で本番環境において実際に繰り返し観測されたリグレッションの一般化**（同一バグが4回作り込まれ、AI レビューが4回とも見逃した事例を含む）

## microservice-boundary-rules.md

### 一言でいうと
要件・設計段階で、機能をどのサービス境界（Bounded Context）に割り当て・どこを分割すべきかを判断するルール集。目的は「正しく分ける」ことではなく **「分けすぎない」こと**。

### 場所
`service-boundary/rules/microservice-boundary-rules.md`

### 参照するスキル・タイミング
- **service-boundary** — ステップ2で必読の本体ルール。service-boundary は beam3-design（新規開発の設計）から自動で、power3-design（既存への機能追加設計）からは大型機能時に任意で呼ばれる

### 主な内容
- **大原則** — ①既定はモジュラモノリス（1デプロイ＋内部モジュール境界。迷ったら分割しない）②論理境界（1リポ・1デプロイ内の区切り＝まず引く）と物理境界（別リポ・別デプロイ・別データストア＝バーを越えたときだけ）を分ける ③物理分離の対価（レイテンシ・部分障害・結果整合性・分散トランザクション困難・運用多重化）
- **判定ルール Rule 1〜6** — 1 同じ業務成果は同じ境界／2 異なるアクターは分離候補（ただしアクターが違うだけでは割らない）／3 独立価値のある能力はサービス候補／4 常に同時変更が必要なら同一境界／**5 データ所有権・整合性境界を割らない（最重要・最大のブレーキ）**／6 BFF はドメイン境界とは別レイヤー
- **物理分離のバー** — 4条件（独立業務価値・変更理由の独立・データ独立所有・スケール/可用性/技術差）が複数同時成立時のみ物理分割を検討。1〜2個なら論理境界どまり＝「将来の独立サービス候補」として記録
- **判断優先順位（7ステップ）** と **出力フォーマット（7項目）** — 機能棚卸し→推奨構成→境界間連携→BFF要否→物理or論理→将来候補→**却下した分割候補と理由**

### 特筆点
- 一貫して**過分割を避ける**思想。最終推奨は多くの場合「1デプロイ＋内部モジュール境界＋将来候補リスト」になるのが正常で、いきなり複数サービスに割るのは過剰のサイン
- Rule 5（データの整合性境界）は「分割への最大のブレーキ」——強整合の越境が1つでもあれば分割の費用対効果は急落する
- 個人・小規模開発ではチーム分割（Conway）の論理が弱いため、**運用負荷の多重化**を判断の主軸に置く

## api-design.md

### 一言でいうと
`api-endpoints.md`（設計契約）を書くときの判断基準を ID 付き（API-0〜14）で規定したもの。URL 命名・ステータスコード・レスポンス形式・ページネーション・バージョニングを扱う。**「良い API とは何か」を示す基準がそれまで存在せず、beam3 が毎回ゼロから決めていた**——service-boundary には判定ルールがあるのに API 設計には対応物が無かった、という構造の穴を埋めるもの。

### 場所
`beam3-design/references/api-design.md`

### 参照するスキル・タイミング
- **beam3-design** — step4 で `api-endpoints.md` を作成する場合**のみ**読む。HTTP API を作らない設計（CLI・ライブラリ・バッチ）では読まない（理由を一言述べてスキップ）
- **power3-design** — 既存 API にエンドポイントを足す／契約を変えるときに読む。ただし**既存の流儀が本書より上位**（後述）

### 主な内容（API-0〜14）
- **API-0 一貫性が最優先（最重要）** — どの選択肢を採るかより、**プロジェクト内で1つに決めて揃っている**ことの方が重要
- **リソースと URL**（API-1〜3）— 名詞・複数形・ケバブケース／URL に動詞を入れない／CRUD に乗らない操作だけサブリソースで動詞を許す／ネストは1段まで
- **メソッドとステータスコード**（API-4〜6）— 安全性・冪等性の表／**200 に `success:false` を詰めない**（HTTP の意味論を潰すとクライアント・監視が誤動作する）／401 と 403 を混同しない／作成は 201 ＋ `Location`
- **レスポンス形式**（API-7〜9）— エンベロープの有無はどちらでもよいが**混在させない**／エラーは機械可読な `code` ＋ フィールド単位の `details`（メッセージ文字列で分岐させない）／日時は ISO 8601・命名規則を統一
- **一覧**（API-10〜11）— **ページネーションは必須**（「今は件数が少ないから」で無制限に返さない）。オフセット vs カーソルの判断表付き／フィルタ・ソートの記法統一
- **バージョニング**（API-12〜14）— `/v1` から始め必要になるまで増やさない／**「破壊的変更」の定義を先に決める**（フィールド追加は非破壊、削除・改名・型変更は破壊的）／廃止は予告 → `Sunset` → `410`
- **リリース前チェックリスト**（12項目）

### 特筆点
- **API-0（一貫性）が教科書的正しさより上位**。既存 API があるなら本書ではなく**既存の流儀に合わせる**——power3（既存改修）では特にこれが効く
- **認証・認可・レートリミット・入力検証は収録しない**。`ai-security-guardrails.md` の P0/P1 が管轄で、本書からは参照だけする（二重管理の回避）
- 境界の切り方は `microservice-boundary-rules.md`、契約から型を生成する思想は coding-principles の **D-3（Contract-First）**。本書は「**契約の中身をどう決めるか**」だけを担う
- スタック固有の実装例（TS/Python/Go）は意図的に落としてある

## ai-security-guardrails.md

### 一言でいうと
AI がコードを書く際に**常時参照する「最低基準」のセキュリティ・ガードレール**。規則を P0（絶対遵守）／P1（原則）／参考（AI の実行範囲外）の3層で定め、beam/power の完了判定にも継承させる。

### 場所
`code-review/references/ai-security-guardrails.md`（スキル同梱の唯一の出典）。power0-onboard がプロジェクトの `docs/rule/ai-security-guardrails.md` にも配置し、グローバル CLAUDE.md が `@import` で常時読み込む

### 参照するスキル・タイミング
- **code-review** — step2 で必読。P0/P1 の唯一の出典として変更コードを照合
- **tdd-implement / direct-implement / beam5-implement / power5-implement** — 実装時に P0 を参照し Definition of Done に組み込む
- **power0-onboard** — レガシーに無い場合、このファイルを配置する
- ドキュメント自身が **beam4-tasks（各タスク完了条件に P0 を含める）・beam5-implement（DoD に必須チェックとして組込む）への継承**を明記

### 主な内容
- **P0（絶対遵守・違反＝一発アウト）5群** — 認証・認可（サーバー側必須／IDOR/BOLA を ID ごとに検証／パスワードは bcrypt・Argon2）／シークレット（直書き禁止・環境変数か Secret Manager・必要なキーは prep.md に列挙）／インジェクション（文字列連結禁止・ORM か Prepared Statement・eval 禁止・XSS 対策）／暗号（自前実装しない）／ログ（機密・個人情報を出さない）
- **P1（原則・逸脱時は理由明記）6群** — 入力スキーマ検証と allow-list／デフォルト拒否・JWT 検証／HTTPS・CORS 明示／レートリミット等（低リスクには過剰実装しない）／重要ロジックはサーバー側／監査ログと依存の lockfile 固定
  - **後から補完した3項目（Web アプリで実害に直結しやすい）**: **トークンを `localStorage` に置かない**（XSS で即座に窃取される。`httpOnly`＋`Secure`＋`SameSite` Cookie に置く）／**Cookie セッションでは状態変更に CSRF 対策**／**セキュリティヘッダー**（最低限 CSP、加えて nosniff・クリックジャッキング対策。**CSP は実装方針に影響するので設計段階で決める**）。いずれも Bearer のみの API 等では構造上非該当
- **参考（AI 実行範囲外）** — 本番/開発分離・スキャン定期実施・依存更新の人間承認・**AI は最終承認者ではない**
- **完了条件（DoD）** — 要件充足／テスト・型・Lint 成功／P0 違反なし・P1 逸脱は理由明記／CI ゲート

### 特筆点
- 冒頭に置かれる最優先の思想は「これは**最低基準**であり、質を犠牲にして形式充足するものではない」
- **「適用しない規則は黙って飛ばさず『なぜ不要か』を一言述べる」明示的スキップ義務**が最大の特徴。プロジェクト種別（Web/API/DB が主対象、CLI・ライブラリ等は非該当が多い）で適用範囲を調整する
- P0 は「コード上で直接守れ、かつ致命的」なものに絞り、運用・組織側は「参考」として明確に分離

## build-hygiene.md

### 一言でいうと
**設定・ビルド・デプロイの層**の判断語彙集。「コードは正しいのに、ランタイム・依存・ツール設定・デプロイ手順のせいで品質が静かに落ちる／本番で壊れる」問題を扱う、`coding-principles.md`（コード設計）と `ai-security-guardrails.md`（セキュリティ）の"間"を埋める第3のレンズ。各技法に ID（R-1 等）を振り、指摘は ID か技法名で引用する。

### 場所
`code-review/references/build-hygiene.md`

### 参照するスキル・タイミング
- **code-review** — 観点 L の出典。差分が `package.json`・lockfile・`tsconfig`/lint・CI・フレームワーク設定・`.devcontainer`/`Dockerfile` を触るときだけ**条件付きで**読み込む（触らなければスキップ）
- **power6-verify / beam5-implement** — レビューループ内で code-review が上記条件を満たせば自動的に効く
- （思想として）**direct-implement の setup・依存追加・ツール設定変更**時の「落とし穴」チェック語彙

### 主な内容（技法 ID 体系 R/P/T/V）
- **R. ランタイム再現性** — R-1 ランタイム版のピン留め（`>=` でなくメジャー固定）／R-2 dev/CI/prod パリティ／R-3 コンテナ・ベースイメージのピン留め（DevContainer/Dockerfile）
- **P. 依存・パッケージマネージャ** — P-1 ビルドスクリプト承認の明示管理（無条件許可の禁止）／P-2 lockfile 固定＋決定的インストール（frozen）／P-3 単一 PM（lockfile 混在の禁止）
- **T. ツール設定の健全性** — T-1 統合が"実効"か（lint/型チェックが実際に効いているか）／T-2 サイレント無効化の明示化（`ignoreBuildErrors` 等をゼロトレランスでなく「明示＋理由＋期限」で）／T-3 設定を現行形式に保つ
- **V. ビルド・デプロイ検証の規律** — V-1 クリーン環境でビルド／V-2 警告を"信号"として扱う／V-3 ビルド入力の再現性（env 宣言）／V-4 生成物を版管理に入れない（`dist/`・`.next/` 等）

### 特筆点
- **最優先の一原則: 迷ったら V-1（クリーンビルド）＋ V-2（警告を拾う）**。この2つが回れば以下の多くは事前に露見する
- **🔶「やり過ぎると逆効果」型を明示**（R-1 の exact 固定・P-1 の無条件承認・T-2 のゼロトレランス・V-2 の `--max-warnings 0`）——絶対規則でなく文脈で重み付けする語彙
- **アプリ vs ライブラリで正解が逆**の項目がある（R-1/R-3: アプリは版を固定／ライブラリは互換範囲を広く宣言し CI マトリクスで複数版を試す）
- coding-principles・ai-security とは**二重管理しない**（シークレットの値は ai-security P0、コード設計は coding-principles に出典を置き、本ファイルは"運用・宣言面"だけを足す）
- 着想は実インシデントの一般化（Vercel デプロイの3警告が既存の「全 green」ゲートをすり抜けた事実）

## ui-performance-verification.md

### 一言でいうと
「実際に動かして確かめる」ときの**目標値**（PERF-0〜4）と**手順**（QA-1〜5）。beam5/power6 の実環境確認は従来「動かせ」とあるだけで中身が無く、beam2 も「NFR は数値必須」なのに数値の出どころが無かった——その両方を1つの出典で埋める。**アクセシビリティ（WCAG AA・キーボード操作）はシステム全体でここにしか無い**。

### 場所
`beam5-implement/references/ui-performance-verification.md`

### 参照するスキル・タイミング
- **beam2-requirements** — **§1 の目標値だけ**を読む。NFR に書く性能数値の相場として使う（手順は読まない）
- **beam5-implement** — step4「実データ・実環境での動作確認」の中身として §2 を使う
- **power6-verify** — step3 の実環境検証で同じく §2 を使う（既存改修向けの注意あり・後述）

### 主な内容
- **§1 性能目標（PERF-0〜4）** — PERF-0 目標値は「相場」であって要件ではない／PERF-1 **Core Web Vitals**（LCP < 2.5秒・CLS < 0.1・INP < 200ms ＋ 補助の FCP・TTFB）／PERF-2 リソース量（総ページ < 1MB・JS < 200KB gzip）／PERF-3 **API は平均でなく p50/p95/p99**／PERF-4 検証できる形で書く（指標・条件・数値）
- **§2 検証手順（QA-1〜5）** — QA-1 スモーク（起動・コンソールエラー・4xx/5xx）→ QA-2 主要ジャーニー（**正常系＋異常系**）→ QA-3 レスポンシブ（375/768/1440px）→ **QA-4 アクセシビリティ**（axe 等で WCAG 2.1 AA・キーボードだけで完走・フォーカス順序）→ QA-5 性能実測。**前段が落ちたら先へ進まない**
- **適用条件の表** — Web アプリ＝全項目／API のみ＝PERF-3・QA-1 のみ／CLI・ライブラリ＝原則なし
- **実行環境** — DevContainer 内の Playwright（Chromium 導入済み）。使えなければ**「自動検証できていない」と明記**する

### 特筆点
- **アクセシビリティが最大の追加**。自動チェック（axe）は機械判定できる違反しか出せないため、**キーボード操作だけは必ず手で通す**と明記している
- **平均を使わない**（PERF-3）。平均は「大半は速いが一部の利用者だけ極端に遅い」状態を隠してしまう
- **相場をそのまま写さない**（PERF-0）。対象ユーザーの回線・端末で調整し、**理由を添えて** NFR に書く
- **power6（既存改修）では触った画面に絞る**。既存に元からある違反は「既知」として記録し、その PR の修正対象にはしない（スコープ膨張の防止）
- 多くのプロジェクトで大部分が非該当になる前提。**該当しない項目は理由を一言述べてスキップ**する

## code-map-diagrams.md

### 一言でいうと
既存システムを読んだ結果を、**人間が見て分かる図**と**機械が検証できる根拠**の両輪で残すための基準。従来 code-map の全体像は「矢印・箇条書き、または簡易図」と曖昧で、内容の正しさは AI の自己申告に頼っていた——ここを**図の必須化**と**根拠の機械検証**で埋める。

### 場所
`power2-understand/references/code-map-diagrams.md`（検証スクリプトは `power2-understand/scripts/verify-code-map-evidence.sh`）

### 参照するスキル・タイミング
- **power2-understand** — step3-4。`docs/code-map.md` の全体像を書くときに読み、図と根拠表を作って検証スクリプトを通す。**既存 code-map があっても、図と根拠が無ければ起こし直す**（beam 製リポジトリの code-map は索引だけで地図の節が無い）
- **power6-verify** — step7。実装でコードが動いた分、根拠を HEAD に対して**再検証**する
- **power5-implement** — 図が実態とずれたら直すが、**検証リビジョンは書き換えない**（未検証なのに検証済みに見せないため）

### 主な内容
- **3種の図（Mermaid）** — **A. 構成**（層・モジュール・境界・外部依存／原則必須）／**B. 主要フロー**（代表的な要求1本を入口から出口まで／明確な入口があるなら必須）／**C. データの流れ**（永続化・外部データ源があるなら推奨）。**非該当はスキップして理由を一言述べる**
- **作図規律 DG-1〜DG-5** — DG-1 メインパスを先に作る／DG-2 主要ノードは最大12／DG-3 **制御を足す前に価値の低い辺を削る**／DG-4 ラベルは装飾でなく意味データ／**DG-5 憶測を描かない**（実コードで確認したものだけ）
- **根拠の記法** — 図の中ではなく**直下の対応表**に `` `src/x/y.ts:12-48` `` 形式で置く。検出条件は「バッククォート内・`/` を含む・拡張子を持つ・`://` を含まない」
- **検証スクリプト** — code-map 冒頭に記録した commit SHA の時点で、根拠のパスと行が実在するかを検査（パス安全性・ファイル実在・行の実在）。**依存は bash と git のみ**

### 特筆点
- **🔵 の意味が変わる**。従来「AI が確認した」という自己申告だった 🔵 を、**検証を通った根拠が付いている項目だけ**に限定した。落ちた根拠は直すか 🟡 に格下げする
- 理由は code-review の設計原則 #6 と同じ——**AI が書いたものを同じ AI がレビューすると、両方に同じ前提＝同じ盲点が入る**。機械的検査でしか担保できない
- **図を描かせること自体が目的の半分**。散文は曖昧なまま書けてしまうが、図はノードと辺を決めないと描けない。**描けない＝理解できていない**のシグナルとして使う
- もう半分は**人間のレビュー効率**。power の推奨運用は「power4 まで進めて人間がレビュー」だが、散文だけでは AI の理解が正しいか短時間で判定できない。図なら誤解が最短で見つかる
- **座標を手で置く形式は採らない**。Mermaid で自動レイアウトさせ、**コード理解に使うべき労力を幾何計算に溶かさない**
- 検証されない書き方をしても**黙って対象から外れるだけ**なので、出力の「検証した根拠: N 件」が書いた数と一致するかを必ず確認する運用

## kano-protocol.md

### 一言でいうと
機能を**狩野モデルの5分類（M/O/A/I/R、＋矛盾の Q）に「質問→表引き」で機械的に振り分け**、その分類をスコープ4案（ミニマム/要望/リッチ/フル）への採否にマッピングするための分類プロトコル。

### 場所
`scope-options/references/kano-protocol.md`

### 参照するスキル・タイミング
- **scope-options** の define モード（機能×4案マトリクスの作成中、Kano 分類の工程）で必読。scope-options は beam2 から呼ばれる

### 主な内容
- **質問ペア** — 機能ごとに2問をペルソナ視点で自問。機能的質問「あったらどう感じるか」／非機能的質問「なかったらどう感じるか」。回答は5択（気に入る／当然だ／どちらでもない／仕方ない／気に入らない）
- **評価表** — 機能的×非機能的の5×5マトリクスから分類を機械的に決定。M 当たり前（無いと不満→ミニマム必須候補）／O 一元的（あるほど満足→要望の主軸）／A 魅力的（あると喜ばれる→リッチ/フル候補）／I 無関心（原則不採用）／R 逆品質（ある方が嫌がられる→不採用＋警告）／Q 懐疑（回答矛盾→定義見直し）
- **圧縮確認の手順** — 質問爆発の防止。AI がペルソナ視点で全機能を仮分類し確信度（🔵🟡🔴）を付け、🔵 は自動採用・**🟡🔴 のみユーザー確認**（一括の multiSelect 1問＋境界ケースの個別確認 0〜2問）
- **分類→4案の既定マッピング表** — 各分類の各案での採否を規定（逸脱可だが逸脱セルには理由必須）

### 特筆点
- 設計思想は**「分類の恣意性を質問→表引きで機械的に抑える」**。狩野モデルの標準質問法を、AI がペルソナ視点で自問する形に成文化
- 質問爆発を防ぐ**「AI 仮分類＋確信度で 🟡🔴 だけ聞く」二段構え**が特徴

## variant-checklists.md

### 一言でいうと
scope-options の**リッチ案／フル案の候補を「思い付き」でなく列挙可能なチェックリストから系統的に導出する**ための、EN-*（強化）と DS-*（発見）の2系統チェックリストと記載様式。

### 場所
`scope-options/references/variant-checklists.md`

### 参照するスキル・タイミング
- **scope-options** の define モード（リッチ案/フル案の候補導出の工程）で必読

### 主な内容
- **EN-*（強化チェックリスト・リッチ案用）** — 既存機能に照らし「どのユーザーストーリー(US-*)の体験を強化するか」を答えられる候補だけ採用。6カテゴリ: EN-1 回復性（アンドゥ・自動保存・リトライ）／EN-2 フィードバック（進捗・通知・ライブ反映）／EN-3 探索性（検索・フィルタ・ページング）／EN-4 入力効率（一括操作・補完）／EN-5 性能体感（キャッシュ・遅延読込）／EN-6 見た目・快適さ（テーマ・アクセシビリティ）
- **DS-*（発見チェックリスト・フル案用）** — 各カテゴリを網羅走査し、採用候補に **コアジョブとの関係（直結／支援／周辺）を明記**（周辺のものは「将来必要になる蓋然性」を一言で根拠づける）。6カテゴリ: DS-1 ライフサイクル（移行・バックアップ・退役）／DS-2 管理・運用（管理画面・監査・統計）／DS-3 連携・拡張（API・Webhook・エクスポート）／DS-4 複数化・スケール（権限・多言語）／DS-5 品質・保守（E2E・性能テスト）／**DS-6 スコープ外の再評価**（PRD 第10章の除外項目を1つずつ見直す）
- **記載様式** — 追加候補のセルには出典 ID を必ず併記（例: 採用（出典: EN-2 / US-03 の体験強化））。チェックリスト外は「その他（要根拠）」節に分離し、根拠を書けたものだけマトリクスに昇格

### 特筆点
- 中核は**「思い付き排除」**——候補は必ず列挙可能なソース（EN-*/DS-*）から出し、チェックリスト外は根拠が書けなければ落とす
- **役割分担が明確**: EN-* は既存体験の強化に限定（新領域は足さない）、新領域はフル案の DS-* の領分
- **DS-6「スコープ外の再評価」は最有力の発見源**——一度検討して除外された機能の在庫だから
